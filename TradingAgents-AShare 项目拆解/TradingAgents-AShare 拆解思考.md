
### 第 07 章 分析师团队

一、7 个分析师从 LangGraph 的 START 同时出发、<mark style="background:#d3f8b6">互不通信、各写一份报告，全部写完后汇合</mark>，把报告交给多空研究员去辩论

为什么：避免报告内容互相污染（这个设计我是认可的，和subagent的含义一样）
问题是7个agent是否过多了，这些agent分析的方法论是什么，数据是怎么处理的（如果说每个agent实现一个方向的数据分析，那如何保证总数据不会对agent的分析产生影响呢）

回答：==这部分的设计很好==
1. 数据采集是集中的，但是每个agent的prompt只能收到它对应的那部分数据（<font color="#92d050">可以调查这种能力是如何在langgraph框架中实现的</font>）
2. 每个agent的prompt要求其只能实现一个方向的分析
3. 每个agent没有工具调用的能力，无法获得数据（<font color="#92d050">类似于subagent中只给部分权限的做法</font>）

我的想法：数据问题暂时不管，但是这个分开思考的方法可以借鉴，甚至可以依此构建相应的复查体系（当不同agent返回的信息矛盾的时候，是如何解决这个矛盾问题的）
应该将一个大的投研报告产出的方法论拆成不同的几部分（仿照这个程序的设计）
这样不仅能更加规范产出报告的格式，还能对应后续报告产出的各个部分

这部分后续目标：聚焦在研报方法论
1. 将7个agent的提示词都抽出来，看它们的方法论是什么
2. 调研现在流行的投研报告是如何构建的，需要哪些方面的数据，进行什么样的数据处理（如有必要，搜集数十篇投研报告，以其为模板进行实现）
3. 根据总结出来的方法论，反推现在的数据源缺什么，看是否能够补全相应的数据信息

二、社交媒体分析师没接社交 API，它拿新闻文本当情绪代理（原因是专用社交 API 有速率限制）。所以”情绪”实际是”新闻语气”，不是真实散户情绪。你如果在意这块信号质量，这是第一个要换数据源的地方。

我的想法：
1. 真正的情绪信息很难通过现有的数据源获取（但是不能放弃对数据源能否获取相应情绪信息的调查）
2. 量价信息虽然也会被人操控，但是其成本注定了操控难度很高
3. 可以用行为类情绪数据作为衡量标准：虎榜、两融余额、散户资金净流入、开户数、雪球/百度指数热度（易获取且难操控）

接下来做什么：
1. 确定研报方法论中是否有对情绪信息分析的内容，看看专业人士是如何实现情绪分析的
2. 优化现有的情绪分析体系，可能要和其他agent合并 

三、量价分析师的 Wyckoff 判断不是 LLM 做的。......这意味着量价信号的质量由那 172 行 Python 决定，改 prompt 改不动它。

我的想法：
1. 数据分析让脚本来做是完全正确的。既省token，又快又好

接下来做什么：
1. 看看是否能将数据的计算公式、数据来源都让LLM生成出来，并且留存到报告中（确保数据的血缘，从而方便LLM）

四、LLM 没绑工具 → 永不产生 tool_calls → 那些 ToolNode 执行 0 次。

我的想法：
1. 这部分可以理解，是为了
	1. 便宜、快——单次调用
	2. 数据一次配齐，防止agent调用工具产生幻觉、错误
2. 问题很严重：LLM自身有完整性解释的倾向。如果发现数据不齐，agent会基于手头的东西硬写，空白处用幻觉（静默失败）

接下来做什么：
1. 我不打算改变这种方式。ReAct模式本身也是为了工具调用。如果数据齐全自然不需要进行调用。但是如果数据不齐全怎么办？是否能设计成agent发现数据不齐全后对总调度进行反馈，然后总调度调用工具重新获取信息。这样是否过于复杂且可行度如何呢
2. 防止LLM因数据不全胡乱生成内容：
	1. AI给出的建议是对传递给agent的数据进行检查（用脚本实现）
	2. 提示词里放口，让AI在数据不全的情况下不做，但是在输出内容中提醒

和AI讨论后确定的方案：
我原来的想法：对agent生成内容的模板进行约束，明确这个agent能用这些数据生成~~哪些内容~~，即数据确定—>内容确定。这样，只用在agent的上游构建门禁，用脚本检查数据即可避免数据不全的问题
AI的回复：
1. **能模板化且通用的是"输出结构"，不能模板化的是"结论内容"。**——因为如果内容也用统一模板实现，LLM就没用了，不如直接写 if-else 填空
2. **不同股票"数据可用性"天生不同**——有些股票天生就缺某些板块的数据

具体方案：
1. 把板块分成两类：
	- **核心板块**：所有股票都有数据、必须输出（日线趋势、当日量能）
	- **条件板块**：数据够才输出，不够就显式关闭并标注"数据不足，本板块略过"（长周期趋势、机构观点）
2. 核心字段缺 → fail fast 跳过这只股票；条件字段缺 → 关掉对应板块 + 标记。

这里引出一个新的问题：这个所谓的投研agent功能似乎和我想的不一样
它并不是出一个完整的投研报告，而是准确直接地得出是否购买的建议
输入？输出？
结果：它的产物既不是"买/不买"，也不是投研报告——是一份<mark style="background:#d3f8b6">交易决策工作底稿</mark>
简单来说，就是多轮agent探讨后得到的内容。其中的数据、字段没有做血缘——模型自己编造数据，模板没有敲定——每次生成的‘会议记录’没有固定的格式
算是好消息：最大的问题还是没有模板，但是整个项目的运行逻辑和一些细节都是可行的，完全可以作为投研底座实现

模板里凡是流水线不产出的字段，模型就会编来填。——每个字段都要能追到一个真实数据源。

我现在已经收集了相当数量的个股研报的组成成分
我的想法是确定哪些组件是经常用到的，哪些用到的较少
取其中比较重要的一些组件，构成闭环即可（但是这个组件分析报告要留下来，要作为汇报的内容之一）

研报不仅是组件的使用频率很重要，对于不同行业也有不同的偏好
我的想法是确实针对不同行业，安装不同的组件，但是这些组件必然有的用得多，有的用得少；有的数据好拿，有的不好拿
对于组件的频率问题，我打算去慧博平台上调研，看一个月甚至几个月中，不同行业研报出现的次数，从而量化这个行业的出现次数，进而量化组件频率

已经拿到相关信息了。现在的想法是确定最低模板包含组件，构成成本最低模板；但是不放弃深层次组件，将其作为深层次内容，只有在需要的时候再提供这方面的搜索与构建

但是数据是重点，需要对A股的数据获取根据现有的组件进行分配

现在已经调研了A股数据方面的程序，决定构建数据源 三档稳定性框架（目的是为了保证数据稳定获得）：tushare / akshare / baostock
决定既穷举这几个数据源能够获得的数据，也和研报组件所需的数据进行匹配
	技巧：结论粒度按「组件」不按「字段」
	不是什么数据都要，根据获取必要性构建

等组件、数据等内容完成，后续的任务重心可能放在将这些组件按照研报的模板组合起来，并且调试字体、格式等

我的想法是先将整个流程跑出来，再根据我的理解对数据具体处理
主要有以下几个方面：
1. 确保数据齐全再生成报告内容。如果数据不齐，要么做数据获取；要么做兜底处理（加门禁检查，使用schema约束），不能无视这个问题，从而保证LLM生成的内容不是乱说
2. 引入脚本，并强调其重要性

和AI的沟通让我深以为然，7agent这个章节是整个程序的核心，且是大工程
重点在于数据层。
① 这环节里真正该先啃的是**数据层**（确定性、可控、投产比最高），不是 LLM 分析师层（它的质量上限被数据层决定）；
② <mark style="background:#d3f8b6">策略要改成"契约先行"</mark>——先冻结这层的输出格式再动下游，否则上游一改、下游全返工。

至于多 agent 辩论的价值，我认为在数据问题解决后可以考虑引入几位金融学大师的投资理念的那个程序作为参考，但是现在数据确实是重中之重

AI提出的方案是使用

AI已经将第一版构建完成，但是我发现有问题：问题主要集中在：我让 AI 构建出一篇完整的研报，所需的最小研报组件循环，但是 AI 由于对研报必须的最小组件的理解有问题，所以导致现在最新构建出来的内容是不完整的。
绝大部分只有金融数据的分析，而没有大模型参加的点评。所以我现在的做法是：将之前总结的完整的研报组件库重新拿出来，让 AI 从用户真正看到的角度去分析一篇研报所需的最小组件循环。
通过对这些组件的确定，来明确如何对现有程序的优化和改进。

同时我确定了图在研报中的重要性，已经让AI去调查，如果从读者的角度来看，这些图的意义是什么，为什么要配这些图，配了这些图需要哪些工具，从而实现研报内容完整性、准确性的构建。

如何保证文章中的数字没有问题：上游把所有数字算好放进一个"允许清单"，模型写完之后，校验器把文章里每个数字抠出来，一个个拿去清单里找。找得到就放行，找不到就判编造。
校验器只会查表不会算，所以模型也不能算

主窗口的能力：这个窗口的主要职能是掌握整个项目的脉络。将开发任务用superpowers整理成可开发的一个个计划表，然后让不同的新窗口按照计划实现；再将其他窗口实现的开发情况返回这个窗口中，进行下一步计划的派发和反馈。这是一个完整的开发飞轮
  所以，这个窗口不要主动承接开发任务，如果可行就直接给我一份完整的计划表，我让其他窗口进行开发；但是同时，这个窗口应该及时根据其他窗口反馈的开发情况及时给我任务书让我去开新窗口进行开发。我希望上面这两点你能自己进行，而不是我要求这个窗口进行什么操作你才进行
