TradingAgents 图并非简单的管道——它是一个**状态驱动的条件状态机**，其执行路径在运行时通过检查 Agent 的输出和辩论计数器来决定。三种截然不同的路由机制控制着流程：允许 Agent 迭代获取数据的**分析师工具调用循环**、具有轮次限制交替的**多头/空头投资辩论**，以及随后带有交易员修订循环的**三方风险辩论**。理解这些条件边对于扩展图、调整辩论深度或调试为何特定 Agent 被调用（或未被调用）至关重要。

## 路由架构概述

`ConditionalLogic` 类将每个路由决策集中到一个可测试的单一对象中。在图构建期间，`GraphSetup` 通过 LangGraph 的 `add_conditional_edges()` 将每个方法注册为条件边，并将字符串返回值映射到具体的节点名称。这将*路由策略*与*图拓扑*解耦——你可以更改辩论阈值或添加新的发言者转换，而无需触碰图的连线。

## 分析师工具调用循环

七个分析师维度（市场、社交、新闻、基本面、宏观、聪明钱、量价）均遵循相同的条件模式：在分析师 LLM 生成响应后，图会检查最后一条消息是否包含 `tool_calls`。如果存在，执行路由至相应的 `ToolNode`；如果不存在，则认为该分析师已完成，并路由至充当扇入同步点的无操作“分析师完成”节点。

路由方法通过命名约定动态解析——`getattr(self.conditional_logic, f"should_continue_{analyst_type}")` 将每个分析师键映射到其专属方法。这七个方法共享相同的实现：检查 `last_message.tool_calls`，返回 `"continue"` 或 `"done"`。这种一致性意味着添加新的分析师维度只需：(1) 在 `ConditionalLogic` 上新增一个 `should_continue_xxx` 方法；(2) 在 `GraphSetup` 中注册该节点和边。

| 分析师键 | 路由方法 | 工具节点 | 完成节点 |
| --- | --- | --- | --- |
| `market` | `should_continue_market` | `tools_market` | Market Analyst Done |
| `social` | `should_continue_social` | `tools_social` | Social Analyst Done |
| `news` | `should_continue_news` | `tools_news` | News Analyst Done |
| `fundamentals` | `should_continue_fundamentals` | `tools_fundamentals` | Fundamentals Analyst Done |
| `macro` | `should_continue_macro` | `tools_macro` | Macro Analyst Done |
| `smart_money` | `should_continue_smart_money` | `tools_smart_money` | Smart Money Analyst Done |
| `volume_price` | `should_continue_volume_price` | `tools_volume_price` | Volume Price Analyst Done |

工具循环是无界的——只要 LLM 持续发出 `tool_calls`，分析师就可以无限期地调用工具。在实践中，LLM 的行为通常在 2-3 次迭代后自然收敛。如果你需要设置硬性上限，请在 `AgentState` 中使用计数器包装现有检查。

## 多头/空头投资辩论循环

投资辩论是多头研究员和空头研究员之间的**双 Agent 交替循环**。`should_continue_debate` 方法通过检查 `investment_debate_state["current_speaker"]` 和全局 `count` 字段来确定下一位发言者。终止条件为 `count >= 2 * max_debate_rounds`，因为每轮包含两次发言（一次多头，一次空头），因此在研究经理接管之前，总共会交换 `2 * max_debate_rounds` 条消息。

发言者交替逻辑非常直观：如果上一位发言者的键以 `"Bull"` 开头，则路由至空头研究员；否则路由至多头研究员。两个研究员节点共享相同的 `should_continue_debate` 条件边，但使用不同的路由映射——多头的映射将 `"Bear Researcher"` 发送至空头节点，而空头的映射将 `"Bull Researcher"` 发送至多头节点。两者的映射均将 `"Research Manager"` 路由至裁判。

```python
if state["investment_debate_state"]["count"] >= 2 * self.max_debate_rounds:
    return "Research Manager"
# 交替：切换至对方发言者
if state["investment_debate_state"].get("current_speaker", "").startswith("Bull"):
    return "Bear Researcher"
return "Bull Researcher"
```

在默认的 `max_debate_rounds=1` 设置下，辩论恰好产生 2 条消息（多头先发言，空头回应），随后研究经理做出裁决。设置 `max_debate_rounds=3` 将产生 6 条消息——即三个完整的来回交锋。

## 三方风险辩论循环

风险辩论引入了**三方 Agent 循环赛**：激进 → 保守 → 中立 → 激进 → ……。`should_continue_risk_analysis` 方法通过检查 `risk_debate_state["latest_speaker"]` 来维持这种轮换。终止阈值为 `count >= 3 * max_risk_discuss_rounds`，因为每轮包含三次发言。

| 最近发言者 | 下一位发言者 |
| --- | --- |
| Aggressive | Conservative Analyst |
| Conservative | Neutral Analyst |
| *(Neutral 或初始状态)* | Aggressive Analyst |

当来自*任何*一个辩论节点达到计数阈值时，图都会路由至 `"Risk Judge"`——即给出最终裁决的风险经理节点。所有三个条件边注册均将 `"Risk Judge"` 映射到同一节点，从而确保无论哪位辩手最后发言都能收敛。

`max_risk_discuss_rounds` 配置控制的是深度而非方向。循环赛顺序是固定的——你不能在轮次中途跳过某位发言者。如果你需要提前终止（例如，所有主张都已解决），则需要在 `should_continue_risk_analysis` 中添加基于主张的守卫，以检查 `unresolved_claim_ids` 的长度。

## 交易员修订循环

架构上最具意义的条件边是**交易员修订循环**——这是图中唯一一个带有累积反馈重新访问已执行节点的循环。在风险裁判做出裁决后，`should_revise_after_risk_judge` 会检查 `risk_feedback_state` 以决定交易员是否必须修订其计划。

决策逻辑包含两个必须同时满足才能进入修订循环的条件：`revision_required` 必须为 `True`（当裁决为 `"revise"` 时设置），且 `retry_count` 必须 ≤ `max_retries`（默认为 1）。当两个条件均满足时，执行路由回交易员，交易员将结合风险裁判给出的硬性约束、软性约束和修订原因重新生成其计划。

```python
def should_revise_after_risk_judge(self, state: AgentState) -> str:
    feedback = state.get("risk_feedback_state", {})
    if (
        feedback.get("revision_required")
        and safe_int(feedback.get("retry_count", 0), 0)
            <= safe_int(feedback.get("max_retries", 1), 1)
    ):
        return "Trader"
    return "END"
```

### 修订状态机

`RiskFeedbackState` 通过多个字段跟踪修订的生命周期。在每次调用风险裁判时，`extract_risk_judge_result` 工具会解析裁判结构化的 `<!--RISK_JUDGE: {...}-->` 块，以提取 `verdict`、`hard_constraints`、`soft_constraints`、`execution_preconditions`、`de_risk_triggers` 和 `revision_reason`。如果裁决为 `"revise"`，`retry_count` 将递增，并且 `revision_required` 会被设置为 `True`。随后，交易员会消费 `summarize_risk_feedback()` 以了解必须更改的内容。

| RiskFeedbackState 字段 | 用途 | 设置者 |
| --- | --- | --- |
| `retry_count` | 已尝试的修订循环次数 | Risk Manager（在 "revise" 时递增） |
| `max_retries` | 修订次数上限（默认为 1） | Initial state / config |
| `revision_required` | 交易员是否必须修订 | Risk Manager（在 "revise" 时为 True） |
| `latest_risk_verdict` | "pass"、"revise" 或 "reject" | Risk Manager |
| `hard_constraints` | 不可协商的约束 | 从裁判输出中解析 |
| `soft_constraints` | 建议性约束 | 从裁判输出中解析 |
| `revision_reason` | 计划被退回的原因 | 从裁判输出中解析 |

### 修订会重置风险辩论

一个关键细节：当交易员被退回进行修订时，它会通过 `build_empty_risk_debate_state()` **将整个 `risk_debate_state` 重置**为空状态。这意味着三位风险辩手将对修订后的计划进行全新的辩论，而不是继续上一次辩论的历史。这样设计的基本原理是，修订后的交易计划发生了根本性变化——旧的风险主张可能不再适用，而新的风险可能会出现。

## 循环内主张驱动的状态传播

虽然条件路由逻辑控制着*下一个执行哪个节点*，但 `debate_utils.py` 中的**主张跟踪子系统**控制着*循环迭代之间流动哪些信息*。每次调用辩手时都会调用 `update_debate_state_with_payload()`，该函数会从 LLM 输出中解析结构化的 `<!--DEBATE_STATE:-->` 或 `<!--RISK_STATE:-->` 块，以更新主张、历史记录和轮次元数据。

主张的生命周期遵循：`open` → `addressed` → `resolved` 或 `unresolved`。`focus_claim_ids` 字段确保下一位发言者优先处理最重要的未解决主张，而 `round_goal` 则随着轮次的推进提供逐步升级的辩论目标。这创造了一种*收敛型*辩论——每一轮都在缩小分歧面，而非扩大它。

| 状态字段 | 投资辩论 | 风险辩论 |
| --- | --- | --- |
| 发言者跟踪 | `current_speaker` | `latest_speaker` |
| 轮次计数器 | `count`（按消息计） | `count`（按消息计） |
| 主张前缀 | `INV-{n}` | `RISK-{n}` |
| 结构化标记 | `<!--DEBATE_STATE:-->` | `<!--RISK_STATE:-->` |
| 轮次目标域 | `"investment"` | `"risk"` |

## 配置参数

所有的辩论深度均由两个配置键控制，这两个键在 `TradingAgentsGraph` 初始化期间传递给 `ConditionalLogic`。Propagator 上的 `max_recur_limit` 充当了防止 LangGraph 无限循环的安全网。

| 配置键 | 默认值 | 影响范围 | 公式 |
| --- | --- | --- | --- |
| `max_debate_rounds` | 1 | 投资辩论深度 | `2 × value` 总消息数 |
| `max_risk_discuss_rounds` | 1 | 风险辩论深度 | `3 × value` 总消息数 |
| `max_recur_limit` | 100 | LangGraph 递归限制 | 节点调用总数的硬性上限 |

要提高辩论的严谨性，可将 `max_debate_rounds` 提升至 3，将 `max_risk_discuss_rounds` 提升至 2——这将在每个循环中产生 6 条投资消息和 6 条风险消息。请注意，每增加一轮都意味着一次完整的 LLM 调用，并伴随着相应的延迟和成本。

## 端到端流程概述

追踪完整的执行路径可以揭示三种路由机制是如何组合的：

1. **扇出**：所有选定的分析师并行运行，每个分析师都有独立的工具调用循环
2. **扇入**：所有“分析师完成”节点汇聚于多头研究员
3. **投资辩论**：多头 ↔ 空头交替进行 `2 × max_debate_rounds` 轮次，然后由研究经理裁决
4. **交易员**：根据辩论结果生成投资计划
5. **风险辩论**：激进 → 保守 → 中立轮换进行 `3 × max_risk_discuss_rounds` 轮次，然后由风险裁判裁决
6. **修订门**：如果风险裁判的裁决为 "revise" 且仍有重试次数，交易员将修订计划 → 风险辩论从头开始；否则，图到达 `END`

在包含一次修订循环的单次分析运行中，理论上的最大节点调用次数为：`(分析师轮次) + (2 × max_debate_rounds + 1) + (1 + 3 × max_risk_discuss_rounds + 1) × 2`，其中 `× 2` 代表初始风险通过加上一次修订通过。使用默认值时，这大约是 20-30 次调用——远在 `max_recur_limit=100` 的安全上限之内。
