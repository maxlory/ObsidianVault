**三方风险辩论与修订**是系统在发布交易决策前的最后一道把关机制。在分析师团队产出七维度研究、多空辩论综合出投资论点、交易员制定出可执行计划之后，三位对抗性风险分析师将从根本不同的立场——**激进、保守和中立**——对该计划进行质询。他们结构化的主张在多轮交叉质询中存续或瓦解，随后独立的**风险裁判**将发布一个机器可读的裁决：通过该计划、直接否决它，或强制交易员在硬性约束下重新制定计划。本页将剖析辩论拓扑、主张生命周期、裁判裁决协议，以及使系统具备自我修正能力的修订循环。

## 辩论拓扑：带结构化退出的循环赛

三位风险辩论者作为**循环子图**接入 LangGraph 状态机，并采用确定性的循环路由。交易员节点始终流向激进分析师，随后传递给保守分析师，再传递给中立分析师，最后循环回激进分析师——直到轮次计数器达到配置的上限，此时流程退出至风险裁判。

> **[原图为 mermaid 图；下列为从渲染 SVG 提取的节点/边标签（近拓扑序），非原始 mermaid 源码]**
>
> latest_speaker ≠ cycle end → count < 3 × max_risk_discuss_rounds → count ≥ 3 × max_risk_discuss_rounds → verdict = revise → verdict = pass/reject → Trader → Aggressive → Conservative → Neutral → RiskJudge → END

路由逻辑位于 `ConditionalLogic.should_continue_risk_analysis` 中，该函数将 `risk_debate_state` 中的 `count` 字段与 `3 × max_risk_discuss_rounds` 进行比对（每个完整轮次包含三位发言者，因此总消息数是配置轮次数的三倍）。如果达到上限，该函数返回 `"Risk Judge"`；否则，它将根据 `latest_speaker` 路由到下一位发言者。随后，`should_revise_after_risk_judge` 方法会检查 `risk_feedback_state`，以决定交易员是否必须修订（`"Trader"`）还是工作流终止（`"END"`）。

## 三位辩论者：角色、立场与上下文

每位辩论者都是一个工厂函数，返回基于共享 LLM 实例的异步节点闭包。它们共享相同的结构模式——读取辩论状态、使用所有分析师报告加上交易员计划格式化提示词、流式传输 LLM 响应、解析结构化载荷——但在**立场**、**提示词模板**和**主张导向**上有所不同。

| 辩论者 | 工厂函数 | 立场 | 提示词键 | 主张焦点 | 读取来源 |
| --- | --- | --- | --- | --- | --- |
| **激进分析师** | `create_aggressive_debator` | `aggressive` | `aggressive_prompt` | 执行风险，上行约束 | 保守 + 中立响应 |
| **保守分析师** | `create_conservative_debator` | `conservative` | `conservative_prompt` | 下行风险，流动性，止损缺口 | 激进 + 中立响应 |
| **中立分析师** | `create_neutral_debator` | `neutral` | `neutral_prompt` | 信息矛盾，虚假两难 | 激进 + 保守响应 |

每位辩论者读取内容的非对称性是刻意为之的：激进辩论者阅读*另外两位*的响应，以寻找保守方案中的弱点；而保守辩论者阅读激进和中立的响应，以 dismantle 过度乐观的观点。中立辩论者同时接收双方观点，能够识别出辩论在何处陷入了抽象讨论，而非可操作的分歧。

每位辩论者都会接收完整的上下文包——`market_report`、`sentiment_report`、`news_report`、`fundamentals_report` 和 `trader_investment_plan`——以及不断演进的 `history`、`focus_claim_ids`、`unresolved_claim_ids` 和 `round_goal`。这确保了每个论点都建立在相同的证据基础之上，防止辩论漂移至无根据的推测。

流式追踪器可见的轮次数计算为 `count // 3 + 1`，因为每轮会产生三条消息（每位辩论者一条）。这与前端人类可读的“Round 1, Round 2”显示相匹配。

## 主张生命周期：从开放到解决

风险辩论实现了**主张驱动**协议，每位辩论者都可以注册新的风险主张、回应现有主张，以及将主张标记为已解决或未解决。这将辩论从无结构的争论转化为可追踪、可审计的风险登记册。主张状态机在 `update_debate_state_with_payload` 内部运行，该函数处理每个 LLM 嵌入其响应中 HTML 注释标签 `<!-- RISK_STATE: {...} -->` 内的结构化 JSON 载荷。

> **[原图为 mermaid 图；下列为从渲染 SVG 提取的节点/边标签（近拓扑序），非原始 mermaid 源码]**
>
> 辩论者创建新主张 → 对手回应 (responded_claim_ids) → 辩论者标记为已解决 (resolved_claim_ids) → 标记为实质性争议 → 达成共识 → open → addressed → resolved → unresolved

主张条目的数据结构捕获了每个风险断言的完整来源：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `claim_id` | `str` | 自动生成为 `RISK-{counter}` |
| `speaker` | `str` | 人类可读标签（如 "Aggressive Analyst"） |
| `speaker_key` | `str` | 用于路由的短键（如 "Aggressive"） |
| `stance` | `str` | `aggressive`、`conservative` 或 `neutral` |
| `claim` | `str` | 风险断言文本 |
| `evidence` | `list[str]` | 最多 3 项支持证据 |
| `confidence` | `float` | 主张置信度，如无法解析则默认为 0.6 |
| `status` | `str` | `open` → `addressed` → `resolved` / `unresolved` |
| `target_claim_ids` | `list[str]` | 此主张反驳的主张 ID |
| `round_index` | `int` | 产生此主张的辩论轮次 |

`focus_claim_ids` 字段是防止辩论在过多线索中发散的机制。在每个回合之后，载荷可以指定 `next_focus_claim_ids` 来引导下一位发言者的注意力。如果 LLM 未指定焦点主张，系统默认优先处理未解决的主张，然后是剩余的开放主张，上限为两个。

## 轮次目标演进

系统没有任由辩论漫无目的地进行，而是在每个回合注入一个**轮次目标**，用于定义预期的认知目标。当 LLM 未在其载荷中发出 `round_goal` 时，`default_round_goal("risk", round_index)` 会从预设序列中提供一个目标：

| 轮次 | 风险辩论目标 |
| --- | --- |
| 1 | "建立最关键的执行风险 claim，明确风险预算冲突点。" |
| 2 | "围绕仓位、止损、流动性约束，攻击对手最薄弱一环。" |
| 3 | "判断哪些风险是可接受波动，哪些风险是硬性红线。" |
| 4 | "逼迫双方给出可执行替代方案，而不是抽象立场。" |
| 5+ | "检查是否还存在未解决的高影响执行风险，否则准备收口。" |

此演进强制执行了一个自然的漏斗过程：从**主张建立** → **对抗性压力测试** → **风险分类** → **可操作替代方案** → **收口检查**。目标文本被直接注入到提示词的 `round_goal` 占位符中，确保 LLM 在每个阶段都被引导至适当的辩论姿态。

## 风险裁判：裁决协议

在最后一轮之后，**风险裁判**（实现为 `create_risk_manager`）将评估整个辩论历史、所有主张以及交易员的原始计划，以产生一个**机器可读的裁决**。裁判使用 `deep_thinking_llm`（而非辩论者使用的快速思考模型），这反映了此最终决策的更高风险性。

裁判的响应必须包含一个带有 `<!-- RISK_JUDGE: {...} -->` 标签的 JSON 块。`extract_risk_judge_result` 函数会将其解析为结构化结果：

| 裁决 | 含义 | 下游影响 |
| --- | --- | --- |
| `pass` | 计划在风险参数内可接受 | 工作流 → `END` |
| `revise` | 计划需要在约束下进行修改 | 工作流 → 交易员（修订循环） |
| `reject` | 计划存在根本性缺陷 | 工作流 → `END`（记录否决） |

伴随裁决，裁判输出四类结构化约束，这些约束将流入 `RiskFeedbackState`：

- **`hard_constraints`**：不可协商的条件（例如，最大仓位大小，强制止损水平）
- **`soft_constraints`**：建议性推荐（例如，首选的对冲方法）
- **`execution_preconditions`**：交易执行前必须满足的条件（例如，“价格必须保持在支撑位之上”）
- **`de_risk_triggers`**：需要立即减仓的事件（例如，“如果成交量跌破 50 日均线”）

如果缺少 `RISK_JUDGE` 标签或格式错误，系统将默认为 `reject`，并附带消息“风控裁决机读块解析失败，按拒绝处理”。这种故障安全机制确保了无法解析的裁判响应绝不会悄然批准一笔交易。

## 修订循环：自我修正的交易员

当风险裁判发布 `revise` 裁决时，图的条件边会路由回**交易员**节点，而不是终止。这创建了一个修订循环，交易员必须在裁判指定的约束下重新制定其投资计划。

修订循环由 `should_revise_after_risk_judge` 控制，该函数检查两个条件：`risk_feedback_state` 中的 `revision_required` 是否为 `True`，以及 `retry_count` 是否未超过 `max_retries`。默认的 `max_retries` 为 **1**，这意味着交易员在系统终止前恰好有一次修订机会——无论是带着修订后的计划还是被否决。

> **[原图为 mermaid 图；下列为从渲染 SVG 提取的节点/边标签（近拓扑序），非原始 mermaid 源码]**
>
> verdict = pass → verdict = reject → verdict = revise → Yes → No → RiskJudge → END (Plan Approved) → END (Plan Rejected) → retry_count ≤ max_retries? → Trader (Revise Plan) → Aggressive → END (Max Retries Exceeded)

当交易员修订时，它会接收完整的 `risk_feedback_state`，包括 `hard_constraints`、`soft_constraints`、`execution_preconditions`、`de_risk_triggers` 和 `revision_reason`。`summarize_risk_feedback` 工具将其格式化为交易员提示词可以纳入的简洁文本块。修订后，整个风险辩论周期将再次运行——三位辩论者重新审查修订后的计划，裁判发布新的裁决。

`retry_count` 仅在 `revise` 裁决时递增，在 `pass` 或 `reject` 时不递增。这意味着 `reject` 总是立即终止，而 `revise` 是唯一触发重新评估的路径。请谨慎配置 `max_retries`：将其设置为 0 实际上会禁用修订循环，使 `revise` 的行为与 `reject` 相同。

## 状态模式：RiskDebateState 与 RiskFeedbackState

风险辩论的整个生命周期被捕获在两个 TypedDict 模式中，它们作为顶级字段存储在全局 `AgentState` 上。`RiskDebateState` 跟踪对话和主张登记册；`RiskFeedbackState` 在周期之间承载裁判的结构化输出。

**RiskDebateState** 在每个风险辩论周期开始时由 `build_empty_risk_debate_state()` 初始化，并由每个辩论者的 `update_debate_state_with_payload` 调用逐步充实：

| 字段 | 初始值 | 更新者 |
| --- | --- | --- |
| `history` | `""` | 所有辩论者（追加） |
| `aggressive_history` / `conservative_history` / `neutral_history` | `""` | 各自辩论者（追加） |
| `latest_speaker` | `""` | 所有辩论者 |
| `current_aggressive_response` / `conservative` / `neutral` | `""` | 各自辩论者（覆盖） |
| `count` | `0` | 所有辩论者（递增） |
| `claims` | `[]` | 创建新主张的辩论者 |
| `focus_claim_ids` | `[]` | 通过 `next_focus_claim_ids` 的辩论者 |
| `open_claim_ids` / `resolved_claim_ids` / `unresolved_claim_ids` | `[]` | 主张状态转换 |
| `round_summary` / `round_goal` | `""` / 默认目标 | 辩论者载荷或默认值 |

**RiskFeedbackState** 仅由风险裁判填充，并由修订循环消费：

| 字段 | 描述 |
| --- | --- |
| `retry_count` | 在每次 `revise` 裁决时递增 |
| `max_retries` | 修订尝试的上限（默认 1） |
| `revision_required` | 当裁决为 `revise` 时为 `True` |
| `latest_risk_verdict` | `pass`、`revise` 或 `reject` |
| `hard_constraints` | 来自裁判的不可协商条件 |
| `soft_constraints` | 来自裁判的建议性约束 |
| `execution_preconditions` | 执行前必须满足的条件 |
| `de_risk_triggers` | 立即降低风险的事件触发器 |
| `revision_reason` | 修订原因的人类可读解释 |

## 流式集成：实时辩论可视化

每位辩论者和风险裁判都通过 `current_tracker_var` 上下文变量逐 token 流式传输其输出。追踪器在每个 Agent 回合中发出两种类型的事件：

1. **`emit_debate_token`**：为每个 LLM 流式块触发，携带 `debate="risk"`、Agent 名称、轮次数和原始 token。这为前端提供了打字机效果显示。
2. **`emit_debate_message`**：在完整响应组装完成并剥离带标签的 JSON 后触发一次，携带清理后的内容。特别是对于风险裁判，会传递 `is_verdict=True` 以表示此消息代表最终决策。

发送给追踪器的辩论轮次数计算为 `int(count // 3) + 1`，将内部消息计数器映射为人类可读的轮次。裁判使用 `round_num=-1` 表示它不属于任何辩论轮次，而是作为一个元决策存在。

## 图布线：一切如何连接

在 `GraphSetup.setup_graph` 中，风险辩论节点被添加到 `StateGraph` 中并使用条件边连接：

- **交易员 → 激进分析师**：简单边，交易员制定计划后始终采用。
- **激进 → 保守 或 风险裁判**：条件边，基于 `should_continue_risk_analysis`。
- **保守 → 中立 或 风险裁判**：相同条件。
- **中立 → 激进 或 风险裁判**：相同条件，完成循环。
- **风险裁判 → 交易员 或 END**：条件边，基于 `should_revise_after_risk_judge`。

所有三个辩论者节点都使用 `quick_thinking_llm` 以保证响应速度，而风险裁判使用 `deep_thinking_llm` 以确保深思熟虑的质量。`max_risk_discuss_rounds` 参数（默认 1，可配置）控制在调用裁判之前运行多少个完整的“三发言者”周期——对于复杂工具可设置得更高，对于追求速度则设置得更低。
