TradingAgents-AShare 是一个面向 A 股市场的**多 Agent 协作投研系统**，模拟了顶尖研究机构的决策工作流。其核心由 14 个专业化 Agent（分析师、研究员、交易员和风险管理经理）组成，它们执行一条结构化的流水线：并行数据采集、基于论点的多空辩论，以及三方风险审查，最终产出交易决策。整个流水线由 **LangGraph 状态机** 进行编排，控制条件路由、辩论循环和修正周期；同时，可插拔的**供应商注册表**透明地处理数据源，并在多个 A 股数据供应商之间实现自动回退。

## 14 个专业化 Agent

系统的分析能力源于 14 个 Agent 之间的分工，每个 Agent 都有独特的分析视角和工具集。这些 Agent 并非铁板一块——它们在设置阶段根据 `selected_analysts` 配置**动态组合**到图中，使系统能够仅激活特定分析所需的相关维度。

| 团队 | Agent | 角色 | LLM 层级 |
| --- | --- | --- | --- |
| **分析师** | 市场分析师 | 价格行为、技术指标 | Quick |
|  | 社交媒体分析师 | 情绪、社交信号 | Quick |
|  | 新闻分析师 | 新闻事件、内部交易 | Quick |
|  | 基本面分析师 | 财务、资产负债表、现金流 | Quick |
|  | 宏观分析师 | 宏观/行业状况 | Quick |
|  | 聪明钱分析师 | 机构资金流、龙虎榜数据 | Quick |
|  | 量价分析师 | VPA 模式、成交量背离 | Quick |
| **研究** | 看多研究员 | 构建看多论点，反驳看空方 | Quick |
|  | 看空研究员 | 构建看空论点，反驳看多方 | Quick |
|  | 研究经理 | 裁决辩论，形成投资计划 | **Deep** |
| **执行** | 交易员 | 将计划转化为可执行交易 | Quick |
| **风险** | 激进辩手 | 主张激进仓位 | Quick |
|  | 保守辩手 | 主张保守仓位 | Quick |
|  | 中立辩手 | 平衡激进/保守观点 | Quick |
|  | 风险经理 (裁判) | 最终风险裁决，批准/驳回修正 | **Deep** |

系统采用双层 LLM 策略：**Quick Thinking** 模型（例如 gpt-4o-mini）处理高并发的分析和辩论任务，而 **Deep Thinking** 模型（例如 gpt-4o）仅保留给两个裁判角色——研究经理和风险经理——因为这些角色在综合细微差别和做出最终裁决时需要更强的推理能力。

## 编排：LangGraph 状态机

系统的骨干是一个使用 `MemorySaver` 检查点编译器进行状态持久化的 **LangGraph `StateGraph`**。该图在 `GraphSetup.setup_graph()` 中构建，根据选定的分析师名单动态添加节点和边。其拓扑结构遵循**扇出/扇入**模式：所有分析师从 `START` 并行执行，各自拥有独立的工具使用循环，然后扇入汇聚到辩论阶段。

图的条件边由 `ConditionalLogic` 类管理，该类封装了三个不同的路由决策：

| 路由决策 | 方法 | 逻辑 |
| --- | --- | --- |
| 分析师工具使用循环 | `should_continue_{type}()` | 如果最后一条消息包含 `tool_calls`，则路由到工具节点；否则标记为完成 |
| 多空辩论继续 | `should_continue_debate()` | 如果 `count >= 2 × max_debate_rounds`，则路由到研究经理；否则在多头和空头之间交替 |
| 风险辩论继续 | `should_continue_risk_analysis()` | 如果 `count >= 3 × max_risk_discuss_rounds`，则路由到风险裁判；否则在激进 → 保守 → 中立之间循环 |
| 裁判后修正 | `should_revise_after_risk_judge()` | 如果 `revision_required` 且 `retry_count ≤ max_retries`，则路由回交易员；否则结束 |

辩论计数器统计的是**单人发言轮次**，而非回合。多空辩论使用 `2 × max_debate_rounds`（每回合 2 名发言者），而风险辩论使用 `3 × max_risk_discuss_rounds`（每回合 3 名发言者）。这意味着 `max_debate_rounds=2` 会产生 4 个总轮次，而 `max_risk_discuss_rounds=1` 会产生 3 个总轮次。

## 状态传播与 Schema

`AgentState` 是一个扩展了 LangGraph `MessagesState` 的 `TypedDict`——它携带着流经整个图的每一条信息：目标股票代码、交易日期、解析后的用户意图、标的/市场/用户上下文、所有分析师报告、辩论状态、风险反馈以及最终交易决策。状态初始化由 `Propagator.create_initial_state()` 方法处理，它构建完整的状态字典，包括从股票代码推断出的空辩论状态和上下文对象。

状态 Schema 被组织为多个上下文层，为每个 Agent 提供结构化的元数据：

| 上下文 | 目的 | 关键字段 |
| --- | --- | --- |
| `InstrumentContext` | 标准化标的身份 | symbol, security_name, market_country, exchange, currency, asset_type |
| `MarketContext` | 交易时段时间 | trade_date, timezone, market_session, market_is_open, analysis_mode, data_as_of |
| `UserContext` | 用户持仓与约束 | objective, risk_profile, current_position, average_cost, max_loss_pct, constraints |
| `WorkflowContext` | 运行元数据 | context_version, request_source, selected_analysts |
| `InvestDebateState` | 多空辩论追踪 | bull_history, bear_history, claims, focus_claim_ids, count |
| `RiskDebateState` | 风险辩论追踪 | aggressive/conservative/neutral histories, claims, count |
| `RiskFeedbackState` | 交易员修正控制 | retry_count, max_retries, revision_required, hard/soft_constraints |

## 数据层：供应商注册表与缓存

数据访问遵循带有自动回退链的**注册表模式**。`DataProviderRegistry` 持有多个供应商（`CnAkshareProvider`、`CnBaoStockProvider`、`YFinanceProvider`、`AlphaVantageProvider`），每个供应商都实现了通用的 `BaseMarketDataProvider` 接口。当调用 `get_stock_data` 等工具函数时，`route_to_vendor()` 会从 `default_config.py` 解析出配置的供应商链，然后按顺序尝试每个供应商——如果主供应商失败或抛出异常，链中的下一个供应商将被透明地尝试。

`DataCollector` 位于供应商层之上，确保**单次获取，跨 Agent 共享**的语义。当图初始化时，一个共享的 `DataCollector` 实例被传递给所有分析师节点。它预获取给定股票代码+日期组合所需的所有数据并缓存结果，这样 7 个并行分析师在分析同一只股票的不同维度时，就不会重复发起网络调用。

## LLM 集成：多供应商工厂

LLM 客户端的创建通过**工厂模式**进行抽象。`create_llm_client()` 根据配置的 `llm_provider` 分发到特定供应商的客户端实现（`OpenAIClient`、`AnthropicClient`、`GoogleClient`）。值得注意的是，兼容 OpenAI 的客户端还处理 `ollama`、`openrouter` 和 `xai` 供应商，因为它们暴露了兼容 OpenAI 的 API。每个客户端都扩展了 `BaseLLMClient` 并返回兼容 LangChain 的 LLM 实例，确保整个图中的集成统一一致。

系统维护两个 LLM 实例——`deep_thinking_llm` 和 `quick_thinking_llm`——在 `TradingAgentsGraph.__init__()` 期间初始化。特定于供应商的参数（Google 的 `thinking_level`、OpenAI 的 `reasoning_effort`、API 密钥）通过 `_get_provider_kwargs()` 解析，并传递给工厂。

## 记忆与反思

每个辩论参与者（看多方、看空方、交易员、投资裁判、风险裁判）都携带一个 `FinancialSituationMemory` 实例——一个轻量级的**基于 BM25 的检索系统**，存储过去的（情境，建议）对。在每个分析周期之后，`Reflector` 从当前 Agent 报告中提取市场情境，将其与 Agent 的辩论/决策输出结合，并要求快速思考 LLM 生成反思教训。这个教训被存储回记忆中，以供未来检索。

每个 Agent 的反思流程为：提取当前市场情境 → 与 Agent 的决策输出配对 → 调用 LLM 进行反思 → 将（情境，反思）存入 BM25 索引。在后续的分析中，Agent 查询其记忆以寻找相似的过去情境，并将检索到的教训纳入其推理中。
