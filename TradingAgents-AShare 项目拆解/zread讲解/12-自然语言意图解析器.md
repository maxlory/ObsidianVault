自然语言意图解析器是系统的认知网关——它将“满仓被套了，成本价1850，想止损，保守型”这类自由格式的用户查询，转化为结构化的意图字典，供每个下游 Agent 进行推理。如果没有这一层，14 个专业 Agent 将无法对用户*真正*想要什么建立共识，导致分析趋于泛化而非个性化。该解析器采用**双轨策略**：以 LLM 驱动的主路径获取丰富的语义，以及基于正则表达式的回退路径，在 LLM 失败或返回无法解析的输出时提供确定性的容错能力。

## 架构：双轨解析流水线

意图解析器位于面向用户的 API 与 LangGraph 状态机之间。当 `propagate_async` 接收到自然语言查询时，它会使用 `quick_thinking_llm` 调用 `parse_intent`——这是一种刻意的设计，旨在最小化此预处理步骤的延迟，将 `deep_thinking_llm` 留给下游实质性的分析工作。解析后的意图随后流入 `Propagator.create_initial_state`，成为图中每个节点都会读取的 `AgentState` 的一部分。

>
> Yes → No → User Query(Natural Language) → parse_intent() → LLM Primary Path → Regex Fallback Path(_extract_user_context_fallback) → System Prompt(intent_parser_system) → LLM Invocation(quick_thinking_llm) → JSON Extraction+ Markdown Fence Cleanup → JSON Valid? → Merge LLM + Fallback(_merge_inferred_user_context) → Fallback Dict(defaults + regex context) → Regex Pattern Matching(objective, risk, horizon,position, cash, constraints) → Structured Intent Dict → Propagator.create_initial_state → AgentState.user_intent → AgentState.user_context(normalized) → build_horizon_context() → Agent System Prompts(horizon context block)

关键的架构洞察在于，两条轨道在概念上是并行运行的——正则表达式回退在 LLM 调用*之前*提取上下文，而合并步骤确保关键数字字段（如 `cash_available`、`current_position_pct`）的确定性正则匹配，始终优先于可能产生幻觉的 LLM 值。这使得系统能够抵御 LLM 对可量化数据的捏造。

## 结构化意图输出

`parse_intent` 函数返回一个包含六个键的字典。每个键服务于特定的下游目的——`ticker` 驱动数据收集，`focus_areas` 和 `specific_questions` 塑造分析师的侧重点，而 `user_context` 则为风险管理及交易决策提供个性化依据。

| 字段 | 类型 | 用途 | 失败时的默认值 |
| --- | --- | --- | --- |
| `raw_query` | `str` | 保留原始输入以便追溯 | 原始查询字符串 |
| `ticker` | `str` | 用于数据获取的 A 股 6 位代码（如 "600519"） | `fallback_ticker` 或 `""` |
| `horizons` | `List[str]` | 分析的时间维度 | `["short"]`（固定——每位分析师使用其固有的时间窗口） |
| `focus_areas` | `List[str]` | 用户指定的分析维度（如 "量价关系"、"主力资金"） | `[]` |
| `specific_questions` | `List[str]` | 用户希望得到解答的具体问题 | `[]` |
| `user_context` | `Dict[str, Any]` | 账户画像、风险偏好、持仓信息 | 回退正则提取的上下文或 `{}` |

无论 LLM 返回什么，`horizons` 字段**始终**为 `["short"]`。这是有意为之的设计：7 位分析师内部各自使用其固有的时间窗口——技术面/资金流分析师关注 1-2 周，而基本面/宏观分析师自然会延伸至 1-3 个月。时间维度标签并非图级别的分支机制，而是每个 Agent 的上下文信号。

## LLM 主路径：提示词驱动的提取

LLM 路径使用 `intent_parser_system` 提示词——一个注册在双语提示词目录（`zh.py` / `en.py`）中的专用系统提示词。该提示词指示 LLM 扮演“交易意图解析器”的角色，且*仅*输出 JSON，不包含任何前缀或后缀文本。它定义了五个可提取字段及包含 10 个可能键的 `user_context` 子对象的模式。

该提示词对标的代码解析有严格的设定：指示 LLM 将公司名称（比亚迪→002594）、英文名称（BYD→002594）及港股/美股代码转换为对应的 A 股代码。这使得解析器能够适应中国投资者引用股票的多种方式。LLM 响应后，解析器在执行 `json.loads` 之前会应用三个清理步骤：剥离 Markdown 代码围栏（`json` / ``）、移除闭合括号前的尾随逗号，以及妥善处理空内容。

## 正则回退路径：确定性上下文提取

当 LLM 产生无法解析的输出时，或者系统需要交叉验证 LLM 提取的数值时，正则回退路径（`_extract_user_context_fallback`）提供了跨六个语义类别的确定性提取。此路径在 LLM 调用*之前*被调用，其结果在调用*之后*进行合并，从而确保可量化字段的正则匹配具有优先权。

### 提取类别与模式

| 类别 | 正则策略 | 输入 → 输出示例 |
| --- | --- | --- |
| **目标** | 6 种动宾模式（想/准备/打算 + 建仓/加仓/减仓/止损） | "想加仓" → `objective: "加仓"` |
| **风险偏好** | 针对 5 个术语的关键词匹配 | "稳健型投资者" → `risk_profile: "保守"` |
| **投资期限** | 针对 6 个术语的关键词匹配 | "做波段" → `investment_horizon: "波段"` |
| **持仓水平** | 关键词到百分比的映射 | "半仓" → `current_position_pct: 50.0` |
| **可用资金** | 带有 万/亿 单位解析的正则表达式 | "可用资金50万" → `cash_available: "50万"` |
| **数字字段** | 针对各字段的定向正则（average_cost, max_loss_pct, current_position, current_position_pct） | "成本价1850" → `average_cost: "1850"` |
| **约束条件** | 7 个关键词约束（不加杠杆, 不追高, 等） | "不加杠杆，不追高" → `constraints: ["不加杠杆", "不追高"]` |

目标模式采用复合结构——动词组 `(想|准备|打算|计划|考虑)` 搭配动作关键词——使其足够灵活，能够捕捉诸如 "准备止损"、"考虑减仓" 或 "打算建仓" 等自然措辞的变体。针对 "继续拿着"、"被套" 和 "先观察" 的特殊模式，则处理了中国散户投资者中常见的口语化表达。

## 上下文合并策略：优先级解析

`_merge_inferred_user_context` 函数使用特定字段的优先级方案，解决 LLM 提取和正则提取上下文之间的冲突。这一点至关重要，因为 LLM 可能会捏造数值——如果用户说 "成本价1850"，而 LLM 猜测 "average_cost": 1900，此时正则匹配必须胜出。

**按字段类型的优先级规则：**

- **硬覆盖字段**（`cash_available`、`current_position`、`current_position_pct`、`average_cost`、`max_loss_pct`）：正则值*始终*覆盖 LLM 值。这些属于可量化的事实，确定性提取比 LLM 推理更为可靠。
- **约束条件**：加法合并——仅当正则约束不存在于 LLM 的约束列表中时才将其追加，在保留正则词典未涵盖的 LLM 检测到的约束的同时防止重复。
- **所有其他字段**（`objective`、`risk_profile`、`investment_horizon`、`user_notes`）：优先使用 LLM 值；仅当 LLM 生成 `None`、空字符串或空列表时，才由正则填充。

合并后，组合上下文会通过 `normalize_user_context`（来自 `context_utils.py`），将带有中文单位标记的数字字符串进行强制类型转换（"50万" → 500000.0，"3亿" → 300000000.0），剥离格式化字符，并根据规范的 `USER_CONTEXT_KEYS` 元组进行验证。

## 时间维度上下文块：从意图到 Agent 提示词的桥梁

意图一旦解析完成，`build_horizon_context` 函数便会将结构化的 `focus_areas` 和 `specific_questions` 转换为格式化的文本块，前置到每位分析师的系统提示词中。这就是单个用户查询（如 "关注主力资金流向，能否突破前高"）转化为 7 位分析师各自的上下文指引的方式。

该函数使用 `horizon_context_block` 提示词模板，其中包含四个占位符：

| 占位符 | 来源 | 示例值 |
| --- | --- | --- |
| `{horizon_label}` | `_HORIZON_LABELS` 映射 | "短线（1-2周，技术面主导）" |
| `{focus_areas_str}` | `focus_areas` 以中文逗号连接 | "量价关系、主力资金" |
| `{specific_questions_str}` | `specific_questions` 以中文分号连接 | "短期能否到+30%目标位" |
| `{weight_hint}` | 当前为空字符串（为未来的权重设置预留） | — |

时间维度标签映射目前定义了两个维度——`"short"` 映射为 "短线（1-2周，技术面主导）"，`"medium"` 映射为 "中线（1-3月，基本面主导）"——锚定了每位分析师的时间参考框架。当 `focus_areas` 为空时，该模块渲染为 "无特殊关注"；当 `specific_questions` 为空时，渲染为 "无"，确保模板始终生成格式良好的输出。

`weight_hint` 参数目前为空字符串，但为未来的动态权重预留——例如，当基本面分析师在 "短线" 维度下运作时，可以注入诸如 "基本面在此维度为次要参考" 的降权提示，以防止在短期决策中过度依赖长期信号。

## 优雅降级：失败模式

整个 `parse_intent` 函数被包裹在 try/except 块中，以捕获*任何*异常——JSON 解析错误、LLM API 故障、意外响应结构上的属性错误——并返回一个最小但有效的意图字典。回退字典使用 `fallback_ticker`（通常为 API 路由已知的标的代码），将 horizons 默认设为 `["short"]`，并仅包含正则提取的 `user_context`。

这种设计哲学——**始终生成有效意图，绝不导致流水线崩溃**——意味着系统能够优雅降级：即使没有 LLM 驱动的语义理解，正则回退依然可以从结构良好的中文查询中提取持仓信息、风险偏好和交易目标。7 位分析师仍将运行其完整分析；只是无法享受个性化关注领域或具体问题带来的益处。

测试套件明确验证了此行为：`test_parse_intent_fallback_on_invalid_json` 确认当 LLM 返回非 JSON 内容时，回退标的代码得到保留，且默认结构得以维持。

## 端到端数据流：从查询到 Agent 状态

解析意图的完整生命周期如下：

1. **API 接收查询**——例如，`"满仓被套，成本1850，保守型，想止损，不追高"`
2. **`propagate_async` 调用 `parse_intent`**，传入 `quick_thinking_llm` 及路由已知的标的代码作为 `fallback_ticker` [trading_graph.py](https://github.com/KylinMountain/TradingAgents-AShare/blob/main/tradingagents/graph/trading_graph.py#L314-L316)
3. **正则回退立即提取**：`objective: "止损"`、`risk_profile: "保守"`、`current_position_pct: 100.0`、`average_cost: "1850"`、`constraints: ["不追高"]`
4. **LLM 将完整查询解析**为 JSON 对象，可能提取出正则无法捕获的额外 `focus_areas` 或 `specific_questions`
5. **合并解决冲突**——正则在 `current_position_pct`、`average_cost` 上胜出；LLM 在 `focus_areas`、`specific_questions` 上胜出
6. **`normalize_user_context` 强制类型转换**——`"1850"` 变为 `1850.0`，`"不追高"` 保持为约束字符串
7. **`Propagator.create_initial_state`** 将意图写入 `AgentState.user_intent`，将标准化上下文写入 `AgentState.user_context` [propagation.py](https://github.com/KylinMountain/TradingAgents-AShare/blob/main/tradingagents/graph/propagation.py#L109-L111)
8. **`build_horizon_context`** 生成每位分析师读取的视角块，以个性化其分析范围
9. **`summarize_user_context`** 渲染人类可读的文本块，注入到交易员和风险管理者的提示词中，为其提供具体的持仓/风险数据以供推理 [context_utils.py](https://github.com/KylinMountain/TradingAgents-AShare/blob/main/tradingagents/agents/utils/context_utils.py#L190-L210)

> AgentState → Propagator → normalize_user_context → _merge_inferred_user_context → _extract_user_context_fallback → quick_thinking_llm → parse_intent → TradingAgentsGraph → REST API → propagate_async(query, ticker, trade_date) → parse_intent(query, quick_llm, fallback_ticker) → _extract_user_context_fallback(query) → fallback_context → invoke([SystemMessage, HumanMessage]) → raw JSON string → Strip fences + cleanup JSON → _merge_inferred_user_context(parsed, fallback) → normalize_user_context(merged) → normalized dict → final user_context → intent dict → create_initial_state(ticker, date, user_intent) → state["user_intent"] = intent → state["user_context"] = normalized

## 接下来

意图解析器是数据到决策流水线的首个节点。一旦结构化意图进入 `AgentState`，它便会传播至随后的每个阶段——从使用 `build_horizon_context` 聚焦分析的 7 个并行分析师，到 `user_context` 为研究经理加权提供信息的牛熊辩论，直至最终根据用户的 `max_loss_pct` 检查持仓约束的风险评判官。要了解解析后的意图如何流经完整的 Agent 工作流，请继续阅读 [LangGraph 状态机 ](https://zread.ai/KylinMountain/TradingAgents-AShare/4-langgraph-state-machine)和 [Agent 状态模式 ](https://zread.ai/KylinMountain/TradingAgents-AShare/6-agent-state-schema)。有关 `ticker` 字段激活的数据层，请参阅[数据收集器与缓存 ](https://zread.ai/KylinMountain/TradingAgents-AShare/10-data-collector-and-caching)。
