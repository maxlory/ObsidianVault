记忆与反思系统赋予了 TradingAgents 经验学习能力——这是一种闭环机制，将过往决策与实际结果进行对比评估，提炼出可复用的经验教训，并注入到未来的 Agent 推理中。若没有该系统，每一次分析周期都将从零开始；而有了它，Agent 能够积累随时间复利的机构知识，从而减少重复犯错，并在可识别的市场环境下 sharpening edge。

## 架构概述

该系统横跨两个时间阶段运行，形成一个自我改进的闭环：**读取时检索**（将过往经验注入到实时 Agent 提示词中）与**写入时反思**（根据已实现收益对已完成的决策进行评估）。这两个阶段通过 `FinancialSituationMemory` 进行桥接，这是一个基于 BM25 的联想记忆存储，负责将市场情况映射到已习得的建议；同时由 `Reflector` 进行编排，驱动所有五个特定 Agent 记忆实例的交易后反思。

## 记忆存储：FinancialSituationMemory

每个 Agent 都拥有其专属的 `FinancialSituationMemory` 实例——一个隔离的、命名空间作用域的联想存储，它使用 **BM25 (Best Matching 25)** 进行词汇相似度检索。该设计刻意保持轻量化：无需外部向量数据库、无需调用嵌入 API、不受 token 数量限制，且与任何 LLM 提供商完全离线兼容。

### 内部结构

该记忆存储维护了两个平行列表——**documents**（市场情况描述）和 **recommendations**（由 LLM 生成的反思经验），二者保持严格的位置对应关系。每次写入时都会重建 BM25Okapi 索引，确保检索索引与存储的数据始终保持一致。

| 组件 | 类型 | 用途 |
| --- | --- | --- |
| `documents` | `List[str]` | 情况描述（拼接的分析师报告） |
| `recommendations` | `List[str]` | 由 LLM 生成的反思经验 |
| `bm25` | `BM25Okapi \| None` | 延迟重建的 token 化文档检索索引 |

来源: [memory.py](https://github.com/KylinMountain/TradingAgents-AShare/blob/main/tradingagents/agents/utils/memory.py#L12-L26)

### Tokenization 与索引策略

分词器使用简单有效的正则表达式 `r'\b\w+\b'` 并转换为小写——在单词边界处拆分并去除标点符号。这一选择意义重大：它避免了对特定提供商分词器的依赖，消除了对外部 NLP 库的依赖，并在中英文文本上产生一致的结果。每次调用 `add_situations` 后，都会通过 `_rebuild_index()` 延迟重建索引，该函数会对完整的文档语料库重新进行 token 化，并构建一个新的 `BM25Okapi` 实例。

```python
def _tokenize(self, text: str) -> List[str]:
    tokens = re.findall(r'\b\w+\b', text.lower())
    return tokens
```

BM25 的词频饱和度与文档长度归一化特性，使其在金融文本检索中具备内在的鲁棒性——它能够避免对重复的市场行话（如 "bullish"、"bearish"）过度加权，同时仍能检索出与情境相关的匹配。与基于嵌入的余弦相似度不同，BM25 无需任何 API 调用，且排名具有确定性和可复现性。

来源: [memory.py](https://github.com/KylinMountain/TradingAgents-AShare/blob/main/tradingagents/agents/utils/memory.py#L27-L55)

### 检索：get_memories

当 Agent 需要过往经验时，`get_memories(current_situation, n_matches=1)` 会对查询进行 token 化，使用 BM25 对所有存储的文档进行评分，将分数归一化至 0–1 范围，并将前 N 个匹配项作为结构化的字典返回：

```python
{
    "matched_situation": "...",    # 存储的情况文本
    "recommendation": "...",       # 反思经验
    "similarity_score": 0.85       # 归一化的 BM25 分数
}
```

分数归一化将每个原始 BM25 分数除以结果集中的最大分数（若所有分数为零则除以 1），从而生成一个相对相关性排名，无论语料库规模大小，该排名都具有良好的可解释性。

## 读取阶段：将记忆注入 Agent 提示词

在实时分析期间，每个具备记忆功能的 Agent 都会通过拼接四份核心分析师报告（市场、情绪、新闻、基本面）来构建**当前情境指纹**，然后使用 `n_matches=2` 查询其专属记忆。排名前 2 的过往建议将被拼接成 `past_memory_str`，并通过 `{past_memory_str}` 占位符注入到 Agent 的提示词模板中。

这五个 Agent 的指纹构建方式略有不同——它捕获的是客观的市场状况，而非 Agent 的主观输出：

## 写入阶段：Reflector

`Reflector` 类负责编排交易后反思——这是一种评估已完成决策并将其提交至记忆的机制。它使用 `quick_thinking_llm`（成本高效的反思无需深度推理）和反思系统提示词进行初始化。

### 反思提示词架构

反思系统提示词指导 LLM 扮演审阅过往决策的资深金融分析师。双语提示词定义了预期的输出结构：

| 语言 | 提示词键 | 核心要求 |
| --- | --- | --- |
| 英文 | `reflection_system_prompt` | 解释对错、原因及改进方法；以简明的可复用经验结尾 |
| 中文 | `reflection_system_prompt` | 判断成败与客观依据 → 拆解成因 → 指出可改进项 → 输出可执行修正动作 → 可复用经验清单 |

中文反思提示词明确要求“可执行的修正动作”而非空洞的口号——这防止了记忆中积累诸如“更加小心”之类的无用建议，转而存储具体、可迁移的规则，例如“当 RSI 出现背离但无量能确认时，在信号确认前减仓。”

### 反思调用流程

每个 `reflect_*` 方法都遵循相同的三步模式：

1. **提取情境** — `_extract_current_situation()` 从已完成状态中拼接四份核心分析师报告
2. **生成反思** — `_reflect_on_component()` 使用反思提示词调用 LLM，传入收益/亏损、Agent 的输出以及客观市场报告
3. **提交至记忆** — 反思结果通过 `memory.add_situations([(situation, result)])` 进行存储

```python
def reflect_bull_researcher(self, current_state, returns_losses, bull_memory):
    situation = self._extract_current_situation(current_state)
    bull_debate_history = current_state["investment_debate_state"]["bull_history"]
    result = self._reflect_on_component("BULL", bull_debate_history, situation, returns_losses)
    bull_memory.add_situations([(situation, result)])
```

LLM 接收一条结构化的人类消息：`Returns: {returns_losses}\n\nAnalysis/Decision: {report}\n\nObjective Market Reports for Reference: {situation}`——确保反思既基于结果数据，也基于决策时盛行的客观市场状况。

### 编排反思：reflect_and_remember

`TradingAgentsGraph.reflect_and_remember(returns_losses)` 方法是同时触发所有五个 Agent 交易后反思的唯一入口。它读取最近完成的状态（`self.curr_state`，在 `propagate()` 或 `propagate_async()` 结束时设置），并将反思分发给每个记忆：

```python
def reflect_and_remember(self, returns_losses):
    self.reflector.reflect_bull_researcher(self.curr_state, returns_losses, self.bull_memory)
    self.reflector.reflect_bear_researcher(self.curr_state, returns_losses, self.bear_memory)
    self.reflector.reflect_trader(self.curr_state, returns_losses, self.trader_memory)
    self.reflector.reflect_invest_judge(self.curr_state, returns_losses, self.invest_judge_memory)
    self.reflector.reflect_risk_manager(self.curr_state, returns_losses, self.risk_manager_memory)
```

此设计意味着反思周期是**外部驱动**的——调用方负责在市场结果已知后提供已实现的 `returns_losses`。图本身不会自动触发反思；这是一种独立的、刻意为之的调用，将分析与评估解耦。

## 设计权衡与考量

### 为什么选择 BM25 而非基于嵌入的检索

| 维度 | BM25 (当前方案) | 基于嵌入 (替代方案) |
| --- | --- | --- |
| **API 依赖** | 无 — 完全离线 | 需要嵌入模型端点 |
| **延迟** | 亚毫秒级 | 网络往返 + 模型推理 |
| **成本** | 每次查询零成本 | 每次嵌入调用的 Token/使用量成本 |
| **提供商锁定** | 无 | 嵌入模型的选择会影响一致性 |
| **跨语言** | 有限（词汇重叠） | 强大（语义空间） |
| **语料库扩展** | 超过约 10 万文档后会下降 | 可扩展至数百万 |
| **确定性** | 完全确定 | 依赖模型，对温度敏感 |

选择 BM25 是针对系统运行机制的一种刻意优化：每个 Agent 的语料库相对较小（每个 Agent 每笔被反思的交易积累一条记忆），在检索期间对外部 API 故障零容忍，并且需要在多次运行中具备可复现的、确定性的行为。

### 记忆隔离 vs. 共享记忆

五实例架构避免了**交叉污染**——这是一种常见的失效模式，即风险厌恶型经验（例如，“亏损 5% 止损”）不当限制了看多研究员的上行情况构建。每个 Agent 的记忆仅反映与其特定决策角色相关的经验，从而保留了驱动高质量辩论的对抗性张力。

### 索引重建成本

`_rebuild_index()` 在每次 `add_situations` 调用时都会对整个语料库重新进行 token 化和索引。对于预期的语料库规模（每个 Agent 几十到几百条目），这种开销微乎其微。如果语料库规模增长到数千条，则需要采用增量索引更新策略。

### 记忆持久化

当前实现仅将记忆存储在内存中——它们在单个 `TradingAgentsGraph` 实例内的多次 `propagate()` / `reflect_and_remember()` 循环中得以存活，但在进程重启时会丢失。对于需要跨会话记忆持久化的生产部署，`FinancialSituationMemory` 类将需要一个序列化层（例如，JSON 或 SQLite 支撑），构造函数中的 `config` 参数已为此预留了空间。

## 与更广泛系统的集成

记忆与反思系统与架构中的其他几个子系统存在交集：

- **[LangGraph 状态机 ](https://zread.ai/KylinMountain/TradingAgents-AShare/4-langgraph-state-machine)**：输入反思的 `curr_state` 是图执行产生的最终状态。记忆实例在图构建期间通过 `GraphSetup` 注入到 Agent 节点中。

- **[多提供商 LLM 工厂 ](https://zread.ai/KylinMountain/TradingAgents-AShare/13-multi-provider-llm-factory)**：反思使用 `quick_thinking_llm` 以最小化成本，而实时分析期间的记忆注入则使用 Agent 配置的任何 LLM。
