TradingAgents-AShare 采用了**双模型思维架构**，其中两个不同的 LLM 实例——*深度思考*和*快速思考*——根据其认知角色被连接到不同的 Agent 上。研究经理和风险经理接收深度思考模型，用于复杂的综合分析与判断；而所有分析师、辩论员、研究员和交易员则使用快速思考模型，进行响应式的迭代推理。特定于提供商的参数（推理努力程度、思考级别、思考预算）在实例化时被透明注入，确保每个提供商原生的“思考模式”API 都能被充分利用，同时不污染 Agent 逻辑。

## 双模型原则

系统的核心配置声明了两个模型槽：`deep_think_llm` 和 `quick_think_llm`，两者默认指向同一提供商，但针对不同的模型层级。深度槽通常指向高能力模型（例如 `gpt-4o`、`claude-sonnet-4-5`），用于需要细致判断的任务；而快速槽则指向更快、更便宜的模型（例如 `gpt-4o-mini`、`claude-3-5-haiku`），用于高频迭代调用。环境变量 `TA_LLM_DEEP` 和 `TA_LLM_QUICK` 会在部署时覆盖这些设置，并且这两个模型共享相同的 `llm_provider` 和 `backend_url`，这意味着你无法在单次运行中跨越深度/快速边界混合使用不同的提供商。

```python
"llm_provider": os.getenv("TA_LLM_PROVIDER", "openai"),
"deep_think_llm": os.getenv("TA_LLM_DEEP", "gpt-4o"),
"quick_think_llm": os.getenv("TA_LLM_QUICK", "gpt-4o-mini"),
"backend_url": os.getenv("TA_BASE_URL", "https://api.openai.com/v1"),
```

来源：[default_config.py](https://github.com/KylinMountain/TradingAgents-AShare/blob/main/tradingagents/default_config.py#L8-L14)

## 特定于提供商的思考配置

每个 LLM 提供商都暴露了不同的 API 接口来控制“模型思考多少”。系统将其标准化为两个配置键，并在客户端构建期间作为 kwargs 注入：

```python
"google_thinking_level": None,      "openai_reasoning_effort": None,    # "medium", "high", "low"
```

`TradingAgentsGraph` 中的 `_get_provider_kwargs()` 方法会读取这些键，并仅为当前活跃的提供商注入相关参数——Google 注入 `thinking_level`，OpenAI 注入 `reasoning_effort`，所有提供商均注入 `api_key`。随后，此 kwargs 字典会被展开传入两个 `create_llm_client` 调用中，确保深度和快速实例都能接收到相同的提供商特定调优。

| 提供商 | 配置键 | 注入参数 | 效果 |
| --- | --- | --- | --- |
| OpenAI | `openai_reasoning_effort` | `reasoning_effort` | 控制 o 系列推理深度（`low`/`medium`/`high`） |
| Google (Gemini 3) | `google_thinking_level` | `thinking_level` | 控制思考深度（`minimal`/`low`/`medium`/`high`） |
| Google (Gemini 2.5) | `google_thinking_level` | `thinking_budget` | 将 `high` 映射为 `-1`（动态），其余映射为 `0`（禁用） |
| Anthropic | — | — | 扩展思考通过内容归一化处理 |

## Google 思考级别映射

`GoogleClient` 实现了一种感知模型的映射，将统一的 `thinking_level` 配置转换为特定于提供商的参数，因为 Gemini 3 和 Gemini 2.5 使用了完全不同的思考控制 API：

> **[原图为 mermaid 图；下列为从渲染 SVG 提取的节点/边标签（近拓扑序），非原始 mermaid 源码]**
>
> Yes → No → Yes + minimal → 'high' → other → thinking_level config → Model contains 'gemini-3'? → Gemini 3 Path → Gemini 2.5 Path → Is Pro model? → Remap 'minimal' → 'low' → Pass thinking_level as-is → thinking_level param → thinking_level value? → thinking_budget = -1 → thinking_budget = 0 → thinking_budget param

Gemini 3 Pro 不支持将 `"minimal"` 作为思考级别，因此它会自动被重新映射为 `"low"`。Gemini 2.5 模型使用数字化的 `thinking_budget`，其中 `-1` 启用动态思考，`0` 则禁用思考。

## 推理模型检测与参数剥离

兼容 OpenAI 的推理模型（o1、o3、GPT-5、DeepSeek-R1 等）会拒绝诸如 `temperature` 和 `top_p` 等标准采样参数。`UnifiedChatOpenAI` 类在构造时会检测这些模型，并在将不兼容的参数传递给 LangChain 的 `ChatOpenAI` 构造函数之前将其剥离：

```python
@staticmethod
def _is_reasoning_model(model: str) -> bool:
    model_lower = str(model).lower()
    return (
        model_lower.startswith("o1")
        or model_lower.startswith("o3")
        or "gpt-5" in model_lower
        or "-r1" in model_lower
        or "thinking" in model_lower
        or "reasoning" in model_lower
    )
```

此检测会触发两种行为：(1) 从 kwargs 中移除 `temperature` 和 `top_p`；(2) `OpenAIClient.get_llm()` 方法跳过设置默认的 `temperature=0`。此外，Moonshot（Kimi）模型会被检测到并强制设定为 `temperature=1`，因为其 API 严格要求如此。

当使用 o 系列或 R1 推理模型作为 `deep_think_llm` 时，`reasoning_effort` 参数（例如 `"high"`）会通过 `OpenAIClient.get_llm()` 中的 kwargs 透传进行转发——这是控制推理深度的正确方式，而不是使用会被自动剥离的 temperature。

## Anthropic 扩展思考归一化

当 Anthropic Claude 模型在扩展思考模式下运行时，响应的 `content` 字段会变成结构化块列表，而非纯字符串：

```python
[{"type": "thinking", "thinking": "..."}, {"type": "text", "text": "..."}]
```

`NormalizedChatAnthropic` 包装器会拦截每个调用路径（`invoke`、`ainvoke`、`stream`、`astream`），并仅提取 `text` 块，将其拼接为单个字符串。这确保了期望获取 `str` 类型内容的下游 Agent 永远不会遇到原始的结构化格式。`_extract_text_from_content` 辅助函数能够优雅地处理所有内容形态——字符串、字典列表或混合类型列表。

## 稳定性与超时配置

`OpenAIClient` 针对推理模型配置了最大的稳定性：**禁用重试**（`max_retries=0`），以防止可能在中途计算超时的思考模型产生重复计费；**超时默认为 300 秒**，为推理模型提供充足的时间。这些设置同时应用于深度实例和快速实例：

```python
llm_kwargs["max_retries"] = 0
llm_kwargs["timeout"] = self.kwargs.get("timeout", 300.0)
```

初始化时会打印一条诊断信息，确认提供商、模型、目标 URL、重试状态和超时时间——这对于调试生产部署至关重要，因为静默重试可能会导致重复的 API 费用。

## 配置回退链与交叉借用

API 层针对 LLM 模型名称实现了三级回退，并由测试套件进行了验证：

| 优先级 | 来源 | 行为 |
| --- | --- | --- |
| 1（最高） | 用户配置（非空） | 直接覆盖模型名称 |
| 2 | 环境变量 | `TA_LLM_DEEP` / `TA_LLM_QUICK` |
| 3（最低） | `DEFAULT_CONFIG` | `gpt-4o` / `gpt-4o-mini` |

**来自用户配置的空字符串不会覆盖低优先级的值**——这防止了数据库中存储的空字符串抹除有效的环境变量默认值。此外，当某个槽位的用户配置和环境变量均缺失时，会触发一种**智能交叉借用**机制：系统会借用另一个槽位中的有效模型名称，确保图始终拥有两个功能完备的 LLM 实例。

通过 Web UI 设置页配置 LLM 模型时，将模型字段清空不会破坏你的部署——回退链保留了环境变量的默认值。但是，如果你只在环境中设置了一个模型，深度槽和快速槽将通过交叉借用同时使用该模型，这会使该模型的 API 支出翻倍。

## 提供商路由摘要

工厂函数 `create_llm_client` 根据 `provider` 字符串路由到相应的客户端类。多个提供商共享 `OpenAIClient`，因为它们实现了兼容 OpenAI 的 API：

| 提供商字符串 | 客户端类 | Base URL | API 密钥来源 |
| --- | --- | --- | --- |
| `openai` | `OpenAIClient` | `https://api.openai.com/v1` | `TA_API_KEY` / kwargs |
| `ollama` | `OpenAIClient` | `http://localhost:11434/v1` | 硬编码的 `"ollama"` |
| `openrouter` | `OpenAIClient` | `https://openrouter.ai/api/v1` | `OPENROUTER_API_KEY` |
| `xai` | `OpenAIClient` | `https://api.x.ai/v1` | `XAI_API_KEY` |
| `anthropic` | `AnthropicClient` | 自动剥离 `/v1` 后缀 | `TA_API_KEY` / kwargs |
| `google` | `GoogleClient` | 提供商默认值 | `TA_API_KEY` / kwargs |

Anthropic 客户端会自动剥离 `base_url` 末尾的 `/v1`，因为 `ChatAnthropic` 会在内部追加它，从而避免了出现 `https://host/v1/v1/messages` 这样的双重路径错误。

## 提供商追踪日志

`provider_trace` 配置键（由 `TA_TRACE` 环境变量控制，默认为 `"1"`）可启用诊断日志记录，记录由哪个 LLM 提供商和模型处理了每个请求。这在多提供商部署中至关重要，因为路由错误可能是静默的——当设置为 `true` 时，系统会记录提供商路由决策，用于事后调试，而不会影响 Agent 工作流。
