**DataCollector** 是一个集中式的数据获取与缓存引擎，位于原始市场数据提供商与 7 个专业分析师 Agent 的交汇处。其核心设计原则看似简单：**一次获取所有数据，向每个 Agent 提供窗口化视图**。当多个分析师在同一交易日需要同一只股票的 OHLCV 数据、基本面或新闻时，这消除了冗余的 API 调用——当每次分析运行涉及 7 个并发 Agent 且横跨 13 个以上数据源时，这是一项关键的优化。

## 架构：一次获取，多次服务

DataCollector 遵循**一次写入 / 多次读取**模式。当 `propagate_async` 开始一次分析运行时，它会在 LangGraph 执行之前调用 `data_collector.collect(ticker, trade_date)`。随后，每个分析师节点通过 `data_collector.get()` 从同一个内存缓存中读取数据，仅选择与其领域和时间范围相关的切片。在图完成执行后，`data_collector.evict()` 会递减引用计数，并在没有任何 Agent 持有引用时释放内存。

`collect` 和 `get_window` 之间的分离是有意为之的。无论时间范围如何，`collect` 始终获取**完整的 365 天历史回溯数据**——因为像 200 日简单移动平均线 (200-SMA) 这样的指标计算需要深层历史数据才能保证准确性。时间范围仅影响分析师用于构建其解读的**分析窗口**元数据（`_data_window` = "14天" 或 "90天"），而不影响原始数据本身。

## 基于引用计数的线程安全缓存

`DataCollector` 类实现了一种**逐键条带化锁**策略，在确保线程安全的同时避免了全局竞争。每个缓存键（`{ticker}_{trade_date}`）都拥有自己的 `threading.Lock`，该锁在元锁下延迟分配。对相同标的和日期的并发调用将阻塞在该键的锁上，从而保证只执行一次获取操作。对不同标的的调用则互不干扰地并行执行。

```
┌─────────────────────────────────────────────────────┐
│                  DataCollector                       │
├─────────────────────────────────────────────────────┤
│  _cache: Dict[str, Dict[str, Any]]                  │
│    "600519_2026-03-12" → {stock_data, indicators…}  │
│    "000858_2026-03-12" → {stock_data, indicators…}  │
│                                                      │
│  _locks: Dict[str, threading.Lock]   ← per-key     │
│    "600519_2026-03-12" → Lock()                     │
│                                                      │
│  _refcounts: Dict[str, int]          ← eviction     │
│    "600519_2026-03-12" → 1                          │
│                                                      │
│  _meta_lock: threading.Lock          ← guards       │
│                                      _locks map      │
└─────────────────────────────────────────────────────┘
```

缓存条目的生命周期遵循**引用计数模式**：`collect()` 填充缓存，`ref()` 在 Agent 读取前递增计数，而 `evict()` 则递减计数。当计数归零时，条目将被清除。锁对象被刻意保留而从不删除——其他线程可能仍持有其引用，在锁被获取期间销毁它将破坏互斥性。锁对象非常轻量，这种内存权衡是微不足道的。

## 本地指标计算：避免冗余 API 调用

`data_collector.py` 第 298-346 行中包含了一项重大的架构决策：**技术指标是通过已获取的 OHLCV CSV 在本地计算的**，而不是通过对提供商的单独 API 调用获取。原始 CSV 被一次性解析为 Pandas DataFrame，随后用 `stockstats` 封装并在单次遍历中计算出全部 10 项指标：

| 指标键 | stockstats 键 | 含义 |
| --- | --- | --- |
| `close_50_sma` | `close_50_sma` | 50 日简单移动平均线 |
| `close_200_sma` | `close_200_sma` | 200 日简单移动平均线 |
| `close_10_ema` | `close_10_ema` | 10 日指数移动平均线 |
| `rsi` | `rsi_14` | 14 周期相对强弱指数 |
| `macd` | `macd` | 指数平滑异同移动平均线 |
| `boll` | `close_20_sma` | 布林带中轨 (20-SMA) |
| `boll_ub` | `boll_ub` | 布林带上轨 |
| `boll_lb` | `boll_lb` | 布林带下轨 |
| `atr` | `atr` | 真实波动幅度 |
| `vwma` | `vwma` | 成交量加权移动平均线 |

这就是为什么即使最长的分析窗口仅为 90 天，获取数据的回溯期仍设定为 365 天——像 `close_200_sma` 这样的指标至少需要 200 个交易日的历史数据才能产生有意义的值。CSV 解析工具 `_parse_csv_to_dataframe` 负责处理标准化，并在数据格式错误或不足时优雅地返回 `None`，随后指标计算循环会捕获该异常并填充为 `"无数据"`。

## VPA 预计算：为 LLM 执行算术密集型分析

**量价分析** (VPA) 模块 `_compute_vpa_indicators` 是数据收集器中计算最密集的函数。它从 OHLCV 数据中预计算 10 余项衍生指标，并将其格式化为结构化的 Markdown 表格——因为 LLM 不擅长算术，却极擅长解读带标签的模式。关键的预计算信号包括：

- **量比**（`volume / 20日均线`）及定性标签：巨量 (>2.0), 明显放量 (>1.5), 温和放量 (>1.0), 缩量 (<0.8), 极度缩量 (<0.5)
- **量价配合** —— 将每根 K 线分类为 一致(涨+放量), 背离(涨+缩量), 一致(跌+放量), 背离(跌+缩量), 或 中性
- **OBV 趋势** —— 10 日移动平均线方向 (上升/下降)
- **形态检测** —— 顶背离，底部放量，恐慌抛售，高位放量滞涨

该函数以 Markdown 表格形式输出最近 30 天的数据，其后跟随一个标记出可操作信号的“关键形态识别”部分。这种设计使 LLM 的角色纯粹局限于解读——它读取预计算的标签，而非进行数值推理。

如果你添加了一个需要预计算指标的新分析师，请遵循 VPA 模式：在 `_fetch_all` 中完成所有数值计算，生成人类可读的 Markdown/文本块，并将其作为新键存储在结果字典中。切勿将算术运算委托给 LLM。

## 时间窗口：短期 vs. 中期

`get_window` 方法使用时间范围元数据对数据池进行标注。这是一种轻量级操作——它创建数据池字典的浅拷贝并添加两个元数据键：

| 时间范围 | `_data_window` | `_horizon` | 典型分析师 |
| --- | --- | --- | --- |
| `short` | "14天" | `"short"` | Market, Volume Price, Smart Money |
| `medium` | "90天" | `"medium"` | Fundamentals, Macro, News, Social |

数据池本身**不会**按时间范围进行过滤——完整的 365 天 OHLCV CSV 和所有基本面数据始终存在。时间范围元数据只是告诉分析师如何*构建*其分析提示词。这是一种经过深思熟虑的权衡：过滤虽能减少 Token 用量，但可能会导致 Agent 丢失交叉引用所需的上下文。

## 错误韧性：_safe 包装器与优雅降级

`_fetch_all` 中的每个数据获取任务都由 `_safe` 辅助函数包装，该函数会捕获所有异常并返回描述性的错误字符串，而不是导致整个收集过程崩溃。这意味着失败的龙虎榜详情调用或缺失的内部交易响应将在数据池中填充类似 `"get_lhb_detail 调用失败：HTTPError: 429"` 的信息——读取该键的分析师将在其提示词中看到该错误信息，而不是使整个分析管道停滞。仅当调用时间超过 0.5 秒时才会输出耗时日志，从而保持了快速路径操作的日志整洁。
