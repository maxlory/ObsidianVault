主张驱动的多空辩论是 TradingAgents-AShare 内部的核心对抗推理引擎。在七个并行的分析师 Agent 生成各自的维度报告后，系统从协作式数据收集转向结构化的辩证过程：**看多研究员**与**看空研究员**交替发言，将每个论点锚定为机器可读的**主张**，这些主张携带 ID、证据、置信度分数和生命周期状态。**研究经理**对辩论进行裁决，并综合生成可执行的投资计划。这种设计确保了最终的交易决策不是浅层的投票计数，而是加权证据命题的可追溯收敛——或是有意推翻。

该辩论在 LangGraph 状态机中占据一个边界明确的子图。所有分析师的 "Done" 节点扇入至**看多研究员**，按照惯例由其开启辩论。此后，条件边在看多和看空之间交替，直到达到可配置的轮次上限，此时控制权流转至研究经理进行裁决。

路由逻辑位于 `ConditionalLogic.should_continue_debate` 中。每次发言都会使 `investment_debate_state["count"]` 加一；由于看多和看空每轮各发言一次，因此 *N* 个完整轮次的总计数为 `2 × N`。当计数达到上限时，无论上一发言者是谁，条件边都会路由至**研究经理**。这保证了平等的发言时间——如果看多开启了该轮，看空总能获得最终的驳斥机会。

## 主张生命周期与结构化载荷

该辩论的标志性创新是**主张**——一种一等命题单元，两位研究员在辩论过程中必须创建、引用并解决它。每项主张都是一条结构化记录：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `claim_id` | `str` | 自增标识符，例如 `INV-1`, `INV-2` |
| `speaker` | `str` | 人类可读标签，例如 "Bull Analyst" |
| `speaker_key` | `str` | 机器键，例如 "Bull" |
| `stance` | `str` | `"bullish"` 或 `"bearish"` |
| `claim` | `str` | 命题文本（根据提示词约束不超过 28 个字符） |
| `evidence` | `list[str]` | 最多 3 条支撑证据项 |
| `confidence` | `float` | 0–1 的置信度分数 |
| `status` | `str` | 生命周期状态: `open` → `addressed` → `resolved` / `unresolved` |
| `target_claim_ids` | `list[str]` | 该主张所攻击的对手主张 ID |
| `round_index` | `int` | 创建该主张的辩论轮次 |

### 主张状态机

> **[原图为 mermaid 图；下列为从渲染 SVG 提取的节点/边标签（近拓扑序），非原始 mermaid 源码]**

主张在系统中的流转如下：当研究员提交回复时，LLM 会发出一段嵌入在 HTML 注释中的 JSON 载荷，标记为 `<!-- DEBATE_STATE: {...} -->`。`update_debate_state_with_payload` 函数解析该载荷，提取 `new_claims`、`responded_claim_ids`、`resolved_claim_ids` 和 `unresolved_claim_ids`，然后相应地修改主张映射表。此协议确保了 LLM 表达的每一个观点都能被程序化地追踪、质疑和解决——将自由形式的辩论文本转化为可查询的命题图。

## DEBATE_STATE 机器可读协议

两位研究员均受其提示词指示，在每次回复末尾的 HTML 注释中追加结构化的 JSON 代码块。其结构如下：

```json
<!-- DEBATE_STATE: {
  "responded_claim_ids": ["INV-1"],
  "new_claims": [{"claim": "...", "evidence": ["..."], "confidence": 0.72}],
  "resolved_claim_ids": ["INV-2"],
  "unresolved_claim_ids": ["INV-3"],
  "next_focus_claim_ids": ["INV-3"],
  "round_summary": "...",
  "round_goal": "..."
} -->
```

`extract_tagged_json` 函数使用正则表达式 `<!--\s*DEBATE_STATE:\s*(\{.*?\})\s*-->` 来隔离并解析此代码块，而 `strip_tagged_json` 则将其从可显示文本中移除。这种双重提取方式意味着人类可读的辩论记录保持整洁，而结构化的状态机在底层默默推进。如果 LLM 未能发出有效的载荷，系统会优雅降级：主张列表保持不变，并从原始回复的前 120 个字符中推导出备用摘要。

## 轮次目标递进

`default_round_goal` 为每轮注入渐进式的目标，而非任由辩论漫无边际。这些目标遵循精心设计的修辞弧线：

| 轮次 | 投资领域目标 |
| --- | --- |
| 1 | 确立核心多/空主张，并解释*为什么是现在* |
| 2 | 攻击对手最薄弱的假设——不要扩展话题 |
| 3 | 辩论时机：交易时间窗口是否有效？ |
| 4 | 辩论失败路径：谁低估了回撤风险？ |
| 5+ | 检查剩余的信息增益；准备收尾 |

每位研究员都会在其提示词上下文中收到 `round_summary` 和 `round_goal`，确保辩论随时间推移不断收紧，而非原地踏步。研究经理也可以通过在 DEBATE_STATE 载荷中发出自己的 `round_goal` 来覆盖默认目标。

## 研究员 Agent 内部机制

`create_bull_researcher` 和 `create_bear_researcher` 均遵循相同的结构模板——它们是封闭了 LLM 实例和专用记忆存储的工厂函数，并返回一个异步节点函数。关键的不对称性完全在于**提示词**，而非代码。

### 共享执行流水线

1. **状态提取**：从图状态中提取 `investment_debate_state`、所有分析师报告、主张列表、焦点/未解决主张 ID 以及轮次元数据。
2. **时间维度上下文注入**：`build_horizon_context` 前置特定时间维度的指令块（短期/中期）以及用户指定的关注领域和问题，并限定于 Agent 的角色（`agent_type="bull"` 或 `"bear"`）。
3. **记忆检索**：`FinancialSituationMemory.get_memories` 获取语义最相似的前 2 条历史推荐，使研究员能够参考历史模式。
4. **提示词组装**：将时间维度上下文 + 角色提示词 + 格式化的分析师报告 + 辩论历史 + 主张子集 + 轮次元数据拼接为单个提示词字符串。
5. **Token 级流式输出**：LLM 通过 `llm.astream` 流式传输其回复。每个数据块被转发至 `EventTracker` 用于前端实时可视化（`emit_debate_token`），并累积至 `full_content` 中。
6. **辩论消息发射**：流式输出完成后，完整回复作为辩论消息发射（`emit_debate_message`），向前端示意本轮发言结束。
7. **状态更新**：`update_debate_state_with_payload` 解析 DEBATE_STATE 代码块，推进主张生命周期，追加历史记录，并返回新的 `investment_debate_state`。

### 提示词不对称性：看多 vs 看空

看多提示词将研究员设定为对抗系统性看空偏见的逆向思考者——"系统存在看空偏见，你必须用硬证据为多头正名"——并要求提供量化的上行催化剂、风险回报比以及市场过度悲观的证据。看空提示词则构造成证据链攻击者，要求识别看多方最薄弱的假设、回撤路径建模以及明确的失败边界条件。两个提示词强制执行相同的 DEBATE_STATE 机器可读块格式，确保尽管修辞立场对立，其结构依然对等。

看多方看到的 `current_response` 字段实际上是看空方的上一次回复，反之亦然。这种交叉互换是关键机制，迫使每位研究员必须直接回应对手的论点，而非各说各话。

## 研究经理：裁决者

研究经理是辩论的裁判，也是通往 Trader Agent 前的最后一步。它接收**深度思考 LLM**（而非研究员使用的快速思考模型），这反映了综合推理需要更高的认知负担。其职责包括：

1. **裁定加权**：列出每位分析师的方向性裁定，并应用时间维度感知加权——技术面/资金流报告主导短期评估，而基本面/宏观面主导中期。
2. **预期差分析**：将聪明钱的仓位与散户情绪进行对比；将分歧（例如机构吸筹 + 散户恐慌）标记为补充性方向信号，但明确将其置于辩论共识之下。
3. **证据分拣**：将辩论证据分类为采纳（最强、有数据支撑）、未解决（高影响但无定论）或丢弃（薄弱或冗余），并附带明确的理由。
4. **可执行计划生成**：输出具体的交易指令——仓位大小、入场区间、止损、止盈阶梯和失败条件——而非模糊的方向性呼吁。
5. **持有理由**：如果裁定为持有，经理必须量化*等待的机会成本*，并明确将触发行动的*验证信号*。

研究经理同样会发射流式 Token 用于前端实时显示，但有一个重要区别：`round_num=-1` 标志着这是裁定而非辩论发言，并且 `is_verdict=True` 会传递给 `emit_debate_message`，以便前端以适当的视觉权重进行渲染。

研究经理使用 `deep_thinking_llm`，而两位研究员均使用 `quick_thinking_llm`。这一架构选择反映了一种深思熟虑的权衡：辩论发言应当快速响应（偏向快速模型），而最终的综合则需要更深入的推理（偏向深度模型）。流式检测工具还会捕获思考模型（如 DeepSeek）的 `reasoning_content`，分别记录首个推理 Token 耗时和首个内容 Token 耗时，用于性能诊断。

## 焦点主张选择与辩论收紧

防止辩论偏题的关键机制是**焦点主张**系统。每次发言后，`update_debate_state_with_payload` 会计算 `next_focus_claim_ids`：

1. 如果 LLM 在其载荷中明确提供了 `next_focus_claim_ids`，且这些 ID 存在于主张映射表中，则直接使用它们。
2. 否则，系统回退至：优先选择**未解决的主张**，其次是剩余的**开放主张**，上限为 2 个。

这意味着辩论会自动收敛于最具争议的命题。当 `format_claim_subset_for_prompt` 渲染焦点主张时，它们的前缀是 `*`（星号）而非 `-`（连字符，给 LLM 提供了在回复中优先处理这些主张的视觉线索。其结果是一个自我收紧的辩论循环，每一轮都缩小范围，直到达成决议或达到轮次上限强制裁决。

## 配置参数

辩论行为由两个主要配置键控制：

| 参数 | 默认值 | 效果 |
| --- | --- | --- |
| `max_debate_rounds` | `1` | 在研究经理接管之前的完整多+空轮次数；总发言次数 = `2 × max_debate_rounds` |
| `max_recur_limit` | `100` | LangGraph 递归限制；必须超过 `2 × max_debate_rounds + analyst_turns + risk_debate_turns` |

记忆存储在 `TradingAgentsGraph.__init__` 中按角色实例化：`bull_memory`、`bear_memory` 和 `invest_judge_memory`，每一个都由带有专用命名空间的 `FinancialSituationMemory` 提供支撑。这种隔离确保了看多方的历史模式不会污染看空方的检索，反之亦然。

## 从辩论到行动：交接

一旦研究经理作出裁定，图将无条件地将边指向 **Trader** Agent（`workflow.add_edge("Research Manager", "Trader")`）。Trader 接收 `investment_plan`（经理的完整综合报告）和 `investment_debate_state`（完整的主张注册表和辩论历史）。这种双通道交接意味着 Trader 可以同时参考执行摘要和原始证据链——这对于构建遵循辩论期间识别的细粒度风险条件的入场仓位至关重要。

在 Trader 提出计划后，系统进入[三方风险辩论与修订 ](https://zread.ai/KylinMountain/TradingAgents-AShare/9-three-way-risk-debate-and-revision)阶段，激进、保守和中立的风险分析师将在最终执行前对该计划进行第二轮结构截然不同的对抗性审查。
