## Story A1: 账单出账时自动获得阶梯返现并抵扣账单

**Epic:** Cashback 年消费阶梯返现
**Story ID:** （待建）
**Priority:** P0
**Story points:** （待工程估算）
**关联 PRD:** 主 PRD §5 账单（出账 job 增加 cashback 计算步骤 + 账单结构加返现记账行）

### User Story

> **As a** 持卡用户，
> **I want** 每期账单出账时，系统按我开卡年内已清算的年消费自动计算阶梯返现，并以 USDT 记账抵扣本期账单，
> **So that** 我的应还金额直接减少，无需任何手动申领动作就能拿到返现权益。

### Context

mentor 已确认（B-2/B-3/B-4）：返现以 USDT 记账、递延到账单出账时统一计算（规避交易流水取消/退款的不确定性）、基数仅计已完成清算的流水。公式参数已拍板（B-1）：按开卡年年消费分档 2%/2.5%/3%，年度 cap 500/1,000/1,500，达档全量适用、边界含等于。每期计算式采用 C-1 推导（可推翻）：本期返现 = max(0, min(年累计已清算消费 × 当前档位比例, 当前档位 cap) − 本开卡年已返总额)。

### Acceptance Criteria

**AC1: 基础档返现正确入账**
```
Given 用户开卡年内累计已清算消费 $10,000，本开卡年已返总额为 0
When 本期账单出账
Then 生成一笔 200 USDT（$10,000 × 2%）的返现记账，本期账单应还金额相应减少 200 USDT，返现流水标注所属账单期
```

**AC2: 仅已清算流水计入基数**
```
Given 用户本期有一笔 $5,000 消费处于「确认中」、一笔 $2,000 已退款/取消、一笔 $3,000 已完成清算
When 本期账单出账计算返现
Then 返现基数只包含 $3,000 已清算消费；退款/取消流水永久不计入；「确认中」流水在其完成清算后计入后续账期的年累计基数
```

**AC3: 年中跳档自动补差**
```
Given 用户上期出账后年累计已清算消费 $110,000、已返总额 500 USDT（2% 档 cap 已触顶）
When 本期新增 $15,000 已清算消费使年累计达 $125,000（≥ $120,000，进 2.5% 档）后出账
Then 本期返现 = min($125,000 × 2.5%, 1,000) − 500 = 500 USDT——跳档后全量按新档位重算并自动补差，且不重复发放已返部分
```

**AC4: cap 触顶后停止返现**
```
Given 用户 2% 档年度 cap 500 USDT 已全额返完，且年累计消费未达 $120,000 下一档门槛
When 后续账单出账
Then 本期返现为 0，不产生负数、不产生重复入账、不产生 0 元流水
```

**AC5: 开卡年切换清零**
```
Given 用户开卡周年日到达，进入新的开卡年
When 新开卡年内首期账单出账
Then 年累计消费、已返总额、档位全部从零重新累计，起始档位回到 2% / cap 500
```

### Edge Cases

- [ ] **返现大于本期应还金额**：用户提前还款或小额账单，出账时应发返现 > 本期应还——抵扣后剩余部分是结转下期还是追加为 USDT 余额入账？B-2 两种形式（追加入账 / 抵扣账单）并存但无裁决规则 → 见 Open Questions
- [ ] **账单周期横跨开卡周年日**：基数按流水清算日期归属新旧开卡年切分——精确切分规则文档未定义 → 见 Open Questions
- [ ] **边界值等于判定**：年累计恰好 $120,000 / $360,000 时必须进入更高档（B-1 明确含等于），测试用例需覆盖等值点
- [ ] **出账 job 失败重跑**：返现计算与入账必须幂等，同一账单期不重复入账
- [ ] **出账时点细节**：D-3 竞品结算周期调研结论可能微调出账时点——依赖待定项 D-3，实现时预留计算触发时点的可配置性

### Out of Scope

- 账单页的返现明细与样式展示（Story A2）
- 返现运营报表与追溯（Story A3）
- 返现追回逻辑——C-2 推导：基数只认清算终态，出账后不存在退款/取消，无追回场景
- Shop 端任何返现（B-12：本期仅信用卡端）

### Open Questions

1. 返现抵扣后剩余额的处理规则（结转 vs 追加 USDT 入账）——B-2 两种形式并存，需产品拍板
2. 开卡年切换的精确时点定义：按开卡周年日自然日切分，还是与账单周期对齐？跨周年日账单期的基数切分规则？
3. 年消费的计价口径：档位门槛以 $ 计，消费流水的美元口径折算规则（如涉多币种）文档未提及

### Definition of Done

- [ ] AC1–AC5 全部通过，含单元测试覆盖：三档位、跳档补差、cap 触顶、开卡年清零、等值边界五类用例
- [ ] 出账 job 重跑幂等验证通过（同一账期二次执行不产生重复返现）
- [ ] 返现记账在账务侧可对平（返现流水总额 = 账单抵扣总额）
- [ ] Edge cases 已处理或已带 Open Question 拍板结论后处理（未拍板项新建 ticket）
- [ ] 产品在 staging 用真实分档数据核对过至少一轮完整出账

## Story A2: 在账单中查看返现明细与年度进度

**Epic:** Cashback 年消费阶梯返现
**Story ID:** （待建）
**Priority:** P0（mentor 原话明确要求账单样式重点展示，属已确认决定 B-5）
**Story points:** （待工程估算）
**关联 PRD:** 主 PRD §5 账单（账单样式重点展示返现）
**依赖:** Story A1（返现数据）

### User Story

> **As a** 持卡用户，
> **I want** 在账单页看到本期返现金额、抵扣关系和年度累计返现进度，
> **So that** 我能直观感知返现权益的价值、确认返现算得对，从而更愿意持续用卡消费。

### Context

B-5 已拍板：展示位 = 账单页返现明细，「本期返现 + 年度累计返现/cap」两行；返现在账单中直接记账抵扣（减少应还），账单样式中重点展示。mentor 原话强调返现是提升用户感知的权益点（A3-5）。

### Acceptance Criteria

**AC1: 本期返现行**
```
Given 本期账单产生了返现
When 用户查看账单页
Then 账单展示「本期返现」金额（USDT）及其与应还金额的抵扣关系，用户能读出：应还 = 本期消费应还 − 返现抵扣
```

**AC2: 年度累计进度行**
```
Given 用户处于某一档位（如 2.5% 档）
When 用户查看账单返现明细
Then 展示「年度累计返现 / 当前档位 cap」（如 750 / 1,000 USDT），与后端记账数据一致
```

**AC3: 零返现期的展示**
```
Given 本期返现为 0（cap 触顶，或本期无已清算消费）
When 用户查看账单
Then 返现区展示 0 及原因提示（如「本年度当前档位返现已达上限」），不留空白、不隐藏该区块
```

**AC4: 视觉重点展示**
```
Given 账单含返现记录
When 账单渲染
Then 返现信息以专属突出区块呈现于账单视觉层级的显著位置（具体样式以设计稿为准，本 AC 只约束「有专属突出区块」这一行为）
```

**AC5: 历史账单一致性**
```
Given 用户查看任一历史账单
When 打开该期账单详情
Then 展示的是该期出账时点的返现快照（本期返现、当期档位、当期累计），不随后续档位变化回改
```

### Edge Cases

- [ ] **等值边界档位展示**：年累计恰好 $120,000 时展示 2.5% 档而非 2% 档（与 A1 判定一致）
- [ ] **跳档补差期的展示**：补差发生的账期，本期返现金额会明显高于「本期消费 × 档位」的直觉值——是否需要补差说明文案 → 见 Open Questions
- [ ] **移动端窄屏**：返现两行在移动端账单不被截断

### Out of Scope

- 返现规则说明页/权益介绍页（文档未提及，不在本期）
- 返现计算逻辑本身（Story A1）
- 独立的返现历史列表页（账单内明细以外的形态，文档未确认）

### Open Questions

1. 跳档补差账期是否需要「为什么这期返得多」的解释文案，避免客诉误解？
2. 展示币种：门槛以 $ 计、记账以 USDT 计，账单展示统一用哪个符号口径？

### Definition of Done

- [ ] AC1–AC5 全部通过
- [ ] 展示数值与 A1 后端记账数据 100% 对平（自动化断言）
- [ ] 设计稿评审通过且账单样式实现与设计稿一致
- [ ] 移动端视口验证通过
- [ ] 产品与设计在 staging 走查通过

## Story A3: 返现运营报表与单用户返现追溯

**Epic:** Cashback 年消费阶梯返现
**Story ID:** （待建）
**Priority:** P1

### User Story

> **As a** 平台运营人员，
> **I want** 在管理后台查看返现运营报表，并能追溯任一用户任一账期的返现计算明细，
> **So that** 我能监控返现成本对资金池的影响、完成账务核对，并在客诉时快速解释返现金额的来龙去脉，而不是每次都找工程查库。

### Context

落地影响面表：主 PRD §8 新增「返现与奖励的运营报表」。mentor 方法论关注点④明确要求评估「后台用户是否因新增功能增加额外工作」——本故事把新增运营动作显式定义并配好工具，避免运营靠人肉查库。

**本功能新增的运营动作（显式列出）**：
1. 周期性（如每月）查看返现成本汇总，监控对资金池目标的冲击（方法论③）
2. 客诉发生时追溯单用户单账期的返现计算明细
3. 财务对账时导出返现流水

### Acceptance Criteria

**AC1: 报表汇总查询**
```
Given 管理后台报表模块已有返现数据
When 运营人员按时间范围查询
Then 展示该区间的返现总额（USDT）、涉及用户数、按档位（2%/2.5%/3%）的金额与人数分布
```

**AC2: 单用户计算明细追溯**
```
Given 某用户某账期存在返现记录
When 运营人员查看该条记录明细
Then 可见完整计算要素链：年累计已清算消费、当前档位与比例、档位 cap、本开卡年已返总额、本期返现计算式与结果
```

**AC3: 对账导出**
```
Given 运营人员在报表页选定时间范围
When 点击导出
Then 生成对账文件（CSV），逐行包含：账单期、用户标识、返现基数、档位、cap、本期返现金额
```

**AC4: 权限控制**
```
Given 一个无报表查看权限的后台账号（沿用现有后台权限体系）
When 访问返现报表模块
Then 拒绝访问并记录审计日志
```

### Edge Cases

- [ ] **报表与账务流水对不平**：提供差异定位入口（按账期下钻到流水级）
- [ ] **跳档补差账期的明细**：补差金额在计算式中单独可见，运营能向用户解释
- [ ] **大时间范围导出**：整年全量导出不阻塞后台（异步生成或分页）

- 面向财务系统的自动化对账接口（本期人工导出）

### Open Questions

1. 报表查看/导出的权限角色划分（运营 vs 财务 vs 合规）沿用现有后台哪套角色？
2. 返现成本是否需要设置预算预警阈值（文档未提及，运营视角可能需要）？

## Story B1: 以记账流水形式收到质押奖励收益

**Epic:** XAUT staking reward
**Story ID:** （待建）
**Priority:** P0
**Story points:** （待工程估算）
**关联 PRD:** 新增模块（staking reward 计息与发放引擎）+ 主 PRD §7 用户端（收益流水展示）
**依赖:** 依赖待定项 D-1（计息细则）

### User Story

> **As a** 持卡用户（信用卡质押持有人），
> **I want** 按独立 APY 周期性收到质押奖励，且每笔奖励以「质押奖励」记账流水的形式出现在我的资金流水里，
> **So that** 我能明确感知质押资产在持续产生收益，从而更愿意保持质押、继续持卡。

### Context

B-6 已确认（推翻此前「复用 stake 产品收益/纯前端展示」的理解）：这是新的奖励机制——给客户独立的奖励 APY，数值低于 stake 产品收益率。B-7：客户感知必须明确，以记账流水形式提示收益更新。C-3 推导（可推翻）：覆盖对象 = 信用卡质押中的 XAUE。C-4 推导：记账币种建议随 cashback 统一用 USDT——依赖待定项 D-1 确认。

### Acceptance Criteria

**AC1: 周期发放入账**
```
Given 用户信用卡质押中持有质押资产，且发放周期到达（周期依赖待定项 D-1）
When 计息发放引擎执行本期发放
Then 用户资金流水新增一笔类型为「质押奖励」的入账流水，包含：金额、计息区间、对应质押资产标识（币种依赖待定项 D-1，C-4 建议 USDT）
```

**AC2: 流水可见可筛选**
```
Given 用户已收到至少一笔质押奖励
When 用户查看交易/资金流水列表

## Story B3: 配置 staking reward 参数并监控发放（管理后台）

**Epic:** XAUT staking reward
**Story ID:** （待建）
**Priority:** P0
**Story points:** （待工程估算）
**关联 PRD:** 主 PRD §8 平台后台 + 新增模块（计息发放引擎的运营侧）
**依赖:** 依赖待定项 D-1（参数清单以 D-1 结论为准）

### User Story

> **As a** 平台运营人员，
> **I want** 在管理后台配置质押奖励的 APY 等参数，并监控每期发放批次的执行结果，
> **So that** 业务能随市场调整奖励水平，发放异常能被及时发现和处理，而不是靠工程改配置、查日志。

### Context

B-6 确定奖励是独立 APY 的新机制，意味着 APY 必然需要一个可运营的配置入口（数值会随业务调整）；发放引擎为新增模块，运营需要批次监控。mentor 方法论关注点④：本故事显式定义 staking reward 给后台新增的工作量。

**本功能新增的运营动作（显式列出）**：
1. 初始配置与后续调整奖励 APY（频率取决于业务策略）
2. 每期发放后核对批次结果，处理失败重发
3. 周期性核对奖励总成本对资金池的影响（方法论③）

### Acceptance Criteria

**AC1: 参数配置与审计**
```
Given 运营人员在后台奖励参数配置页
When 修改 APY（及 D-1 确定后的其他参数）并提交
Then 新参数保存成功，且审计日志记录操作人、时间、旧值、新值
```

**AC2: 参数变更生效边界**
```
Given APY 参数变更提交成功
When 下一个计息区间开始
Then 新 APY 仅对生效时点之后的计息区间生效，已计提的历史收益不回溯重算
（⚠️ 生效规则本身依赖待定项 D-1；本 AC 为建议默认值「区间切换生效、不回溯」，若 D-1 另有定义以 D-1 为准）
```

**AC3: 发放批次监控**
```
Given 一期发放批次执行完成
When 运营人员查看发放记录
Then 可见批次状态（成功/部分失败/失败）、涉及用户数、发放总额、计息区间，失败明细可下钻到用户级并支持重发
```

**AC4: APY 合理性警示**
```
Given 运营输入的奖励 APY 数值不低于当期 stake 产品收益率
When 提交配置
Then 系统给出警示并要求二次确认（B-6 业务约束：奖励 APY 低于 stake 产品收益率；此 AC 为 C 层式建议——用警示而非硬阻断，保留业务灵活性，可推翻）
```

### Edge Cases

- [ ] **对比基准数据源**：AC4 需要「当期 stake 产品收益率」作为对比值，其数据来源（人工录入 vs 系统取数）文档未定义 → 见 Open Questions
- [ ] **发放执行中修改参数**：批次执行期间锁定参数读取版本，避免同批次内参数不一致
- [ ] **权限最小化**：参数配置权限与报表查看权限分离，配置权限收敛到指定角色
- [ ] **参数配置为空/引擎未初始化**：发放周期到达但参数未配置时，引擎不执行并告警，而非按 0 或默认值发放

### Out of Scope

- cashback 报表（Story A3；后续若统一「返现与奖励报表」再合并）
- APY 的自动化定价策略（文档未提及，人工配置）

### Open Questions

2. stake 产品收益率对比基准从哪里取数（AC4 前置）？
3. 参数变更是否需要双人复核（maker-checker）？涉及资金成本的参数，合规上可能有要求——文档未定义

- [ ] AC1–AC4 全部通过

## Story C1: 登记与管理出金白名单地址

**Epic:** 白名单地址 AML
**Story ID:** （待建）
**Priority:** P0
**Story points:** （待工程估算）
**关联 PRD:** 主 PRD §7 用户端（新增：出金白名单地址管理页）

### User Story

> **As a** 持卡用户，
> **I want** 登记、查看和管理我的出金白名单地址，且登记时地址经过 AML 检测，
> **So that** 平台向我付款只会打到我确认过的安全地址，我的资金不会被误付或付到风险地址。

### Context

B-10：白名单管出金——客户登记出金白名单地址，平台只向白名单地址付款；入金因 web3 属性无法限制。C-6 推导（可推翻）：登记时地址同样过 WaaS AML 检测；当前信用卡 PRD 无用户主动提现功能，白名单的生效场景 = 后续任何向用户链上地址付款的动作（提现功能上线时、退款到链上时）。登记入口、变更/删除流程、数量上限、冷静期均为 D-4 待定。

### Acceptance Criteria

**AC1: 登记成功路径**
```
Given 用户在白名单管理页提交一个格式合法的链上地址
When WaaS AML 检测通过（阈值以 WaaS 为准，B-11）
Then 该地址进入白名单列表，展示登记时间与「已生效」状态
```

**AC2: 登记地址本身命中风险**
```
Given 用户提交的地址被 WaaS AML 判定命中黑灰
When 检测完成
Then 拒绝登记、向用户明确提示该地址存在风险且未加入白名单，同时该次命中记录同步到管理后台（供 Story C3 查看）
```

**AC3: 出金强校验**
```
Given 平台发起任何向该用户链上地址付款的动作（提现/链上退款等场景，随对应功能上线生效）
When 目标地址不在该用户的有效白名单中
Then 付款被阻断，不允许向非白名单地址出金
```

**AC4: 无白名单地址时的出金请求**
```
Given 用户未登记任何白名单地址
When 用户触发出金场景（对应功能上线后）
Then 出金被阻断，并以空状态引导用户先完成白名单登记（给出登记入口），而非报错死路
```

**AC5: 格式前置校验**
```
Given 用户提交格式非法或链类型不匹配的地址
When 点击提交
Then 前端/服务端格式校验直接拦截并提示具体原因，不发起 AML 检测调用（节省检测成本）
```

- [ ] **每用户地址数量上限**——依赖待定项 D-4

- 用户主动提现功能本身（当前 PRD 不存在该功能，本故事只建白名单能力与校验闸门）

```

### Edge Cases

- [ ] **已废弃旧地址再次收到入金**：web3 无法阻止他人向旧地址转账，该笔资金的检测与隔离路径必须仍然生效且用户端可见状态——处置细节文档未定义 → 见 Open Questions
- [ ] **检测异步的中间态**：若 D-2 确认检测为异步，用户在检测完成前看到的状态（「到账确认中」）需要定义——依赖待定项 D-2
- [ ] **同一用户短期内多次命中**：是否升级处置（冻结充值功能并转人工）——文档未定义 → 见 Open Questions
- [ ] **部分命中**：一笔还款入金被隔离导致账单逾期风险——被隔离资金不算还款成功，逾期判定与用户提示如何衔接 → 见 Open Questions

### Out of Scope

- 管理后台的处置操作与隔离台账（Story C3）
- 隔离资金的终局处置（退回/上报）流程——文档未定义，不在本故事虚构
- 入金地址限制（B-10 明确入金不限制）

### Open Questions

1. 已废弃地址后续再收到的入金如何处置、如何在用户端呈现？
2. 用户对风险判定有异议时的申诉通道？文档未定义（客服路径 or 产品内入口）
3. 风险隔离导致还款未入账时，逾期与罚息判定是否豁免宽限？——直接影响客诉与合规，建议尽快拍板
4. 风险提示文案的合规边界（能向用户披露多少判定信息）需合规审核

### Definition of Done

- [ ] AC1–AC4 全部通过
- [ ] 与 WaaS 联调覆盖：通过、命中、超时三态（依赖 D-2 接口）
- [ ] HD 换址链路集成测试通过（旧地址停用、新地址生效、通知触达）
- [ ] 命中场景的用户端状态与 Story C3 后台状态一致性断言通过
- [ ] 风险提示文案经合规审核

## Story C3: 风险地址管理与隔离资金处置（管理后台）

**Epic:** 白名单地址 AML
**Story ID:** （待建）
**Priority:** P0
**Story points:** （待工程估算）
**关联 PRD:** 主 PRD §8 平台后台（新增：地址风险管理模块）+ §11 钱包架构（黑灰独立归集记录）+ S4 AML 章（口径修订为 WaaS）
**依赖:** 依赖待定项 D-2（阈值配置项、禁用/替换操作流程）

### User Story

> **As a** 合规/运营人员，
> **I want** 在管理后台集中查看所有 AML 命中记录、隔离资金台账与地址处置状态，并能执行或确认地址禁用与换址操作，
> **So that** 合规义务有据可查、风险资金不流入正常资金池，且每个处置动作可追溯，无需依赖工程手工查库处理风险事件。

### Context

落地影响面：§8 新增「地址风险管理模块（禁用/替换/隔离记录查看）」；§11 黑灰独立归集记录；S4 AML 章由「自建接 Chainalysis」改为「接入 WaaS AML 能力」，黑灰标准以 WaaS 阈值为准（B-11）。mentor 方法论关注点③④：隔离资金不得冲击正常资金池目标；本故事显式定义 AML 给后台新增的工作量。

**本功能新增的运营/合规动作（显式列出）**：
1. 日常查看 AML 命中告警与隔离记录（频率取决于命中量，需上线后观测）
2. 对命中地址执行或确认禁用 + HD 换址
3. 隔离资金台账核对，确保与正常资金池隔离
4. 白名单登记命中记录的复核（与 Story C1 AC2 联动）
5. 配合监管/审计出具处置记录

### Acceptance Criteria

**AC1: 命中记录列表**
```
Given 存在 AML 命中事件（入金命中或白名单登记命中）
When 合规人员打开地址风险管理模块
Then 可见命中列表：用户、地址、命中时间、WaaS 判定结果、涉及金额（入金类）、当前处置状态，支持按状态/时间筛选
```

**AC2: 隔离资金独立记账**
```
Given 一笔命中资金被禁止归集上账
When 合规人员查看隔离台账
Then 该笔资金在独立归集记录中可见（金额、来源地址、命中依据、隔离时间），且不计入平台正常资金池余额与用户可用余额
```

**AC3: 地址禁用与换址的操作与审计**
```
Given 一个命中风险的充值地址
When 合规人员执行（或确认系统自动执行的）禁用 + HD 派生新地址
Then 地址状态变更为已禁用、新地址生效，全程审计日志记录操作人/时间/处置依据，且用户端同步更新（对应 Story C2 AC3）
```

**AC4: 判定标准以 WaaS 为准（口径统一）**
```
Given 任一条命中记录
When 合规人员查看判定详情
Then 展示 WaaS 返回的风险等级/判定依据原文；后台不提供自定义黑灰判定标准的入口（B-11：以 WaaS 阈值为准，避免与 S4 旧口径的数值分歧复活）
```

**AC5: 双端状态一致**
```
Given 一条命中记录完成任一处置动作
When 对比用户端展示与后台记录
Then 两端对该笔资金/该地址的状态展示一致（B-9 双端提示同源）
```

### Edge Cases

- [ ] **隔离资金的终局处置**：退回原地址、司法上报、长期冻结的流程与责任人未定义——本模块先做「隔离 + 台账 + 状态标记」，终局处置为后续故事 → 见 Open Questions
- [ ] **WaaS 服务不可用**：入金检测不可用期间的降级策略（全部挂起归集 vs 放行后补检）——依赖待定项 D-2，需在对接清单中明确
- [ ] **误判申诉与人工放行**：是否允许合规人员对命中记录人工复核放行？若允许，须双人复核 + 审计——文档未定义 → 见 Open Questions
- [ ] **存量回溯**：上线前已入金的历史资金/已有充值地址是否回溯检测——文档未定义 → 见 Open Questions
- [ ] **命中量超预期**：若 WaaS 阈值偏严导致命中量大，人工处置工作量失控——上线初期需要命中量监控（方法论④）

### Out of Scope

- 隔离资金的退回/上报执行流程（未定义，待合规流程明确后另立故事）
- WaaS 阈值本身的配置（B-11：以 WaaS 平台设置为准，是否可调属 D-2 对接范围）
- Shop 端地址风险（B-12）
- 自建 Chainalysis 接入（B-8 已排除）

### Open Questions

1. **隔离资金终局处置**：退回/上报/解冻的决策流程、责任人、时限——合规工作量的大头，且直接关系用户资产，建议优先拍板
2. 是否允许人工复核放行误判（及其权限与复核机制）？
3. 存量地址与存量资金是否回溯检测？
4. 命中告警是否需要主动推送给合规（邮件/IM），还是仅后台被动查看？——影响响应时效与工作量

### Definition of Done

- [ ] AC1–AC5 全部通过
- [ ] 隔离台账与账务系统对平（隔离资金不出现在正常资金池报表，自动化断言）
- [ ] 处置操作审计日志完整可查
- [ ] 与 Story C2 的双端一致性联测通过
- [ ] 合规同事在 staging 完成一次「命中 → 查看 → 处置 → 台账核对」全流程演练
- [ ] S4 AML 章口径修订完成（自建 Chainalysis → WaaS）

## 附 · 写作过程中发现的需求缺口（建议优先补齐）

1. **cashback 抵扣剩余额的裁决规则缺失**：B-2 说返现「追加入账或直接抵扣账单」两种形式并存，但没有选择规则。当用户提前还款或账单金额小于应发返现时，剩余返现是结转下期还是追加为 USDT 余额？直接影响账务模型设计，建议出账 job 开发前拍板。（Story A1）
2. **staking reward 终态结算规则缺失**：质押品被清算、用户解押/销卡时，已计提未发放的收益如何处理（按日折算发放 / 不满周期没收 / 即时结清）——D-1 只覆盖正常周期的计息发放，终态场景完全空白，而清算恰恰是质押信用卡的高频风险事件。（Story B1）
3. **AML 隔离资金的终局处置缺失**：命中后「禁止归集 + 独立记录」只是把资金停住，退回、上报、解冻的流程与责任人没有定义——这是合规后台真正的工作量大头（mentor 关注点④），也直接关系用户资产安全；连带的「隔离还款导致账单逾期是否豁免」会最先产生客诉。（Story C2/C3）
4. 次级缺口：XAUT vs XAUE 奖励对象口径（B1）、白名单是否需人工审批（A-1 与 A-2 之间未闭合，C1）、白名单存量地址复检（C1）。
