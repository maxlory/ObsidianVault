>
> **持续积累**：后续需求优化中出现的类似疑问，都追加到本文档，作为同一批需求的参考资料。
>
> **两个"清算"务必分清**（本批需求反复出现，先声明）：
> - **交易清算 / settlement**：信用卡**消费交易**的清结算（授权→清算→入账）。cashback 与 staking reward 的计算基数用的是这个。
> - **强制清算 / liquidation**：抵押率击穿平仓线时**抵押品被变现还债**。§6 提到的"清算残值"属于这个，与交易清算无关。

## 疑问 1 · Cashback 的清算时点、与出账日的关系、资金池与后台影响（来自评审反馈 #2）

### 1.1 问题

cashback 返现基数是"已清算（settlement）完成的消费交易"。那么——① XAUE 信用卡的**交易清算时点**具体是什么时候？② 与**账单出账日**是什么关系？③ 这样"递延到出账时按已清算流水计算"的设计，会不会对**基础资金池**造成不必要的波动？④ 会不会给**后台**增加额外工作？

### 1.2 交易清算时点（依据现有 PRD）

来源：`prd-xaue-credit-card.md §4.5 / §4.6 / §4.3`

XAUE 信用卡的授权决策在发卡处理商 RedotPay 侧完成，平台只做**事后消费 Webhook 记账**。一笔消费的状态流转：

1. **预授权（PRE_AUTH）**：用户刷卡 → 供应商批准 → 金额冻结（占用"已冻结授权"额度）
2. **最终清算（settlement）**：平台收到供应商 `cardTransactionSuccess` Webhook → 该交易**清算完成**，转入"已出账未还"→ **此刻起不再产生取消/退款风险**（准终态）
3. 取消（预授权超时未清算，冻结自动释放）/ 退款（`cardTransactionRefund`）都发生在清算完成之前或作为独立冲正

> **清算时点 = 平台收到 `cardTransactionSuccess` Webhook 的时刻**。这是 cashback 能否计入基数的判定点。

### 1.3 账单出账日 与 清算时点的关系（依据现有 PRD）

来源：`prd-xaue-credit-card.md §5.1 / §5.3`

- 账单日默认每月 1 日，账单生成器**每月 1 日凌晨**扫描并出账；还款日 = 账单日 + 21 天。
- 出账时统计范围 = **上一自然月内已完成清算的全部消费交易**。
- 卡组织轨道上，消费从授权到清算通常 **T+1 ~ T+3 工作日**。

**关系结论**：账单出账日（月初）时，上一自然月**绝大多数**消费交易都已清算完成，所以"出账时按已清算流水算 cashback"在时点上是成立的——出账时基数已是终态，不会再退款/取消。

**唯一边界**：月末最后 1-3 天发生的消费，可能在月初出账时**尚未清算完成**。处理办法（对齐 Chase 传统卡惯例）：**跨月未清算的交易顺延计入下一期 cashback 基数**，不在本期计。此边界规则建议写进 PRD §2 业务规则（当前已在 AC-01 边界覆盖，落地时明确一句）。

### 1.4 对基础资金池的冲击分析

**结论：递延到出账时统一计算的设计，对资金池冲击小、波动可控，优于逐笔即时返现。**

- **返现成本的来源**：cashback 在出账时以 USDT 记账抵扣账单 = 平台少收回等额 USDT，这是平台的**补贴成本**，需由平台收入/备付金覆盖。**年度 cap（每用户 500 / 1,000 / 1,500 USDT）严格封顶了单用户成本上限**，全平台成本可按开卡数估算、可预测。
- **为什么波动小**：递延到出账日"一个月算一次、一次性入账"，资金流**集中且可预测**；相比之下，若逐笔消费即时返现，每笔都要动一次资金、且要处理未清算交易的返现回滚，现金流波动大得多。
- **可预测的跳增点**：用户年中年消费跨过 $120,000 / $360,000 档时，出账当期会因"全量补差重算"出现一次返现跳增。但这**基于用户消费额、完全可预测**，不是不可控波动；且仍受年 cap 封顶。
- **与备付金的关系**：cashback 抵扣的是"用户应还账单"，不产生**即时可提现负债**（这也是本轮确认"cashback 无提现功能、只抵账单"后的直接好处——不会有一笔随时可被提走的现金压在备付金上）。

### 1.5 对后台工作量的影响（mentor 关注点④）

| 新增工作 | 性质 | 说明 |
|---|---|---|
| 出账 job 增 cashback 计算步骤 | **自动化，不增人工** | 出账时自动按已清算流水算，无需人工干预 |
| 返现成本核对 | 轻量运营 | 定期核对返现成本 vs 预算（返现报表支持） |
| 返现相关客诉 | 需客服支持 | 如用户对跳档补差金额有疑问，需解释（建议配"补差说明"文案降低客诉） |
| 对账 | **比即时返现更简** | 出账统一计算 + 只认清算终态 → 无返现追回（clawback）链路，对账负担低于逐笔即时返现的竞品 |

**结论**：cashback 给后台增加的主要是"自动化计算 + 轻量成本核对 + 少量客诉"，**没有引入重的人工流程**；且"递延+只认终态"的设计本身就是为了让后台对账最简。
