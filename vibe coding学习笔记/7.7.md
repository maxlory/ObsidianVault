## Skill的渐进式披露架构设计

意义：以渐进式披露管理skill中的内容意味着什么
1. 减少token的消耗
2. 减少其他内容对应该专注内容的影响
总结：渐进式披露的本质——以最小的 token 投入获得最高的任务完成质量

补充：注意力稀释效应
	注意力稀释效应，说的是上下文越长，LLM对每个信息片段的关注度越低。
	一个 5000token 的上下文中的关键指令，比一个50000 token 上下文中的同样
	指令，会被更准确地执行。一一这个有时候我们也叫“Lostin the midde”，也就
	是不要让大模型大海里捞针的意思。

### 下面是对Skill中内容的具体拆解：
#### 层级 1：目录页（Entry Point）
description—— Skills 系统扫描阶段读取的内容
	description内容具体，定位清晰，让 Claude 能准确判断相关性（LLM通过语义理解description确定是否调用skill）
	重点：<font color="#92d050">所有  Skill 的 description 共享 15,000 字符的总预算，单个 description 的上限约 1,536 字符（context 预算的 1%/所有 skill description 上限的10%）</font>
	思考：所以如果项目中的skills数量过多，不仅可能会影响LLM对skill的调用，更会导致上下文被skill的内容消耗

#### 层级 2：章节（Main Content）
SKILL.md——skill的正文部分，激活后才加载
	这一部分的设计原则是主文件提供“路线图”，通过文件引用指向详细内容，然后 Claude 根据用户请求决定加载哪些具体内容。
	重点：SKILL.md的目的更像是目录展示，告诉LLM这个skill中有哪些能力、文件。<font color="#92d050">给LLM指明如果要做什么，应该使用什么文件。而不是将全部能力都塞入正文中，导致LLM的注意力被稀释</font>
	注意：<u>在SKILL.md中可以添加一个Quick Reference 表格，让 Claude 快速定位需要哪个参考文件</u>
	1. 用“用户可能说的关键词”作为路由条件（而非“文件内容的技术名称”）
	2. 每个路由条目一行，不要超过 10 个条目（超过就需要分层）
	3. 高频路由放前面
	![[Pasted image 20260708094305.png]]
	总结：SKILL.md本质上是一个路由器——根据用户请求的类型，将 Claude 导向不同的资源文件
	![[Pasted image 20260708094437.png]]
	

#### 层级 3：附录（On-Demand Resources）
其他文件——**只有当 SKILL.md 中引用了这些文件，Claude 才会去读取这一类文件**
	<font color="#92d050">附录中的内容只有在读取完 SKILL.md 后，才有可能会读取。是否被读取，需要看 SKILL.md 中是否引用了这些文件</font>。
	让附录文件名清晰明了确实有帮助，但是不稳定，因为 agent 不一定会主动遍历整个文件夹，更不一定会读取所有文件内容。
报告模板：templates——不提供“知识”，而是提供“输出格式”
计算脚本：scripts——Claude 不需要**理解计算逻辑**，只需执行代码
	注意：<font color="#92d050">Skill 中的脚本生成交互式 HTML 文件，在浏览器中打开——Claude不需要因为生成网页，而消耗token</font>（类似于skill-creator中的可视化脚本）

#### 二、SKILL.md设计原则
1. 主文件控制在  500 行以内
2. 用 Quick Reference 表格做个快速路由
3. 什么内容放SKILL.md，什么内容放引用文件？——高频内容内联，低频内容外链
	常用的信息直接放在主文件，偶尔用到的详细信息放在引用文件，用<font color="#92d050">契约式引用</font>
	让 Claude 知道什么时候该加载、加载后能得到什么
	契约式引用三要素包括：
	1. 触发条件：什么情况下应该加载（“当用户问到 X 时”）
	2. 文件路径：去哪里找
	3. 内容预期：加载后能得到什么（“计算公式和行业基准”）
