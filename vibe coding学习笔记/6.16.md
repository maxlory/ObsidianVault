关于skill-creator的一些学习

重要资源的分层架构：
目录	             放什么	                   关键性质
scripts/	 脚本、工具	  **能直接执行**,不必把代码读进上下文
references/	大块文档、API 手册	   **用到时才读进来**,平时不占上下文
assets/	  模板、图标等	  **出现在最终产出里**,不是给模型读的

渐进式披露：
层级	                               内容	                  何时进上下文	                     体量
第 1 层:元数据	      name + description	永远在(开机就加载)	          ~100 词
第 2 层:SKILL.md            正文	          主要指令skill 一旦触发就加载	  理想 <500 行
第 3 层:附带资源	  references/scripts/assets	真用到才加载(脚本甚至能不读就跑)	无上限

以下是细节上的重点：
硬规则:
SKILL.md 保持 <500 行，快到上限就加一层**目录结构**,并明确指路“模型接下来该去读哪个文件”(L96)；
大 reference 文件(>300 行)要**带目录**(L98)。

按领域拆分(L100–109):
一个 skill 支持多个框架时,**按变体拆 references**——例如 /references/{aws,gcp,azure}.md,Claude 只读相关那个。

description 写得不准 → description 决定skill能否被触发。如果 description 不好，skill 正文写得再好也白搭。
description 要同时包含”这 skill 做什么”和“什么时候/什么语境该用它”,”所有 when-to-use 信息都放这里,不放正文”。
当前 Claude 倾向漏触发时，建议把描述写得主动一点(pushy)。

如果能在skill中解释为什么这么做，而不是简单地说必须这么做，对AI理解并且执行效果更好

能从当前对话中提取出用户想固化的流程，从而变成skill

skill-creator这个skill中本身就有要求用MCP等在创建skill之前进行调研，但是我几乎没见到调用过

skill中自带TDD测试，但是这个测试似乎没有避免过拟合的问题，测试的题目质量也堪忧。我觉得这个skill太大了，导致其中很多设计得很好的细节没有完全落地（毕竟AI有偷懒的嫌疑）。我的想法是将整个skill拆成设计、测试几个部分，形成一个完整的循环

skill中自带三个评测 subagent 的提示词
打分：给优化前后的两个内容打分，并且给出一句话判断
盲测对比：content(正确性/完整性/准确性)和 structure(组织/格式/可用性)分开按 1–5 打分。打分前不知道哪个内容是谁的
诊断：对比skill优化前后的文档差异和具体执行过层，给执行过程打分；根据文档差异对之前表现的打分进行核验

文件中的四条心法：
1. 从反馈中改进，但是不要过拟合。改动不要过于扣细节
2. 保持skill精简。不让skill浪费模型时间做无用功（和skill要求模型的具体流程有关）
3. 最好在skill中解释为什么这样做，而不是强制要求不这样做
4. 如果在多个测试用例中都出现了相同的动作，考虑是不是写成脚本放进scripts中

Description 自动优化循环：自己造触发评测集。脚本中包含自动优化循环（结构很完整，内容很多，非常适合抓出来重新做一个skill）
