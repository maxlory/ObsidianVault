### Sub-Agents
组件解决的都是上下文问题：如何使当前的上下文对结果的生成最有效
Sub-Agents的定义：拥有独立上下文，只给出最终结果——中间的过程不会对上下文造成污染
为什么一定需要一个新的agent执行任务：
	其实可以让Claude自己做这件事，然后让它忘掉具体过程，只记得结果。
	**工程化的本质**——解决的是行为不可控问题。==通过工具权限边界，把“我希望你别这么做”变成“你物理上做不到”。==毕竟Claude本身是一个不可控的发动机，工程化就是方向盘，牢牢地控制AI向确定的方向前进
我现在比较好奇地是：能不能自己设计经常使用的subagents，毕竟subagents是可以自己调用的

Claude的内置自代理：
Explore：翻项目、找位置
Plan：在真正修改代码之前，收集上下文、梳理依赖、生成实施路径
General-purpose：当任务比较复杂，需要多种能力配合
尝试将调研类的skill都作为subagent实现

==什么情况下需要使用Sub-Agents==
1. 高噪声输出任务：执行过程中会产生大量中间信息，但真正有用的，往往只有一个结论。（比如：测试、搜索、摘要、调研等）
2. 角色边界明确：由于大模型本身的不可靠性，一些可能限制在特定目录、进行特定行为的操作不稳定。子代理可以将特定行为限定在特定范围中。
3. 并行展开的研究型任务：调研多个问题，或者对比几种技术方案、从多个视角分析同一个问题时，这些探索之间往往是相互独立的。带回的结果也是独立的、可相互借鉴的
4. 可以拆成清晰阶段的流水线式任务。这类任务的关键在于每一个阶段的目标、权限和输出都是明确的。

==不适合使用Sub-Agents==
1. 任务需要频繁来回确认需求、不断调整方向，那子代理这种“派出去干活再回来汇报”的模式反而会拖慢节奏
2. 如果任务的各个阶段高度耦合，每一步都强依赖上一阶段的详细过程，那强行隔离上下文只会增加认知负担
3. 非常简单的小任务，启动子代理本身就有开销，直接在主对话中完成，反而更高效

重点：
1. 子代理不能生成子代理
2. Claude Code 支持自定义 agent type
3. 子代理既可以显式调用（直接说子代理的名字；也可以自动调用，但是要提到使用子代理实现）
4. 普通 subagent 不继承主对话中已经读取的 skill 内容。它只能读取自己配置中预加载的 skills，或者读取主 agent 在委派消息里显式传给它的摘要。

## 长期指导工程设计的通用方法论
==一、多 Agent是否需要的判断——上下文管理==
1. 上下文内容过多导致模型表现下降，需要管理上下文
2. 多个不同领域上下文同步进行，会互相污染

## 四种核心设计模式（多Agent设计模式）
1. ==Sub-Agents==：一个 <font color="#92d050">Supervisor</font> Agent 充当老板，将任务分解后委派给专门的 Sub-Agent。每个 Sub-Agent 解决一个特定的任务。（多Agent并行）
	**特点**：
	1. 上下文隔离能力非常强。每个 Sub-Agent 都拥有独立的上下文窗口
	2. 多个 Sub-Agent 可以同时展开工作，从而显著提升复杂任务的效率。同时token消耗剧增
	结论：适合大量信息过滤，多个不同领域信息串联
2. ==Skills==：渐进式能力加载（单Agent串行）
	**特点**：
	1. 始终与同一个 Agent 直接交互，交互路径最短，体验也最为流畅。
	2. 上下文隔离能力上相对较弱。随着交互的累积，上下文和消耗的token会不断上涨
	结论：适合需要连贯对话的场景
3. ==Handoffs==：活跃的 Agent 根据对话状态动态切换。Agent A 完成自己的阶段后，通过调用  handoff()  工具将控制权（和上下文）传递给 Agent B。（多Agent串行）
	**特点**：
	1. 不同 Agent 之间通过显式的交接机制完成角色切换，上下文并非整体共享，而是可以根据需要选择性地传递。
	2. 采用严格的顺序执行，不支持并行展开
	3. Handoffs 是通过 Prompt + 状态约束 + 工程结构模拟出来的。所以是一种“工程模式”，不是一个“框架特性”。
	
	**如何判断是否属于Handoffs**：
	1. 明确的阶段状态（State）
	2. 每个阶段都是一个“角色约束的 Agent 视角”。和上面相似，每个阶段的Agent角色都是确定的
	3. <u>显式的阶段完成条件</u>（Handoff Trigger）。这是 Handoffs 能稳定运行的核心。每个阶段都必须有完成条件（Exit Criteria）， 否则就会“卡在阶段里出不来”。
	**结论**：Handoffs 模式最适用于<u>具有明确阶段划分的流程型场景</u>。例如：从信息收集到问题诊断再到解决方案输出的多阶段客服或工单系统
4. Router：核心在于对输入进行语义拆分与职责分流。首先由 Router 对用户请求进行分类和分解，然后将子查询并行分发给各自负责的专业 Agent，最后再将多个结果统一合成为一个对用户友好的响应。（多Agent并行）
	特点：
	1. Router 的**可选处理路径**通常是事先设计好的

==决策树==：
你的任务需要多 Agent 吗？
├─ 单一领域、工具 < 5 个、上下文 < 50K tokens
│  └─→ 不需要。用单 Agent + 好的 prompt 即可
│
├─ 单一领域、但工具 > 10 个
│  └─→ 考虑 Skills 模式（渐进式能力加载）
│
├─ 多领域、各领域需要独立上下文
│  └─→ 使用 Sub-Agents 模式
│
├─ 需要多步骤状态流转（如客服工单流程）
│  └─→ 使用 Handoffs 模式
│
└─ 需要跨多个数据源并行查询
   └─→ 使用 Router 模式

### ==从单一 Agent 到复杂智能体系统设计的一系列黄金法则==
1. 从**单 Agent** 开始 → 只在遇到明确瓶颈时才升级
2. 先加工具，再加 Agent → Tools 是最小的扩展单位（skills）
3. 选对模型 > 堆更多 token → 升级模型的效果超过翻倍预算
4. 上下文隔离是核心价值 → 多 Agent 的第一价值不是并行，是隔离
5. Token 成本要求高价值任务 → 不是所有场景都值得多 Agent
顺序：单一agent —> +skills —> + sub-Agents —> 使用混合架构
==新的启示==：不是说一开始就要使用agent。任何系统，无论输入或者输出多么混乱，必然有确定性的部分。所以，更好的建议是在worflow的节点中使用agent，而不是一上来就用复杂的agent实现

多agent架构的优点：
1. 避免上下文过多。导致模型能力下降和上下文污染
2. 限制agent使用工具的权限，减少幻觉
3. 利于任务拆解。不同的agent执行不同的任务
4. 容错高。一个agent出错，其他agent能够自主决策从而补全
5. 效果好。专业化分工

缺点：
1. 总成本高
2. 耗时长
3. 设计难度大。主要是多agent之间的分工和边界权衡问题。agent生成的内容会相互影响，所以上面提到的容错高存疑
