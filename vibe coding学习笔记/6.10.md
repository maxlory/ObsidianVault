State中是否需要添加新的字段：
1. 安全门禁：安全问题必须用代码强制执行。防止LLM被用户用prompt诱导绕过（不能只有LLM节点）
2. 由于几乎每一条新消息都是从 START 开始重新跑完整个 graph。为了避免关键字段被LLM重复查询，这种关键字段也需要在State中额外添加

之前的State / Node / Edge 三件套 + 模式表 解释了langgraph中的积木有哪些，但是没有解释这些积木是如何拼接在一起的，或者说为什么要拼接在一起

以下这些东西名字叫什么，起什么功能，放在什么位置，本身是什么东西；有没有哪种功能和某种模型是绑定的

Reducer（针对State中的字段合并规则）
它是什么: **State** 每个字段可以声明"新值来了怎么合并"——是覆盖还是追加。messages 用 add_messages 就是追加
决定了哪个模式能不能成立: Map-Reduce / 一切并行。两个 Node 并行写同一个字段，没有 reducer 直接报错——这是并行的隐藏前提
金融类比: 多部门同时给一张表填意见：必须事先约定是"各自追加一行"还是"后填的覆盖先填的"，否则打架

注意：Reducer分为覆盖和追加，默认是覆盖，追加需要另外申明
─────────────────────────────────────
Send API（动态分发）（这个不是很清楚，指定下一步edge不就能实现么，为什么要设立一个新的东西）
它是什么: 条件边可以返回一组 Send 对象，每个 Send 把一份子任务专属的小 State 发给同一个 Node 的一个并行副本
决定了哪个模式能不能成立: Map-Reduce 的本体。子任务数量运行时才知道（比如"分析 LLM 拆出来的 N 个议题"），普通边画不出来
金融类比: 把 10 份财报同时分给 10 个分析师，每人只拿到自己那份，不用看全卷宗

关于问题的解答：
1. edge是在构建graph的时候就定死了，必须提前确定有哪几条分支；但在 Map-Reduce 场景里，具体有哪几条分支是LLM临时生成的，事前无法确定
2. edge只能传全量State，即完整的State。而send可以发送部分内容，在 Map-Reduce 场景里，send可以控制发送给独立子任务的内容，避免多个字任务混淆
─────────────────────────────────────
Command（节点内路由）（这个不是很清楚，难道指定下一步去哪不是edge就能做到的么，为什么要单独设立一个节点）
它是什么: Node 的返回值可以同时做两件事：更新 State + 指定下一步去哪。等于把"做事"和"指路"合并在一个 Node 里
决定了哪个模式能不能成立: Multi-Agent handoff 的本体。agent A 决定"把任务交给 agent B"时，用 Command 一步完成移交
金融类比: 部门经理批完意见直接在表上写"转交风控部"，不用走

关于问题的解答：LLM驱动的路由用Commend，固定规则路由用Edge
1. edge需要在state中中转一遍。LLM在node中输出后，修改State中的字段，edge再根据State的字段进行判断；而Commend直接判断去哪个方向，避免了中转
2. edge无法实现跨子agent传递内容
─────────────────────────────────────
interrupt()（中断点））（实现人工介入的节点）
它是什么: Node 里调用 interrupt() → 整个图暂停并存档（靠 Checkpointer），人给了答复后从断点恢复，答复值注入回那个 Node
决定了哪个模式能不能成立: Human-in-the-Loop 的本体。没有 Checkpointer 就没有 HIL——暂停的状态没地方存
金融类比: 审批流转到"需董事会签字"就冻结归档，董事会签完字从冻结点继续，不用从头跑流程
─────────────────────────────────────
Checkpointer vs Store（短期记忆和长期记忆）
它是什么: Checkpointer = 单次对话内的记忆（thread 内每步快照）；Store = 跨对话的长期记忆（用户偏好、历史结论）
决定了哪个模式能不能成立: 决定 agent"记得住什么"。前沿 agent 标配两者都有
金融类比: 单笔交易的流水档案 vs 客户的长期信用档案
─────────────────────────────────────
recursion_limit（步数上限）（控制循环次数）
它是什么: 图的总步数兜底，超了直接抛错
决定了哪个模式能不能成立: 所有循环类模式（ReAct、Reflection）的保险丝
金融类比: 风控的单日交易次数上限——防程序化死循环
