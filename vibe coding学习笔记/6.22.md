
对于目前的AI来说，上下文就是一切。上下文能决定后续生成的内容。
现在的绝大多数工程化构建，都是在约束上下文对AI的影响
![[Pasted image 20260622161524.png]]
`CLAUDE.md` 是唯一一个「全程加载、全程占 token」的方法。你写的每一行，不管这次任务用不用得上，**都在消耗上下文窗口**
`Skills` 的设计很聪明：**只有名字和描述在启动时加载，完整内容等到被调用时才进上下文**。用完之后如果上下文满了，最旧的 skill 会被踢掉
`Subagents` 也是一种上下文注入，它是另起一个对话，在自己独立的上下文窗口里跑，跑完只把最终结果返回给主会话，所以从主会话角度来看，其上下文成本是零（**不占用主对话的上下文，所以不会对主对话产生影响**）
`Hooks` 完全绕过了上下文窗口。它是代码，由 harness 在外部执行（**不消耗上下文，代码自动执行**）

## CLAUDE.md
两种：项目根目录或任意子目录下的
特点：只要会话存在就读取，不会丢失；上下文压缩后重新读取，不会丢失（项目根目录）
有利有弊。既然CLAUDE.md必然占用会话上下文，那么其被执行得最彻底。但是如果过于膨胀会影响其效果，所以需要将不必要的内容放到Rules、Skills 这些按需加载的机制里

## Rules
定义：**给特定文件或目录设定的约束，可以做到「碰到这类文件才生效」**
是更精细的 `CLAUDE.md`：`CLAUDE.md` 是全局生效的，Rules 可以只在碰到特定路径的文件时才加载
重点：如果没有paths 前置字段，Rules会和`CLAUDE.md`一样开局即加载
对于我这种个人工作者来说，Rules没有什么意义
毕竟Rules的本质：**把“跨项目通用偏好”从每个** **`CLAUDE.md`** **中抽离出来，避免重复维护。**

## Skills
定义：不是提示词，但是可以作为上下文的一部分。特点是按需加载，这就对skill的name+description的要求很高，毕竟这是调用skill的根本。
在我看来，skill在未来相当长的一段时间中是使用agent的主流方式。因为其是对上下文管理的最小单元，而上下文管理是agent的核心
注意：上下文压缩后skill会被重新注入

## Hooks
定义：当遇到特定的问题，就自动执行。是触发脚本，不是LLM自己的判断
八种Hook 事件：
**PreToolUse**：工具执行前触发
**PostToolUse**：工具执行后触发
**PermissionRequest**：权限对话框弹出前触发
**SessionStart**：会话启动时触发
**PreCompact**：上下文压缩前触发
**Stop**：回复完成时触发
**SubagentStop**：subagent回复完成时触发
**UserPromptSubmit**：提交 prompt 时触发

## Subagents
特点：
	有独立上下文，返回最终摘要。对会话的上下文影响极低。
	可以有精确的工具权限控制。不同的subagent可以有不同的权限
我同样认为subagents是未来agent使用中的重点。有没有对可能会经常用到的subagents的管理
三个典型场景可以去尝试：深度搜索（大量中间结果不需要保留）、日志分析（翻几百行 log 找问题）、依赖审计（逐个检查库版本）

## Output Styles、System prompt、System Prompt Append
System prompt是Claude Code 底层规则，Output Styles是对System prompt的补充说明，尤其针对风格、人设方面

## 常见误区
「每次 X，必须做 Y」、「绝对不要做 Z」这些硬性约束写在CLAUDE.md
这些内容可以用hook实现，执行能力最强，token消耗最低
Rule 没加路径限定：没加路径限制的Rule和CLAUDE.md没什么区别

## Dynamic Workflows
定义：让 Claude 自己写编排脚本，协调多个 subagent 并行工作，解决复杂任务
避免偷懒：重复任务agent自动跳过
自我偏好：让agent自己审查自己，它倾向于没问题
目标漂移：真正有价值的内容经过飘逸后损失
