对钊哥给的AI产品技能全景文档的研究
一句话==核心==：<font color="#92d050">AI 产品和传统软件最大的不同，是输出从确定的，变成了概率的。</font>

### 一、拿到需求，先别想模型（拆解需求）（重点）
回答四个问题：
	这是什么<mark style="background:#d3f8b6">任务类型</mark>？输入输出的边界在哪？成功怎么量化？出错了谁来兜底？

拆解框架： ==IODEC==
输入（Input），结构化还是非结构化、质量如何。
输出（Output），要 JSON 还是自然语言、下游是人还是系统。
决策点（Decision），谁判断对错、置信度低走哪条路。
错误代价（Error），漏报和误报哪个更要命。
覆盖率（Coverage），有没有处理不了的样本，那些怎么路由出去。

几个反复踩的坑：
第一，把「AI 做 X」当成一个任务不拆。
第二，输出格式不定，模型吐自然语言，下游要 JSON，对不上。
第三，成功标准模糊，「让 AI 更准确」不是标准，「召回率不低于 95、精确率不低于 90、P95延迟不超过 2 秒」才是。
第四，忽略边界样本，语言混用、极短文本、空值，必须显式设计fallback。（要考虑到脏输入的可能性，并且通过显式设计fallback兜底异常情况）

==需求清单==：（可执行清单）
任务类型一句话： 用一句话说清楚 AI 干什么。不是"智能审批转账"这种含糊的，而是拆到不能再拆的单个任务。
输入 schema： 喂给模型的数据长什么样、有哪些字段。输入数据类型是什么
输出 schema： 模型吐出来的结果长什么样。同样要把字段、类型、可选值全部写死。
可量化的成功指标
出错的 fallback 路径：模型出错时怎么兜底。
样本覆盖范围：准备的样本覆盖了哪些情况。

### 二、prompt工程（重点）
==Prompt 工程==：不是「写一段话让 AI 听懂」，而是用结构化设计，把模型的歧义空间压到最小，让它在任何合理输入下，输出都可预测、可评估。（上下文工程的本质）

<font color="#92d050">好的Prompt应该包含什么</font>：
角色设定：告诉模型它是谁、能力边界（在这个角色里你只许做什么：防止模型产生幻觉、越权、跑偏等问题）在哪。
任务描述：用动词开头，说要做什么，而不是说不做什么。（最好是解释为什么这样做，而不是用绝对性的语言强制要求不做什么）
约束条件：字段定不下来就填 null 不要猜。（模型处理过程中必须遵守的行为准则）
输出格式：强制 JSON、字段类型枚举写死。（强制输出的数据类型）
少样本示例：给两到五个输入输出对校准预期。例子要覆盖正常单、边界单、还有该拒绝的单，模型才知道边界在哪。

<mark style="background:#d3f8b6">我的想法</mark>：我觉得真实的产品设计中，很难能够完全定下来约束条件和输出格式。因为用agent处理的一般都是多变的复杂任务，可能有很多不同的结果。这种设计可能更适合有固定规则的任务
而且以上内容都对一开始举的例子：智能审批转账，有强耦合性

<font color="#92d050">常用技巧：</font>
<u>让模型先在标签里想再给答案，这叫思维链，能提推理准确率</u>；（ "先在 thinking 标签里分析推理过程，再在 answer 标签里给出最终结论。"）
控制输出长度；
<u>信息不足时返回结构化的错误</u>；（避免错误答案模糊化，下游系统能够准确判断问题在哪里）
还有语言锁定，始终用中文回答

### 三、评估设计 Eval（重点）
指导思想：因为模型输出是概率的，「做了」不等于「对了」。记住这个顺序：先建 Eval，再改 Prompt，再上线

==具体评估指标搭建==：
评估指标分三层。
任务指标：看具体任务，**分类**看精确率（模型是否判断对了）、召回率（模型是否判断全了）、F1（平均分），抽取看字段级准确率，**摘要**看 ROUGE，**生成**只能人工打分。
系统指标：看延迟、Token 消耗、错误率（系统崩溃/报错的比例）、覆盖率（多少请求 AI 真的处理了）。
业务指标：看自动化率（多少任务完全不用人）、人工修改率（AI 给了结果但人改了多少）、采纳率（AI 的建议人接受了多少）、还有错误造成的真实损失。三层都要看，只看一层会骗自己。

==评估数据集==：
1. 每个任务类型至少一百到五百个样本
2. 人工标注，必须覆盖边界情况
3. 一旦建立就冻结——模型失败也不许改测试集，只能扩充
4. <mark style="background:#d3f8b6">做切片分析</mark>。平均数这种数据很容易骗人，所以需要深入挖掘数据，找到真正的高风险区
5. 专门准备对抗样本。测注入攻击（用户在正常输入里夹带"指令"，试图让 AI 忽略原本的规则、做它不该做的事），测分布外输入（AI 训练/测试时见过的数据长一个样，实际使用时来了一个画风完全不同的输入，AI 没见过这种东西），测边界条件（输入在技术上合法，但刚好卡在规则的边缘，最容易让 AI 判断出错的地方）
6. 没有自动指标的生成类任务，要做人工评估。定好评分维度和打分标准，至少两个人独立打分，kappa（只看超出随机一致的那部分评测）到 0.6 才算可接受，分歧样本交第三方仲裁
7. 把这些标准固化成自动化的评估流水线，配上质量门禁：F1 低于 0.9 阻断发布，P95（把所有请求按耗时从短到长排一队，排在第 95% 位置的那个值） 超 3 秒阻断

### 四、混淆矩阵（只是数据的解释）
**精确率**：模型说是的里面有多少真的是（在意误报，比如金融风控、垃圾邮件过滤）
**召回率**：总体说是的里面，模型说是的有多少（在意漏报，比如医疗诊断、安全检测）
**F1**：精确率和召回率的调和平均（两者同等重要时用，比如信息抽取）
陷阱：<font color="#92d050">类别不平衡</font>（检测例子多且正确率多，导致错误类型不明显）
一千笔申请里只有十笔违规，一个永远预测「合规」的模型，准确率高达 99%，看着漂亮，但违规召回率是 0，完全没用。所以类别不平衡时，别看准确率，看 F1、看AUC、分正负类单独统计。
ROUGE：判断摘要的指标。衡量生成文本和参考答案的词重叠情况，但它只看字面不看语义
AUC：衡量模型区分正负类的本质能力，不受阈值影响
统计显著性：测试集一百个，差异要 5% 以上才有意义。样本太少、提升太小，很可能只是噪声。（测试样本过少，提升如果不够多的话，可能只是噪声，而不是真的有提升）

### 五、·LLM 调用层（理解）
关于LLM：
1. 模型选择
2. max_tokens 控制输出上限防超长
3. temperature 控制随机性：抽取分类用 0 要确定、创意生成调高要多样（temperature在不同的情景下应该设置不同）

LLM的上下文管理：LLM 是无状态的，多轮对话每次都得把完整历史带上。所以要管理上下文：短对话全量带，长对话用滑动窗口，更长的用摘要压缩，RAG 场景按需检索（<u>在把问题发给模型之前，先帮它去知识库里"查资料"。查到的资料总结进prompt中发给模型</u>）。
LLM 是无状态的，多轮对话每次都得把完整历史带上：每次发新消息，程序把之前所有的对话记录全部打包，连同新消息一起重新发给模型（大模型每次都不记得之前的内容，都是将上下文打包后传给大模型，它才知道的）（难怪上下文越多，模型效果越差，消耗token越多）
==总结==：<mark style="background:#d3f8b6">所谓的上下文工程全部都是对输入模型的prompt进行优化。一旦prompt输入模型后就再也无法改变了。</mark>
不管是带对话历史、做摘要压缩、还是 RAG 检索——所有操作都发生在按下发送键之前，本质都是在精心组装这一次的 prompt 内容。
prompt 就是你和模型之间唯一的沟通通道，所有的上下文管理、格式约束、角色设定，最终都要变成 prompt 里的文字才能生效。

==Agent = 模型 + 工具 + 编排逻辑==
- 模型：负责想（判断下一步该干什么）
- 工具：负责做（查数据库、发邮件、算数）
- 编排逻辑：负责管（控制循环怎么转、最多跑几轮、什么时候停、出错了怎么办、要不要让人确认）

成本技巧：
1. 模型选择
2. <u>固定前缀用Prompt 缓存复用</u>：每次调用API 时，发给模型的 prompt 里其实有一大段是每次都一样的。例如角色设定、输出格式等。API 提供商支持缓存——如果你这次发的前缀跟上次一模一样，服务商直接复用上次已经处理过的部分，只处理新增的用户问题。重复部分的费用大幅降低。
3. <u>不要求实时的走批处理 API</u>，能省一半：正常调 API 是实时的。但是如果允许服务商安排在服务器空闲时处理任务，有折扣

### 六、RAG 架构
LLM的缺陷：训练数据有截止日期+训练数据有限，往往不能涵盖自己需要的数据

==构建RAG的流程==：
1. 文档切片。固定长度简单但可能切断语义，按段落切保留语义。
   关键参数：<u>每块五百到一千 token，相邻块重叠一到两成防止边界信息丢，每块再附上来源、页码、章节等元数据</u>。
2. 向量化。把文本变成高维向量，语义相近的向量距离也近。
   <u>中文场景一定要用中文优化过的模型</u>，比如 <font color="#92d050">bge-m3</font>（中文表现好的多语言 embedding 模型），别拿英文模型硬套。
3. 存进向量数据库。<u>小原型用 Chroma，中大型用 Qdrant 或 Weaviate，已经有PostgreSQL 的直接上 pgvector</u>。检索方式上，纯向量适合语义、全文适合关键词，两者加权的混合检索效果最好。
4. 精排，Rerank。<u>先粗检召回 Top-20，再用一个更精准的交叉编码模型重新排序，取Top-5</u>。它同时看问题和文档，精度高，还能大幅减少注入上下文的 token 量。
   粗检找出相关的20条（速度快），对这20条用交叉编码模型（把问题和文档拼在一起喂进模型，模型能逐字对照"这个问题到底跟这段文档有多相关"）重新排序，找出最相关的5条（准度高）
5. Context 注入。<u>把检索结果拼进 Prompt，明确告诉模型「只基于提供的文档回答，文档里没有就说无法回答」</u>。这样答案才有据可循。

是否需要微调：
知识频繁更新、需要引用来源、私有文档量大，用 RAG；
只是要<font color="#92d050">固定的输出风格，那才考虑微调</font>。


### 七、Agent 框架
==Agent = 模型 + 工具 + 编排逻辑==
- 模型：负责想（判断下一步该干什么）
- 工具：负责做（查数据库、发邮件、算数）
- 编排逻辑：负责管（控制循环怎么转、最多跑几轮、什么时候停、出错了怎么办、要不要让人确认）

核心循环叫 ReAct，推理加行动
模型根据现有的工具，决定调用什么工具，得到什么结果，根据结果再思考用什么工具，循环往复

工具设计的好坏决定Agent获取的信息，决定Agent的表现。
<font color="#92d050">好的工具具有5个特征</font>：
单一职责、描述精准（最重要，是模型调用工具的唯一依据）、参数明确、幂等、错误信息清晰

Agent的设计重点：
1. 设最大步骤数，比如十步，防止无限循环
2. 高风险操作，执行前必须有人工确认
3. 防止幻觉工具调用，调了不存在的工具或瞎填参数
4. 无限循环，反复调同一个
5. 过度自信，信息不够还硬下判断
6. 目标漂移，执行着执行着偏离了初衷
