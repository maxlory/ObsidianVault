==Sub-Agent的编排==
优势：subagent可自己设计；subagent的权限是固定的，不会越过边界；使用子代理能够保证上下文干净；不同自代理的上下文不会互相污染
限制：子代理不能生成子代理——>子代理之间不能互相调用——>子代理的编排只能由主对话实现

<font color="#92d050">为什么这样设计</font>：
1. 主对话拥有全局视野：主对话可以看到每个阶段的输出，从而在关键节点做出判断：继续、重试还是终止
2. 权限隔离：每个子代理智能只有自己配置的工具权限，不能通过嵌套调用绕过限制
3. 调试容易：出了问题能够精确定位到具体节点，而不会出现错误的嵌套

<font color="#92d050">Resume 恢复机制</font>
定义：每个子代理执行完后都有一个 agent ID，可以用这个 ID 恢复它的完整上下文
重点：
1. 已经跑完的子代理的内容会保留在主对话中
2. 中断的子代理的恢复有两种选择：
	1. 接着 Fixer 断点继续
	2. 重新开始一个 Fixer

<mark style="background:#d3f8b6">如何实现</mark>：
1. 自然语言调用
2. @-mention（子代理名字）
3. 手动输入ID


多子代理流水线的核心工程问题——==交接契约==
交接契约是什么：每个阶段的输出格式中，应该有一个明确的  Handoff（交接）  部分。简单来说，就是要对每个子代理的输入、输出内容进行强制规范
<mark style="background:#d3f8b6">怎么做</mark>：
1. 在子代理的prompt中将输出入的格式强调清楚
2. 使用hooks约束（hook也能在子代理中使用。使用方法是写在frontmatter中/写在settings.json中）
3. 写入workflow的schema中

==主对话编排的四种介入形式==——全自动、关键阶段审批、逐阶段审批和回退重试四种介入形式
1. 全自动：所有节点、链接自动实现
2. 关键阶段审批：关键节点人工介入审批
	重点：关键节点是什么？——权限的变动：从只读到读写的跨越
3. 逐阶段审批：每个链接都人工介入
4. 回退重试：遇到问题时回退到上一个子代理

如何实现编排：
1. 自然语言
2. Hooks审批
3.  Workflow 分阶段

==系统提示词指示 LLM 严格遵循 `Thought → Action → Observation` 格式==，而基于正则表达式的解析器将 LLM 的文本输出桥接到实际的 Python 函数调用。
在“Reason”阶段，LLM 对当前状态进行深思熟虑并规划下一步（深思式）。在“Act & Observe”阶段，它执行工具调用并立即接收环境反馈（反应式）。
