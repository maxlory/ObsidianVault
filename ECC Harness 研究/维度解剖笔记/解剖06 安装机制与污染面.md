# ECC 安装机制与污染面（维度 06）

> 研究对象：`/Users/aa00158/harness-research/ECC`（只读浅克隆，commit `e4e4163`）
> 结论目标：给出"如何在完全不污染现有 ~/.claude 的前提下试用 ECC"的确切答案。
> 证据纪律：每条论断后标 `路径:行号`。无法核实的标"未验证"。

## 0. 一句话结论（TL;DR）

**ECC 的 `install.sh --target claude` 会往 `~/.claude/` 直接倾倒 460~983 个文件**（取决于 profile），
其中 **skills 是平铺写进 `~/.claude/skills/<skill-name>/`——和你 79 个自建 skill 同一个命名空间**。
好消息有三条：
1. **installer 从不碰 `settings.json`**（全仓库 grep 无任何 settings.json 写入代码；README.md:407 也明说 "leaves any existing `~/.claude/settings.json` untouched"）；
2. **同名 skill 目录已存在时会跳过而不是覆盖**（`scripts/lib/install/claude-skill-migration.js:273-283`），这是唯一一处真正的"保护用户文件"逻辑；
3. `--dry-run` 经代码核实**确实 0 写盘**。

坏消息也有三条：
1. 这个"跳过保护"**只对 `skills/` 生效**，`agents/`（67 个 .md）、`commands/`（94 个）、`rules/ecc/`、以及 6 个直接落在 `~/.claude/` 根目录的文件（含 `README.md`、`AGENTS.md`、`plugin.json`）**全部是无条件 `fs.copyFileSync` 覆盖**；
2. 卸载只删 install-state 里登记过的文件，**"因冲突被跳过"的文件不会被登记，但被覆盖的文件也不会被恢复**——没有备份机制；
3. 用户 `~/.claude/agents/` 的 3 个自建 agent 只要**重名**就会被静默覆盖，且不可恢复。

**最安全的试用路径**：`--target claude-project` 装到一个空目录（如 `~/ecc-trial/.claude/`），全程不碰 `~/.claude`。
详见 §12。

## 1. 安装体系的整体骨架：谁调用谁

### 1.1 调用链（从命令行到写盘）

```
install.sh (32 行 bash wrapper)
  └─ exec node scripts/install-apply.js "$@"        install.sh:32
       ├─ parseInstallArgs()                        scripts/lib/install/request.js
       ├─ createInstallPlanFromRequest()            scripts/lib/install/runtime.js
       │    └─ createManifestInstallPlan()          scripts/lib/install-executor.js:722
       │         ├─ resolveInstallPlan()            scripts/lib/install-manifests.js:521  ← 读 3 个 manifest
       │         │    └─ planInstallTargetScaffold()  scripts/lib/install-targets/registry.js:47
       │         │         └─ adapter.planOperations()  ← 产出"目录级"操作
       │         └─ materializeScaffoldOperation()  scripts/lib/install-executor.js:642
       │              └─ 把目录级操作展开成一个个 copy-file  ← 这一步才知道真实文件数
       ├─ [--dry-run] previewInstallPlan()          scripts/lib/install/apply.js:147   ← 只读
       └─ [默认]      applyInstallPlan()            scripts/lib/install/apply.js:163   ← 真写盘
```

白话解释几个术语：

- **manifest（清单文件）**：三个 JSON，放在 `manifests/`。它们是"配方表"，描述"哪个模块包含哪些源目录"，安装器读它决定要拷什么。
- **module（模块）**：配方表里的最小单位，例如 `agents-core` 对应源目录 `agents/`。定义在 `manifests/install-modules.json`。
- **profile（预设）**：module 的打包组合，例如 `full` = 25 个 module。定义在 `manifests/install-profiles.json`。
- **component（组件）**：给人用的选择面，`--with` / `--without` 的参数。定义在 `manifests/install-components.json`，一个 component 映射到若干 module。
- **target（目标）**：装到哪个 harness（Claude Code / Cursor / Codex …），每个 target 有一个 **adapter（适配器）**，负责把源路径翻译成目标绝对路径。代码在 `scripts/lib/install-targets/`。
- **operation（操作）**：一条"从 A 拷到 B"的记录，是最终写盘和卸载的账本单位。

### 1.2 两层 operation 的区别（容易被 install-plan.js 的输出骗到）

`install-plan.js --profile full --target claude` 报的是 **301 个 operation**，但真实落盘是 **983 个文件**。
原因是 adapter 产出的是 `kind: 'copy-path'` 的**目录级**操作（`scripts/lib/install-targets/helpers.js:88-108`，
`scaffoldOnly: true`），要等 `materializeScaffoldOperation()`（`scripts/lib/install-executor.js:642-694`）
递归展开目录后，才变成 `kind: 'copy-file'` 的逐文件操作。

> 🔑 **install-plan.js 的输出会低估污染量 3 倍多**。想看真实文件数只能看 install-apply.js 的 dry-run，或自己调 `createManifestInstallPlan()`。
> 而且 `install-plan.js` 自己在 printPlan 里就承认了这点：
> `scripts/install-plan.js:153` —— "target filtering and operation output currently reflect scaffold-level adapter planning, not a byte-for-byte mirror of legacy install.sh copy paths."

### 1.3 三种安装模式（mode）

代码里同时存在三条路（`scripts/install-apply.js:163` → `scripts/lib/install/runtime.js`）：

| mode | 触发方式 | 说明 |
|---|---|---|
| `legacy` | `install.sh python typescript`（裸语言名，无 `--profile`） | 只拷 `rules/<language>/` 到 `~/.claude/rules/ecc/`，最小面。代码 `install-executor.js:539-606` |
| `legacy-compat` | 语言名 + `--with` 之类混用 | 把语言映射到 module 再走 manifest 路。`install-executor.js:608-640` |
| `manifest` | `--profile` / `--modules` / `--skills` | 主流路径，本笔记默认讨论这条 |

`legacy` 模式的污染面小得多——只写 `~/.claude/rules/ecc/common/` + `~/.claude/rules/ecc/<lang>/`
（`install-executor.js:305-355`），不碰 skills / agents / commands。这是一个被 README 冷落但对"低污染试用"很有用的口子（见 §12 路径 D）。

`.claude-plugin/` 之所以被摊平到 `~/.claude/` 根目录，是因为 adapter 把它声明成了 `nativeRootRelativePath`

### 3.3 路径重映射规则（source → destination）

| `rules/...` | `~/.claude/rules/ecc/...` | **加了 `ecc/` 命名空间** |

注释和代码都显示：skills 曾经装在 `skills/ecc/<name>/`（nested，旧版），**现在改成平铺 `skills/<name>/`**，
并有专门的迁移代码把旧的 nested 副本删掉（`claude-skill-migration.js:399-409`）。
这个"平铺化"决定就是和用户自建 skill 撞车的直接原因。

## 4. claude vs claude-project 的差异

**结论：`claude-project` 确实只写当前工作目录的 `.claude/`，代码级可确认。**

两个 adapter 文件（`claude-home.js` / `claude-project.js`）内容几乎逐行相同，只差三处：

| 字段 | claude-home.js | claude-project.js |
|---|---|---|
| `id` | `'claude-home'` (:49) | `'claude-project'` (:49) |
| `target` | `'claude'` (:50) | `'claude-project'` (:50) |
| `kind` | `'home'` (:51) | **`'project'`** (:51) |

`rootSegments` 两者都是 `['.claude']`（`claude-home.js:52` / `claude-project.js:52`），
`installStatePathSegments` 都是 `['ecc','install-state.json']`（:53）。

差异全部由 `kind` 驱动，落到 `helpers.js:39-53` 的 `resolveBaseRoot()`：

```js
if (scope === 'home')    return input.homeDir || os.homedir();
if (scope === 'project') { const projectRoot = input.projectRoot || input.repoRoot; ... return projectRoot; }
```

而 `projectRoot` 由 `scripts/install-apply.js:165` 传入 `process.cwd()`。

> ✅ **所以 `cd /tmp/ecc-trial && bash /path/to/ECC/install.sh --target claude-project --profile full`
> 的全部写盘范围就是 `/tmp/ecc-trial/.claude/`，一个字节都不会进 `~/.claude/`。**
> 这是代码层面确认的，不是文档承诺。

**唯一一处 claude-project 特有的小差别**：`claude-project.js:68` 过滤外部平台路径时传的是硬编码字符串 `'claude'`
（`isForeignPlatformPath(p, 'claude')`），而 claude-home 传的是 `adapter.target`（`claude-home.js:68`）。
效果是 claude-project 也把 `.claude-plugin/` 当成"自己人"（因为 `PLATFORM_SOURCE_PATH_OWNERS['.claude-plugin'] = 'claude'`，
`helpers.js:6`）。若不这么写，claude-project 会漏掉 `.claude-plugin/` 那 4 个根文件。属于有意为之，不是 bug。

**一个副作用需要注意**：Claude Code 读项目级 `.claude/` 是有的（skills/agents/commands 项目级都支持），
所以装到 `$CWD/.claude/` 之后，**只要你在那个目录下开 Claude Code，ECC 的 281 个 skill 就都生效**——
隔离的是文件，不是行为。这正好是"试用"想要的效果。

## 5. --dry-run 到底做什么（控制流核实）

**结论：`--dry-run` 100% 不写盘，代码级确认。**

控制流（`scripts/install-apply.js:169-183`）：

```js
if (options.dryRun) {
  const plan = previewInstallPlan(rawPlan);      // :170
  ... console.log(...)                           // :172 / :174
  return;                                        // :176  ← 直接返回，永不到达 applyInstallPlan
}
const result = applyInstallPlan(rawPlan);        // :179  ← 只有非 dry-run 才走到
```

`return` 在 `applyInstallPlan` 之前，没有任何 fallthrough。

`previewInstallPlan`（`scripts/lib/install/apply.js:147-161`）的全部工作是：
1. 调 `prepareClaudeSkillMigration(plan)`；
2. 拼一个对象返回，字段 `applied: false`。
**函数体内无任何 `fs.write*` / `fs.copyFile*` / `fs.mkdir*` 调用**（对照第 163 行开始的 `applyInstallPlan`，
那里有 `fs.mkdirSync`(:185, :239)、`fs.writeFileSync`(:207, :214, :231, :240)、`fs.copyFileSync`(:235)）。

`prepareClaudeSkillMigration`（`claude-skill-migration.js:354-383`）也只做读：
`pathExists()` → `fs.lstatSync`（:13）、`readInstallState()` → `fs.readFileSync`（`install-state.js:22`）、
`fs.readdirSync`。**没有写。**

上游的 plan 构造同样只读：
- `getPackageVersion` / `getManifestVersion`：`fs.readFileSync`（`install-executor.js:21, 30`）
- `getRepoCommit`：`execFileSync('git', ['rev-parse','HEAD'])`（`install-executor.js:39-44`）——只读 git 命令
- `materializeScaffoldOperation`：`fs.existsSync` / `statSync` / `readdirSync`（`install-executor.js:658-693`）
- `createInstallState`：纯内存对象构造 + 校验（`install-state.js:230-280`），**注意它不调 `writeInstallState`**

> 🔑 唯一的写盘函数是 `writeInstallState()`（`install-state.js:288-293`，含 `fs.mkdirSync` + `fs.writeFileSync`），
> 它只被 `applyInstallPlan` 调用（`apply.js:180` 和 `apply.js:250`）。dry-run 路径引用不到它。

**残余风险（低，~15%）**：`install.sh` 在 `node_modules` 不存在时会先跑 `npm install`（`install.sh:18-21`），
这会写 `<ECC仓库>/node_modules/` 和可能的 lockfile。**这发生在参数解析之前，`--dry-run` 拦不住它**。
本次研究环境 node_modules 已存在，所以这条不会触发；但在干净克隆上 `install.sh --dry-run` 仍会 npm install。
规避：直接 `node scripts/install-apply.js --dry-run ...`，绕开 bash wrapper。

## 6. install-plan.js 是否完全不写盘

**结论：完全不写盘。**

`scripts/install-plan.js` 全文 276 行，`require` 的只有三个模块（:6-16）：
`./lib/install-manifests`、`./lib/install/config`、`./lib/install/request`。

## 7. install-state：卸载账本记在哪、记了什么

### 7.1 落点

- `--target claude` → **`~/.claude/ecc/install-state.json`**（`claude-home.js:53`）
- `--target claude-project` → **`$CWD/.claude/ecc/install-state.json`**（`claude-project.js:53`）
- 其余 target → `<root>/ecc-install-state.json`（例如 `~/.codex/ecc-install-state.json`）

写入函数只有一个：`writeInstallState()`（`scripts/lib/install-state.js:288-293`），
被 `applyInstallPlan` 调用两次（`scripts/lib/install/apply.js:180` bridge state，`:250` final state）。

### 7.2 格式（schema `ecc.install.v1`）

权威定义在 `schemas/install-state.schema.json`，代码里另有一份**手写的、不依赖任何 npm 包**的等价校验器
（`scripts/lib/install-state.js:37-206`；文件头注释 :4-9 解释了原因：企业供应链审计要求"审过的字节就是装上的字节"，
所以 installer 闭包不 require 任何非内置包）。

顶层字段（`install-state.js:88`）：

| 字段 | 含义 |
|---|---|
| `schemaVersion` | 固定 `"ecc.install.v1"` |
| `installedAt` | ISO 时间戳 |
| `lastValidatedAt` | 可选，doctor 跑过后写 |
| `target` | `{ id, target, kind, root, installStatePath }` —— 例如 `{id:"claude-home", kind:"home", root:"/Users/x/.claude"}` |
| `request` | `{ profile, modules[], includeComponents[], excludeComponents[], legacyLanguages[], legacyMode }` —— 复现安装命令用 |
| `resolution` | `{ selectedModules[], skippedModules[] }` |
| `source` | `{ repoVersion, repoCommit, manifestVersion }` —— repoCommit 来自 `git rev-parse HEAD`（`install-executor.js:39`） |
| `operations` | **卸载账本本体**，一条一个文件 |

每条 operation（schema :169-206 / `install-state.js:177-197`）：

```json
{
  "kind": "copy-file",
  "moduleId": "agents-core",
  "sourceRelativePath": "agents/planner.md",
  "destinationPath": "/Users/x/.claude/agents/planner.md",
  "strategy": "preserve-relative-path",
  "ownership": "managed",
  "scaffoldOnly": false
}
```

`full` profile 下这个数组有 **983 条**，文件本身大约几百 KB。

### 7.3 一个反直觉的设计：install-state 不记录"被覆盖前是什么"

schema 里没有任何 `previousContent` / `previousJson` 之类的备份字段（`schemas/install-state.schema.json:164-208`，
`additionalProperties: true` 允许有，但 `createInstallState()` 从不写入）。

有意思的是**卸载代码却会去读这两个字段**：
`getOperationPreviousContent(operation)` / `getOperationPreviousJson(operation)`
（`install-lifecycle.js:672, 681, 710, 719, 770, 779`）。
也就是说卸载器**准备好了"恢复原内容"的能力，但安装器从不填这些数据**（至少 `copy-file` 这条路径不填）。

> ⚠️ **净效果：被 ECC 覆盖的用户文件（agents/、commands/、根目录 README.md 等）在卸载时是"删掉"而不是"还原"。**
> 因为 `executeUninstallOperation` 对 `kind === 'copy-file'` 只有一条分支：`removeContainedPath(..., {force:true})`
> （`install-lifecycle.js:651-668`），没有 previousContent 分支。

## 8. 卸载机制与回滚干净度

### 8.1 命令

```bash
# 官方推荐（README.md:525-535）
node scripts/ecc.js uninstall --dry-run
node scripts/uninstall.js --dry-run     # 直接调用
node scripts/uninstall.js               # 真删
node scripts/uninstall.js --target claude   # 限定单个 target
```

`scripts/uninstall.js:76-81` 把 `homeDir = process.env.HOME || os.homedir()`、`projectRoot = process.cwd()`
传给 `uninstallInstalledStates()`（`install-lifecycle.js:1665`）。

### 8.2 卸载算法

1. `discoverInstalledStates()`（`install-lifecycle.js:1081-1092`）→ 对每个 target 算出 install-state 路径，
   过滤掉不存在的（`:1670` `.filter(record => record.exists)`）。
2. `getManagedOperations(state)`（`install-lifecycle.js:81-83`）——**只取 `ownership === 'managed'` 的 operation**。
3. 逐条 `executeUninstallOperation(operation, record.targetRoot)`（`:1707`）。
4. 删 install-state 文件本身（`:1712-1717`）。
5. `cleanupEmptyParentDirs()`（`:1628-1663`）——自底向上删空目录，遇到非空/符号链接就停。

安全约束：所有删除都过 `removeContainedPath(path, trustedRoot, ...)`，把删除限制在 targetRoot 内
（代码注释 `install-lifecycle.js:650` 引用了 CVE 编号 **GHSA-hfpv-w6mp-5g95**，说明历史上出过"删到 root 外面"的洞）。

### 8.3 ⚠️ 不带 `--target` 会扫全部 14 个 target

`normalizeTargets()`（`install-lifecycle.js:29-32`）：

```js
if (!Array.isArray(targets) || targets.length === 0) {
  return listInstallTargetAdapters().map(adapter => adapter.target);   // 全部 14 个
}
```

所以 `node scripts/uninstall.js` 会同时检查
`~/.claude`、`~/.codex`、`~/.hermes`、`~/.opencode`、`~/.openclaw`、`~/.qwen`
**加上** `$CWD/.cursor`、`$CWD/.agent`、`$CWD/.gemini`、`$CWD/.zed`、`$CWD/.kimi`、`$CWD/.codebuddy`、
`$CWD/.joycode`、`$CWD/.claude`。
只要哪个目录里有 ECC 的 install-state，就一起卸。**在错误的 cwd 下跑卸载会连带清掉别的项目级安装**——
先跑 `--dry-run` 看 `plannedRemovals` 再动手。

### 8.4 能不能干净回滚？分三种情况

| 情况 | 卸载后 | 干净度 |
|---|---|---|
| ECC 新建的文件（`~/.claude/agents/planner.md` 等原本不存在的） | 删除 + 清空父目录 | ✅ 干净 |
| ECC 覆盖了你的同名文件（`~/.claude/agents/code-reviewer.md` 你自己也有一个） | **删除，不还原**（`install-lifecycle.js:651-668`） | ❌ **你的文件永久丢失** |
| 冲突被跳过的 skill 目录 | 不在 operations 里 → 不动 | ✅ 你的文件安全 |

### 8.5 已知残留

1. **`~/.claude/hooks/hooks.json` 的路径改写版本**。
   `applyInstallPlan` 在拷完所有文件后，额外写了一次 `hooks/hooks.json`（`apply.js:238-245`），
   内容是把 `${CLAUDE_PLUGIN_ROOT}` 占位符替换成绝对路径后的版本。
   这个 **"额外写"没有对应的 operation 记录**（它是在 operations 循环之外做的），
   但 `hooks/hooks.json` 本身作为一个 copy-file operation 已经在账本里，所以文件会被删掉。
   ✅ 实际不残留，但设计上有隐患：如果哪天源里没有这个 copy-file operation，这个文件就会孤儿化。
2. **merge-json 目标**（例如 cursor 的 `mcp.json`）卸载时走 `deepRemoveJsonSubset`（`install-lifecycle.js:748`），
   把 ECC 加的键从你的配置里减掉，保留你自己的键。这条设计得不错，但**只对 `merge-json` 类操作有效**，
   claude target 下几乎全是 `copy-file`。
3. **`npm install` 装进 ECC 仓库的 `node_modules/`** 不属于 install-state，卸载不管，需要手动删仓库。
4. **Claude Code 自己的运行时状态**（`~/.claude.json` 里的 MCP 开关、plugin 启用状态）不在 install-state 里。
   走 `/plugin install` 路线时，ECC 的启用记录写在 `~/.claude/settings.json` 的 `enabledPlugins`
   （README.md:170-183 给出的正是这个 JSON 结构）+ Claude Code 的 plugin cache，
   **`scripts/uninstall.js` 完全不管这些**——README.md:538 也承认："Plugin users should remove the plugin from Claude Code"（要手动）。

## 9. 冲突处理：ownership / managed vs user-owned / 覆盖策略

### 9.1 `ownership` 字段其实只有一个值

全仓库 grep（排除 node_modules / .git）显示：**`ownership` 被赋值的地方只有 `'managed'`，从来没有 `'user-owned'`**。

| 位置 | 值 |
|---|---|
| `scripts/lib/install-executor.js:139` | `ownership: 'managed'` |
| `scripts/lib/install-executor.js:262` | `ownership: 'managed'` |
| `scripts/lib/install-executor.js:651` | `operation.ownership \|\| 'managed'` |
| `scripts/lib/install-targets/helpers.js:94` | 默认参数 `ownership = 'managed'` |
| `scripts/lib/install-targets/helpers.js:141` | `options.ownership \|\| 'managed'` |
| `scripts/lib/install-targets/cursor-project.js:50` | `ownership: 'managed'` |

而 `'user-owned'` 这个字符串**只出现在警告文案和测试里**
（`claude-skill-migration.js:229, 236` 是文案；`tests/scripts/install-apply.test.js:471` 等是断言）。

> 🔑 **正确的心智模型**：`ownership: 'managed'` = "这条记录进了 install-state，ECC 认领它，卸载时会删"。
> "user-owned" 不是一个字段值，而是一个**推断出来的状态**：文件存在于磁盘上、但不在 install-state 的 operations 数组里
> → 就算 user-owned。判定逻辑在 `claude-skill-migration.js:273`：
> `if (pathExists(flatSkillRoot) && !hasManagedFlatFile)`。

消费端只有一处：`getManagedOperations()`（`install-lifecycle.js:81-83`）用它过滤卸载/修复的范围。

### 9.2 遇到同名已存在文件：**只有 skills 会保留，其余全覆盖**

这是本维度最重要的结论。

#### (a) skills/ —— 有保护

保护逻辑全在 `scripts/lib/install/claude-skill-migration.js`，且**只对 target `claude` / `claude-project` 生效**
（`:9` `CLAUDE_TARGETS = new Set(['claude','claude-project'])`，`:355-358` 非 Claude target 直接 `createDisabledMigration`）。

两级判定（`classifySkillGroup`，`:265-299`）：

1. **目录级**：`~/.claude/skills/<name>/` 已存在，且该 skill 的任何文件都不在 install-state 里
   → 整个 skill 的所有操作被移出 `appliedOperations`，打印警告
   （`:273-283`，文案见 `:225-230`：`Skipped Claude skill '<name>' at <path>: the flat skill directory is user-owned because it is not recorded in ECC install-state.`）
2. **文件级**：目录是 ECC 管的，但里面某个文件不在账本里 → 单文件跳过
   （`:285-298`，文案 `:232-237`）

跳过的操作最终不会写进 `finalState.operations`（`:334-339` 用 `skippedDestinations` 过滤），
所以**卸载时也不会误删你的 skill**。这套设计是对的。

#### (b) agents/ commands/ rules/ecc/ scripts/ hooks/ 根目录文件 —— 无保护，直接覆盖

`applyInstallPlan` 的主循环（`scripts/lib/install/apply.js:183-236`）对非 skill 路径没有任何"目标已存在"检查：

```js
for (const operation of appliedPlan.operations) {
  assertSafeClaudeSkillOperation(appliedPlan, operation);   // :184 只查符号链接逃逸，不查存在性
  fs.mkdirSync(path.dirname(operation.destinationPath), { recursive: true });   // :185
  ...
  fs.copyFileSync(operation.sourcePath, operation.destinationPath);             // :235  ← 无条件覆盖
}
```

`assertSafeClaudeSkillOperation`（`claude-skill-migration.js:115-129`）第一件事就是
`if (!CLAUDE_TARGETS.has(target)) return;`，第二件事是
`if (!descriptor || !samePath(...flatDestinationPath)) return;` ——
**只要目标路径不是 `<root>/skills/<name>/...` 就直接放行**，连符号链接检查都不做。

> ⚠️ **所以 `~/.claude/commands/learn.md`、`~/.claude/agents/<同名>.md`、`~/.claude/README.md`
> 只要重名就是 `fs.copyFileSync` 静默覆盖，没有警告、没有备份、卸载也不还原。**

#### (c) 目录级警告只在 legacy 模式有

`isDirectoryNonEmpty(rulesDir)` → `warnings.push('Destination ... already exists and files may be overwritten')`
（`install-executor.js:313-315`），但这条只在 **legacy 模式**（裸语言名安装）里，
manifest 模式（`--profile`）根本不调用 `planClaudeStyleLegacyInstall`，所以**看不到这条警告**。

### 9.3 README 提到的 "conflict warning" 在哪

README.md:301：
> "If a flat skill directory is user-owned, ECC preserves it, prints a conflict warning, and keeps any older managed copy tracked for a safe uninstall instead of overwriting user files."

对应代码：`scripts/lib/install/claude-skill-migration.js:225-237`（生成文案）
+ `scripts/lib/install/apply.js:155-158`（塞进 `plan.warnings`）
+ `scripts/install-apply.js:110-115`（打印到 stdout）。

**这段 README 描述是准确的，但它只讲 skills**。README 全文没有一处说明 agents/commands 会被覆盖。
把 README.md:301 当成"ECC 不会覆盖我的文件"的通用承诺，会踩坑。

### 9.4 一个值得表扬的细节：bridge state

`applyInstallPlan:176-181` 在**第一个文件写入之前**先写一次 install-state（bridge state），
把即将写的所有操作提前认领。目的（代码注释 `:177-180`）：如果安装中途崩了，
下次卸载能清掉这批半成品，而不会因为"没记账"把它们误判成 user-owned 而留下垃圾。
这是个成熟的工程细节。

## 10. settings.json 会被怎么改（合并还是覆盖）

### 10.1 结论：**installer 完全不碰 settings.json**

证据（三重）：

1. **grep 无命中**：`grep -rn "settings.json" scripts/lib/install*.js scripts/lib/install/ scripts/lib/install-targets/ manifests/ install.sh install.ps1` → 0 结果。
2. **写盘点只有 5 处**，全部在 `scripts/lib/install/apply.js`，目标由 operation 决定：
   - `:207` merge-json 的目标（claude target 下没有这类操作）
   - `:214` MCP 配置过滤后写
   - `:231` markdown 链接改写后写
   - `:235` `fs.copyFileSync` 普通拷贝
   - `:240` **`hooks/hooks.json`** —— 唯一一个"额外生成"的文件
   加上 `install-state.js:291` 写 install-state。**没有任何一处指向 settings.json**。
3. **README 明说**：README.md:407 —— "That writes resolved hooks to `~/.claude/hooks/hooks.json`
   and **leaves any existing `~/.claude/settings.json` untouched**."

> ✅ **对用户的直接意义：你 `~/.claude/settings.json` 里的自建 hooks 和 permissions，
> 走 `install.sh` 路线是 100% 安全的。既不合并也不覆盖。**

### 10.2 那 hook 怎么生效？—— 一个隐含的坑

`applyInstallPlan:238-245` 会额外生成一份 `~/.claude/hooks/hooks.json`，
把源文件里的 `${CLAUDE_PLUGIN_ROOT}` 占位符替换成真实绝对路径
（`replacePluginRootPlaceholders`，`apply.js:85-108`；`pluginRoot = plan.targetRoot`，即 `~/.claude`）。

**但 Claude Code 并不会自动加载 `~/.claude/hooks/hooks.json`**——它只读 `settings.json` 里的 hooks 配置，
或者 plugin 目录下的 `hooks/hooks.json`。README.md:409 自己承认了这点：
"Claude Code v2.1+ already auto-loads **plugin** `hooks/hooks.json`"（强调 plugin）。

推论（置信度 中 ~65%，可自行验证）：**走 `install.sh` 手动安装路线，ECC 的 hook 装了但不会自动跑**，
除非你手动把 `~/.claude/hooks/hooks.json` 的内容抄进 `settings.json`——而 README.md:401 又明确劝阻这么做。
文档在这里是自相矛盾的，未在代码中找到自动接线的实现。
> 👉 验证动作：装到隔离目录后，`cat <隔离目录>/.claude/hooks/hooks.json`，
> 再对照 `~/.claude/settings.json` 是否出现同名 hook —— 如果没有，就是不生效。

### 10.3 走 plugin 路线才会动 settings.json，而且是你自己动手

README.md:166-186 给的"declarative"方案是让**你自己**往 `~/.claude/settings.json` 加：

```json
{
  "extraKnownMarketplaces": { "ecc": { "source": { "source": "github", "repo": "affaan-m/ECC" } } },
  "enabledPlugins": { "ecc@ecc": true }
}
```

这是手工编辑，不是 installer 行为。`/plugin marketplace add` + `/plugin install ecc@ecc`
则由 Claude Code 自己维护这两个键——**这条路径的写入者是 Claude Code，不是 ECC**，
所以它对 settings.json 的修改是"加键"而非"覆盖文件"，你的 hooks/permissions 同样安全。

plugin 元数据：`.claude-plugin/marketplace.json:12-15`（`name: ecc`, `source: ./`, `version: 2.1.0`）。

### 11.4 一个容易忽略的间接冲突：触发面污染

你精心调过触发词的 79 个 skill 会和 ECC 的 280 个抢触发。
这不是"污染文件系统"，是"污染你的 agent 行为"——而且**卸载能还原文件，还原不了你重新调触发词的工时**。

> 🤔 这是我认为"绝对不要装进 `~/.claude`"的头号理由，比文件覆盖更严重。

## 12. "只试用不污染"的可行路径逐条评估

按"隔离度 × 可用性"排序，**推荐 A 或 B**。

### 路径 A ⭐推荐：`--target claude-project` 装到一个空目录

```bash
mkdir -p ~/ecc-trial && cd ~/ecc-trial
node /Users/aa00158/harness-research/ECC/scripts/install-apply.js \
  --target claude-project --profile developer --dry-run --json > /tmp/plan.json
# 看完计划再去掉 --dry-run 真装
```

- **写盘范围**：只有 `~/ecc-trial/.claude/`（代码确认，§4）。983 文件（full）/ 753（developer）。
- **`~/.claude` 受影响**：**零**。
- **能不能用起来**：能。在 `~/ecc-trial` 里开 Claude Code，项目级 `.claude/skills`、`.claude/agents`、
  `.claude/commands` 都会被加载，ECC 的 skill/agent/command 全部可用。
- **回滚**：`rm -rf ~/ecc-trial`，一步到位，比走 uninstall 还干净。
- **不可逆点**：无。
- **残余风险（低 ~10%）**：项目级 hooks 需要 `.claude/settings.json` 才生效，ECC 不写它 → hook 层能力试不到。
  如果你要试 hook，得手工把 `~/ecc-trial/.claude/hooks/hooks.json` 的内容抄进 `~/ecc-trial/.claude/settings.json`
  （这是项目级 settings，不是全局，仍然安全）。

### 路径 B ⭐推荐（要试 home 类 target 时用）：`HOME` 环境变量重定向

```bash
mkdir -p /tmp/ecc-home
HOME=/tmp/ecc-home node /Users/aa00158/harness-research/ECC/scripts/install-apply.js \
  --target claude --profile full
ls /tmp/ecc-home/.claude          # 全部 983 个文件在这里
```

- **依据**：`scripts/install-apply.js:166` —— `homeDir: process.env.HOME || os.homedir()`。
  所有 home 类 adapter 走 `resolveBaseRoot('home', input)` → `input.homeDir`（`helpers.js:40-42`）。
- **上游背书**：ECC 自己的测试套件就是这么做隔离的
  （`tests/scripts/install-apply.test.js:15-34`：`fs.mkdtempSync` + `env.HOME` / `env.USERPROFILE` 覆盖）。
  说明这是被测试覆盖的正式行为，不是野路子。
- **Windows 注意**：还要同时设 `USERPROFILE`（测试文件 :32 就是这么写的）。
- **回滚**：`rm -rf /tmp/ecc-home`。
- **不可逆点**：无。
- **残余风险（低 ~15%）**：`os.homedir()` 在极端情况下不读 `HOME`（macOS 上 Node 的 `os.homedir()`
  会先看 `HOME` 再回落到 `getpwuid`）。但代码里 `process.env.HOME` 是**第一优先级**且短路，
  所以只要 `HOME` 非空就一定命中。
  👉 验证动作：装完立刻 `ls -la ~/.claude/ecc/` —— 不存在就说明隔离成功。

### 路径 C：只装单个 skill（`--skills <synthetic-id>`）

```bash
node scripts/install-apply.js --target claude --skills code-tour --dry-run
```

实测：`skill:code-tour` → **只 1 个文件** `~/.claude/skills/code-tour/SKILL.md`。

> ⚠️ **重大陷阱**：这招只对**合成组件**有效。`manifests/install-components.json` 里**预定义了 15 个 `skill:*` 组件**，
> 它们不是指向单个 skill 目录，而是指向**整个 module**：
>
> | 你以为装 1 个 | 实际拉进来的 module | 实测文件数 |
> |---|---|---|
> | `skill:tdd-workflow` | `workflow-quality` | **85** |
> | `skill:security-review` | `security`（+ workflow-quality + platform-configs） | **106** |
> | `skill:deep-research` | `research-apis` | **16** |
> | `skill:plan-canvas` / `eval-harness` / `verification-loop` / `strategic-compact` / `continuous-learning` / `windows-desktop-e2e` | 全是 `workflow-quality` | 85 |
> | `skill:coding-standards` / `frontend-patterns` / `vue-patterns` / `backend-patterns` | `framework-language` | 大 |
> | `skill:mle-workflow` | `machine-learning` | 大 |
> | `skill:unified-memory` | `skill-unified-memory` | 小 |
>
> 机制：`addSyntheticSkillComponents()`（`install-manifests.js:172-208`）遇到已存在的 component id 就 `continue`（:177-179），
> 所以这 15 个预定义的把合成版顶掉了。
> 剩下 266 个 skill 才是真·单目录安装（`install-manifests.js:184-195`，`paths: ['skills/<id>']`，`dependencies: []`）。

- **写盘范围**：`~/.claude/skills/<name>/`（合成型 1 个目录）。
- **风险**：仍然写进 `~/.claude/skills/`，还是会占你的 skill 触发命名空间；且如果同名（如 `deep-research`）
  会触发冲突跳过。
- **不可逆点**：几乎无（可精准 `rm -rf` 那一个目录）。
- **评价**：适合"只想看某个 skill 怎么写的"，不适合"体验整套 ECC"。

### 路径 D：legacy 模式，只装 rules

```bash
node scripts/install-apply.js --target claude typescript      # 裸语言名，无 --profile
```

- 只写 `~/.claude/rules/ecc/common/` + `~/.claude/rules/ecc/typescript/`（`install-executor.js:317-342`）。
- 不碰 skills / agents / commands。
- rules 是"always-loaded 上下文"，会直接消耗你每次会话的 token 预算，但不改变 skill 触发。
- **不可逆点**：无（`rules/ecc/` 是 ECC 专属命名空间，`rm -rf ~/.claude/rules/ecc` 即可）。

### 路径 E ❌不推荐：`/plugin install ecc@ecc`

- 文件落在 Claude Code 的 plugin cache（`~/.claude/plugins/...`），**不进 `~/.claude/skills/`**，
  文件隔离度其实不错。
- 但：① Claude Code 会往 `~/.claude/settings.json` 写 `extraKnownMarketplaces` + `enabledPlugins`
  （README.md:170-183 就是这两个键）；② plugin 的 281 个 skill 依然进入全局触发面；
  ③ 卸载要走 Claude Code 的 `/plugin` UI，`scripts/uninstall.js` 管不到（README.md:538 承认）。
- **不可逆点**：settings.json 被 Claude Code 改写（虽然是加键，但你 settings.json 有自建 hooks，
  任何自动改写都是风险）。

### 路径 F ❌❌绝对不要：`bash install.sh --profile full`（默认 target=claude）

- 983 个文件进 `~/.claude/`。
- `~/.claude/commands/learn.md`（你 5644 字节的自建命令）**被覆盖，永久丢失**。
- 你的 79 个 skill 被 280 个 ECC skill 稀释。
- `install.sh` 还会在 `node_modules` 缺失时先跑 `npm install`（`install.sh:18-21`）。

### 路径对比总表

| 路径 | 写盘位置 | 文件数 | 碰 `~/.claude`？ | 碰 settings.json？ | 回滚方式 | 推荐 |
|---|---|---:|---|---|---|---|
| A `claude-project` | `$CWD/.claude/` | 753~983 | ❌ 否 | ❌ 否 | `rm -rf $CWD` | ⭐⭐⭐ |
