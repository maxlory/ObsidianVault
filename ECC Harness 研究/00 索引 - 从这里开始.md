## 一 · 结论层（6 份）

### [[01 ECC 工程化流程与工具分类]] ⭐ 主文档，461 行

回答三件事：这些工具怎么被调用、ECC 的工程化流程骨架是什么、每个工具属于哪个环节该不该要。

- **调用机制**：五种部件五种触发者（rules 宿主常驻 / hooks 宿主强制 / skills 模型自主 / agents 模型派发 / commands 人手敲）。破除"装了就自动串成流水线"的误解——ECC 原文写着 **"gated, not autonomous"**
- **流程骨架**：7 阶段（Intake → Research → Plan → **GATE 1** → Scaffold → Implement → Review → Commit → **GATE 2**）+ 5 种操作按意图分流 + 4 档规模分级
- **工具分类**：全部 281 skill / 67 agent / 94 command 按 Phase 0-9 + 3 个横切层重组，每个带取舍标注（❌不装 / ⭐关注但暂不装 / ⚪与你无关 / 🔧骨架件）
- **三个值得移植的设计**：GateGuard 事实强制门的核心论断、陈旧回放防护、right-sizing 分级表

### [[02 ECC 隔离方案与污染面清单]] 162 行

零污染研究/试用的完整方案，全部实测得出。

- 污染面精确清单：`--profile full` 落 **983 个文件**（不是 install-plan 报的 301——那是目录级操作数）
- 覆盖行为分三档：skills 同名跳过是唯一保护，**markdown 和其它一切无条件覆盖且卸载不还原**
- 撞名实测：你的 `commands/learn.md` 会被覆盖 → 装前必须备份
- 试用路径分 7 档，含 `HOME` 重定向沙箱（ECC 自己测试套件用的手法）
- **三个命令级陷阱**：`install.sh --dry-run` 拦不住 npm install、`--skills tdd-workflow` 实际装 44 个目录、卸载不带 `--target` 会扫全部 14 个安装目标（威胁你的 `~/.codex` `~/.openclaw`）

### [[03 ECC 组件筛选报告（基于 Issue 实证）]] 261 行

从 682 条 issue + 8003 条评论里筛出哪些组件真有问题。**方法论可复现，脚本还在**。

- **语料分层**：bot + 作者占 **88%**（7024/8003），真实第三方仅约 979 条
- **方法论硬局限**：句子级情感提取得到负面 177 句、正面 **2 句**——issue 结构上不产生好评
- 两份第三方系统性审计：[#1213](https://github.com/affaan-m/ECC/issues/1213) 用 ECC 自带 `skill-stocktake` 审了 88 个 skill、[#1430](https://github.com/affaan-m/ECC/issues/1430) 用知识图谱审了 299 个 agent 文件
- 我对 #1430 的**修正**：它说 "same template" 夸大了——正文重合实测只有 7-18%
- 筛选结果：281 skill → 8-10 个，67 agent → 4 个，常驻成本 18.9k → <1k token/轮

### [[05 workflow-quality 模块深度解析]] ⭐ 403 行

对唯一默认安装的 skill module（43 个 skill）做的逐个解剖，含两张 mermaid 流程图。

- **文件构成**：36 个纯 SKILL.md vs **7 个带可执行代码**（`continuous-learning-v2` 12 文件 / `ck` 10 / `agent-self-evaluation` 7 / `skill-stocktake` 4 / `rules-distill` 3 / `continuous-learning` 3 / `delivery-gate` 2），逐个列出附加文件干什么
- **43 个按职能分六组**：开发主流程质量 14 / 学习与记忆 6 / 元治理与自我审计 12 / 规划与决策 7 / 上手导览 3 / 上下文管理 1
- 🔑 **协同关系必须分「实锤」和「纸面」**：grep 全部 48 个 hook 脚本，**43 个 skill 里只有 4 个被 hook 层真正引用**（`continuous-learning` v1/v2、`plan-canvas`、`ck`），其余 39 个全靠模型自主判断加载——**装了不等于会生效**
- 🔑 **`delivery-gate` 是唯一会真的拦住你的机制**：220 行 Python Stop hook，含 4 条抓"AI 给自己找台阶"的正则（"先跳过测试" / "这是既有问题" / "测试挂了但我之后会修"），以及三个 `exit 2` 硬阻塞条件
- **完整开发例子**：给 Web 应用加 OAuth2 登录，flowchart 标出每一步是「人手动 / 宿主强制 / 模型自主 / 模型派发」四类触发者中的哪一类；另一张 sequenceDiagram 拆解收工那一刻 `delivery-gate` 的三级判定
- `verification-loop` 是这个 module 的**事实枢纽**（7 个 skill 指向它），但它自己只有 130 行——枢纽比外围薄

### [[06 workflow-quality 重点 skill 详解与调用时序]] ⭐ 532 行

基于我自己的 `重点关注的skills.md` 分类，对 32 个重点 skill 做的逐个详解 + 三张场景时序图 + 一个机制层问题的解答。

- **对我的分类的评价**：我漏了 3 个（`ecc-recipes` / `ecc-guide` / `configure-ecc`），其中 `ecc-recipes` 正是"编排 skill 的 skill"；建议升级 2 个（`error-handling` 因为我做量化会踩数据源限流、`agent-sort` 因为它干的就是组件筛选）；建议降级 1 个（`plankton-code-quality` 绑外部工具）
- **21 + 11 个 skill 详解**：每个给「本质一句话 → 实际怎么工作（内部步骤）→ 对我的用法」
- **三张场景时序图**：接手陌生项目 / 从需求到落地 / 定期治理自己的 79 个 skill
- 🔑 **核心问题解答：有没有编排 skill 的 skill？** 有 —— `ecc-recipes`，但它的 description 第一句就限定 **`Advisory only`**（只给建议不执行）。加上 `orch-pipeline`（"gated, not autonomous"）和 `plan-orchestrate`（"Generative only — never invokes"），**三个编排层没有一个是运行时调度器**
- 🔑 **漏调用的担心完全成立**：skill 靠模型读 description 概率性触发、43 个里只有 4 个被 hook 引用、Claude Code 没有 `disabledSkills`、frontmatter 没有依赖声明字段。四条解法按确定性排序：**hook（唯一 100%）> command 显式入口 > rules 常驻 > description 优化**
- 🔑 **一个意外结论**：我自己的体系在编排这点上已经比 ECC 做得好（`project-lifecycle` 是真编排，ECC 的 `ecc-recipes` 只是顾问）。缺的是 right-sizing 分级表，可以直接从 ECC 搬

### 有实质内容的 4 份

**[[渠道04 HackerNews 与 Lobsters]] 253 行** — 全套里**最锋利**的一份

> "ECC 里我唯一真正觉得有用的 skill 是 `/strategic-compact`……而且这个效果你用一句话 + `/compact <message>` 就能复现。除此之外就是裸奔。ECC 大概带了 300 个 skill，我可能该直接删了它！"

元结论：23 万 star 的仓库在 HN 被投稿 4 次全部 0 评论、被提问 1 次无人回答。对比 Superpowers 196分/254评论、Get Shit Done 473分/247评论。还有人专门做了"把 ECC 装进隔离 microVM"的产品——说明**安装污染被商业化识别为痛点**。
